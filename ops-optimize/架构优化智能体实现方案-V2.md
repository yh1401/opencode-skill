## 总体说明

> 面向中心节点与省节点，结合业务拓扑、运行指标、调用链及宿主机关系，识别可用性、容量、稳定性和故障域集中风险，形成有证据支撑的架构优化建议。
>

## 方案概览

| 分析对象 | 分析重点 | 数据来源 | 预期输出 |
| --- | --- | --- | --- |
| 中心节点：贵州、广州多 AZ | 副本可用性、容量瓶颈、负载分布、OOM、服务依赖 | 模块拓扑接口、Prometheus、Pinpoint 拓扑接口 | 按节点、模块、应用组织的风险清单与优化建议 |
| 省节点：云公司相关节点 | 项目多实例是否集中于同一物理宿主机 | 节点列表、物理机与云主机关系、项目部署拓扑 | 宿主机集中部署清单及故障域分散建议 |

实施流程：**确定分析范围 → 采集数据 → 统一对象映射 → 执行规则 → 汇总证据 → 生成报告**。

分析结果应区分“已发现风险”“未触发规则”“数据不足”和“不适用”。接口失败、监控缺失或关联不完整时，不应直接给出无风险结论。

分析范围覆盖贵州与广州多 AZ 两个中心节点。模块归属以接口返回数据为准，当前业务范围如下。

| 节点 | 模块数量 | 业务模块 |
| --- | --- | --- |
| 贵州 | 6 | 核心业务 API、设备信令调度、直播服务网关、设备告警、云眼核心业务、设备云存上传 |
| 广州多 AZ | 7 | 核心业务 API、设备信令调度、直播服务网关、设备告警、云眼核心业务、设备云存上传（苏州）、消息中心 4.0 |

### 1.2 运行指标检查流程

遍历两个节点返回的 `nodes`，提取各对象的 `projectName`。第一阶段仅对名称以 `-dep` 结尾的应用执行容器检查，其余应用记录为本阶段未覆盖。该命名规则用于初步筛选，Deployment 身份仍需通过监控或资源信息确认。

建议先按节点和应用去重查询，再将结果关联回所属模块；同一应用属于多个模块时，保留全部归属关系。应用名称可能跨集群或命名空间重复，应结合实际监控标签补齐唯一标识。

Prometheus 即时查询接口：`http://183.56.210.90:8082/api/v1/query`。

涉及“持续 15 分钟”的规则，需要完整时间窗口证据，可采用经过验证的 PromQL 时间窗口表达式，或在确认可用后使用范围查询接口。单次即时值不足以证明持续触发。

#### 1.2.1 副本数量与可用性

检查应用副本数是否满足冗余要求，以及期望副本数与可用副本数是否一致。

> 待确认口径：原文要求“是否大于 2 个副本”，对应至少 3 个副本。如业务实际要求为“至少 2 个副本”，应另行确认后配置规则。副本不足与单点部署需分别描述；多个副本也可能位于同一故障域。

**容器指标**

期望副本数：`kube_deployment_spec_replicas`。

示例：kube_deployment_spec_replicas{cmdb_node="云公司->贵州", deployment="ddnsmgr-003151-dep", endpoint="https-main", env="生产",}

可用副本数：`kube_deployment_status_replicas_available`。

kube_deployment_status_replicas_available{cmdb_node="云公司->贵州", deployment="ddnsmgr-003151-dep", endpoint="https-main", env="生产",}

#### 1.2.2 容量瓶颈
- CPU限流风险：限流周期比例＞20%，持续15分钟；关联调用延迟
- 内存容量风险：工作集／有效内存limit＞85%，持续15分钟
- 扩容容量风险：HPA达到最大副本，资源或业务负载仍持续偏高

#### 1.2.3 负载不均衡
- Pod负载不均衡：同规格Pod最大CPU负载／平均负载＞2，持续15分钟

#### 1.2.4 稳定性风险
- OOM风险：近期出现OOMKilled，并有对应重启证据

### 1.3 服务链路与依赖分析

基于 Pinpoint 数据构建服务调用关系，结合模块与应用归属，识别关键依赖和潜在故障传播路径。拓扑连边代表观测到的调用关系；风险判断还需要调用量、耗时、错误率和业务重要性等证据。

| 分析内容        | 能回答的问题               |
| ----------- | -------------------- |
| **服务依赖拓扑**  | 谁调用谁，依赖哪些数据库、缓存和消息组件 |
| **集中依赖**    | 哪些服务或组件被多个上游共同依赖     |
| **下游依赖过多**  | 哪些服务依赖复杂，潜在故障传播面较大   |
| **长调用链**    | 哪些路径可能放大延迟及排障复杂度     |
| **异常依赖**    | 哪些调用边错误率高、耗时长或存在慢调用  |
| **上下游影响范围** | 一个依赖异常，可能影响哪些服务和核心业务 |
| **关键依赖识别**  | 哪些依赖位于多条核心链路上，应优先保护  |
| **循环依赖**    | 是否存在服务间相互调用、边界耦合问题   |

#### 1.3.1 数据获取步骤

1. 按第 1.1 节获取机房模块与应用归属。
2. 对目标模块调用应用链路拓扑接口，保留原始节点、调用边及可用的统计字段。
3. 关联业务归属，汇总依赖风险及受影响模块。

## 二、省节点故障域分析
### 2.1 分析目标与实施步骤

检查同一项目的多个云主机实例是否集中在同一物理宿主机，识别多实例部署背后的共同故障点。原文称为“服务亲和性分析”，其优化目标是分散故障域、满足反亲和部署要求。

1. 获取节点列表，筛选名称以“云公司”开头的节点。
2. 获取物理机与云主机关系，传入节点的 `ctyun_node_code3` 字段。
3. 获取项目列表与部署信息，传入节点的 `node` 字段。
4. 建立“项目 → 云主机 → 物理宿主机”的映射，识别集中部署情况。
5. 输出风险项目、涉及实例、宿主机分布和调整建议。

节点的 `ctyun_node_code3` 为空时，记录为映射数据不足，等待补齐或确认替代查询方式。不同接口使用不同节点标识，不能混用。

通用接口地址：https://easyviews.tech.ctseelink.cn/api/third/thirdAuth/getTykjProvince（POST）

### 2.5 宿主机集中度判定建议

| 场景 | 判定与处理 |
| --- | --- |
| 仅部署 1 台云主机 | 记录单实例部署；是否构成风险由业务冗余要求决定 |
| 多台云主机全部位于同一宿主机 | 明确标记共同故障点，建议分散到不同物理宿主机 |
| 多台云主机分布于多个宿主机，但部分集中 | 输出每台宿主机承载数量与比例，评估单宿主机故障的影响 |
| 部分云主机无法映射宿主机 | 标记数据不足，输出已匹配与未匹配清单，避免低估风险 |
| 同一云主机映射到多个宿主机 | 标记映射冲突，核查数据更新时间及迁移记录 |

建议记录两个统计值：**宿主机数**与**最大宿主机集中比例**。最大宿主机集中比例等于单一宿主机承载的该项目云主机数最大值除以该项目云主机总数。映射不完整时，仅输出已知分布与覆盖率，不据此作完整故障域结论。

## 三、规则口径与证据要求

以下内容为实施建议，不改变前文接口示例及已有阈值。

| 风险类型 | 判定依据 | 需要保留的证据与注意事项 |
| --- | --- | --- |
| 副本不足 | 期望副本未达到已确认的冗余要求 | 期望副本、可用副本、节点及应用；副本要大于 2 |
| 副本不可用 | 可用副本低于期望副本 | 差值、持续时间；关联发布、扩缩容和故障事件 |
| CPU 限流 | 限流周期比例大于 20%，持续 15 分钟 | 对同一容器和时间窗口计算限流周期与总周期的比值；总周期为零时不计算，关联调用延迟 |
| 内存容量 | 工作集 / 有效内存 limit 大于 85%，持续 15 分钟 | 明确容器范围与有效 limit；limit 缺失、为零或不适用时单独记录 |
| 扩容容量 | HPA 达到最大副本，且资源或业务负载仍持续偏高 | HPA 当前与最大副本、目标指标与实际负载；无 HPA 的应用标记不适用 |
| Pod 负载不均衡 | 同规格 Pod 最大 CPU 负载 / 平均负载大于 2，持续 15 分钟 | 统一采样窗口与 CPU 口径，排除不同规格、启动阶段；平均值接近零时避免比值失真 |
| OOM | 近期出现 OOMKilled，并存在对应重启证据 | 容器终止原因、重启增量、时间窗口；“近期”窗口需配置，历史终止原因不能单独证明近期 OOM |
| 链路依赖 | 集中依赖、复杂依赖、长链路、异常调用、循环依赖 | 调用边及统计窗口、请求量、错误率与耗时；链路长度、依赖数等阈值需另行制定 |
| 宿主机集中 | 同一项目多个云主机实例落在同一物理宿主机 | 项目实例列表、宿主机映射、覆盖率及业务角色 |

## 四、数据处理与智能体职责

### 4.1 数据采集与关联

1. 为每次分析记录任务标识、采集时间、分析窗口和目标节点。
2. 校验接口业务状态、必要字段和数据更新时间；对超时或异常执行有限重试，并保留失败状态。
3. 统一节点、模块、应用、项目、云主机及宿主机标识，记录跨数据源的映射依据。
4. 将规则阈值、观察窗口与适用范围配置化，记录本次分析所使用的规则版本。
5. 汇总结果时保留原始证据引用和映射覆盖率，使结论可追溯。

### 4.2 规则引擎与大模型分工

规则引擎负责数据关联、数值计算与阈值判定，保证同一输入得到一致结果。大模型负责解释风险、串联业务影响、组织报告和提出优化建议。对于缺失指标、未确认阈值或接口未提供的字段，大模型应明确说明信息不足，不补造数据。

优化建议需针对证据提出，例如补足副本、调整资源限制、核查 HPA 配置、分散宿主机部署或保护关键下游依赖。具体变更仍需结合业务约束评估；本方案的直接产出为分析报告和建议清单。

## 五、分析报告输出要求

报告按“节点 → 模块 / 项目 → 应用 / 实例”组织，每条风险至少包含以下信息。

| 字段 | 内容要求 |
| --- | --- |
| 分析对象 | 节点、模块、应用或项目及唯一标识 |
| 风险类型与状态 | 风险分类，以及已发现风险、未触发、数据不足或不适用 |
| 判定依据 | 触发规则、阈值、实际观测值、持续时间 |
| 证据 | 指标查询结果、调用拓扑、云主机与宿主机映射及采集时间 |
| 影响范围 | 涉及实例、上下游服务、所属核心业务；推断需显式标注 |
| 优化建议 | 与风险对应的具体处理建议、前置条件和建议优先级 |
| 数据限制 | 指标缺失、映射不完整、采样窗口不足或口径待确认等 |

报告首页建议展示分析范围、采集窗口、数据覆盖率与主要风险。建议优先级结合业务重要性、影响范围和证据充分程度确定，避免仅凭单一指标大小排序。

## 六、实施顺序与验收建议

| 阶段 | 工作内容 | 验收重点 |
| --- | --- | --- |
| 第一阶段：数据联通 | 联调模块、节点、项目与宿主机接口，核实监控标签 | 目标对象可定位，字段含义明确，缺失与冲突可识别 |
| 第二阶段：基础规则 | 完成副本、容量、负载、OOM 及宿主机集中分析 | 规则可配置、持续时间可验证、结果可追溯 |
| 第三阶段：链路分析 | 接入 Pinpoint，关联模块归属与上下游影响 | 明确拓扑覆盖范围、统计窗口和风险判定依据 |
| 第四阶段：报告生成 | 汇总规则结果并生成优化建议 | 每条结论均有证据，数据不足可见，建议与风险匹配 |
