## 1. 接口总览

| 接口 | 方法 | 路由 | 作用 | Handler |
|---|---|---|---|---|
| 关系列表 | GET | `/api/external/operationTopology/list` | 条件分页查询关系记录 | `GetOperationTopologyList` |
| 拓扑图 | GET | `/api/external/operationTopology/graph` | 聚合返回拓扑图 nodes+edges | `GetOperationTopologyGraph` |
| 手动同步 | POST | `/api/external/operationTopology/sync` | **异步提交**一次 Apollo 采集（立即返回，结果经 `/sync/status` 轮询） | `SyncOperationTopology`（handler 提交任务） |
| 同步状态 | GET | `/api/external/operationTopology/sync/status` | 异步同步任务的进度/结果（含 `stageText`/`percent` 进度字段） | `GetSyncTaskStatus` |
| 同步日志 | GET | `/api/external/operationTopology/sync/logs` | 读取最近同步日志（展示最近 256KB，`download=1` 附件下载完整日志） | `GetSyncLogs` |
| 类型枚举 | GET | `/api/external/operationTopology/middlewareTypes` | 中间件类型 distinct 列表 | `GetOperationTopologyMiddlewareTypes` |
| 节点详情 | GET | `/api/external/operationTopology/detail` | 单节点完整元数据（应用/中间件） | `GetOperationTopologyDetail` |

> 全模块共 **7 个接口**：查询类 4 个（graph / list / detail / middlewareTypes）＋ 同步类 3 个（sync 异步提交 / sync/status 轮询 / sync/logs 日志读取）。其中 `detail`（节点详情）的请求/响应在《[curl-接口测试文档.md](curl-接口测试文档.md)》§9.1 展开；本表其余接口在下方小节逐一说明。

路由挂载于 `/api/external` 组（`ExternalApiGroup`），前缀 `operationTopology`，见 [router/operation_topology.go](../router/operation_topology.go)。

调用链路统一：`Handler → service 层 → 数据源路由`（`datastore.mode=auto` 时 DB 优先、不可用回退本地快照/镜像文件）+ `global.GVA_LOG`（zap 日志）。handler 不做业务逻辑，只做参数绑定、调用 service、统一响应封装。

## 2. 核心数据链路（各接口共享）

```
Apollo(EasyOps代理) ──采集──▶ 解析规则 ──▶ 快照落库(operation_topology) ──▶ 查询聚合 ──▶ 前端
   │  /sync 触发               │ 中间件规则匹配        │ DB 优先 / 文件镜像降级      │ /list /graph 读取
   │  定时任务每天01:30          │ 地址提取(host:port)   │ 按 sync_date 定位最新       │ 属性补充关联

关系接口(EasyOps) ──采集──▶ app_dp_relation（跳①：appId ↔ 部署项目）──▶ 与主表内存 join
   (随同一次同步)               有变化才替换 + 文件镜像                 deploy_pinpoint_relation（跳②：DB→文件）
```

数据采用**每日快照**策略：按 `sync_date` 分桶（表列 / 文件 `data:{sync_date:{env:[行…]}}`），同 `sync_date` 重复同步 = **整表/整桶替换**；每次同步后按 `topology_snapshot_keep`（默认 3）**只保留最近 3 个日期桶**（DB 表与本地文件同口径，更早的桶清理），既能拿上一版做前后对比，又不会随同步次数无限堆积。查询默认取**最新快照日期**。跳① 关系表不含日期维度，每次同步与库内数据比对，**仅在检测到变化时整表替换**（无变化跳过，表内不产生无谓膨胀）。

## 3. 接口一：关系列表 `GET /list`

### 3.1 请求参数（Query）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `page` | int | 1 | 页码 |
| `pageSize` | int | 20 | 每页条数 |
| `node` | string | - | **appId 属性**：机房/节点精确匹配（查询期属性补充回填值；下推 + 属性补充后复核） |
| `engProject` | string | - | **appId 属性**：工程项目名精确匹配（同一 appId 的属性列表内匹配） |
| `ppApplication` | string | - | **appId 属性**：PP 应用名精确匹配（同一 appId 的属性列表内匹配） |
| `env` | string | - | 环境精确匹配 |
| `middlewareType` | string | - | 中间件类型精确匹配 |
| `depProject` | string | - | **appId 属性**：部署项目名**模糊**匹配（包含匹配，等价 LIKE %xx%） |
| `apolloAppId` | string | - | appid 精确匹配 |
| `apolloHostName` | string | - | Apollo 实例（套）名称**模糊**匹配（包含匹配） |
| `connectAddr` | string | - | 连接地址**模糊**匹配 |
| `syncDate` | string | 最新快照 | 快照日期 YYYY-MM-DD |
| `expandDepNode` | bool | **`true`（默认展开）** | 部署点展开开关（`*bool` 三态，与 `/graph`、`/detail` 同口径）：不传 / `1` / `true` → 展开（按部署点扩行，`pageTotal` = 5266）；显式 `0` / `false` → 折叠（属性补充不扩行，`pageTotal` = 1418）。量级随每日快照变化，以接口返回为准 |
| `source` | string | 无（默认 `db` 优先，不可用回退 `file`） | 数据源覆盖 `db\|file` |

> 上表 `expandDepNode` 影响 §3.2 步骤 5~6 的实现分支与 `pageTotal` 口径，详见下方「口径分支」与《[运维拓扑.md](运维拓扑.md)》§4.5。

### 3.2 处理逻辑

```
1. 参数兜底：page<=0 → 1；pageSize<=0 → 20
2. 数据源路由：`mode=auto` 时 DB 优先，不可用回退本地快照文件（每请求可用 `source=db|file` 覆盖）
3. 若 syncDate 为空 → LatestSyncDate(env) 取最新快照日期（带 env 过滤）
4. 过滤下推 relationFilterApps(attr)：depProject/engProject/node/ppApplication 四属性经跳①×跳② 索引收窄候选 apollo_app_id 集合（只收窄，不替代复核）
5. 取全量候选行（Page=1,PageSize=-1）→ attachAppAttrs：跳①×跳② 属性补充（多值聚合为列表，不扩行；dep_project/eng_project/node/pp_application 单值列取列表首值，多值走 depProjects/engProjects/nodes/ppApplications）
6. filterAttachRows 属性补充后复核（判定粒度为 appId，任一属性命中即保留该 appId 的全部关系行）+ 其余可选条件内存过滤
7. 内存倒序（行序逆序，等价 DB id desc；**file 模式下 `id` 恒为 0，仅行序可见**）+ 分页窗口收集（只留当前页；total = 候选关系行数，不放大）
8. 返回 { code, list, pageTotal }
```

> **口径分支（`expandDepNode`）**：上列步骤 5~6 描述**折叠口径**（显式 `expandDepNode=0`）：属性补充不扩行，`pageTotal` = 快照关系行数（1418）。**默认展开**时改为按部署点扩行（`expandByDeploySlot`，行本身即部署点粒度、属性取单值），复核走 `filterSlotRows`，`pageTotal` = 5266（2026-09-20 快照）。两种口径完整对照见《[运维拓扑.md](运维拓扑.md)》§4.5。

> **下推与复核必须同口径**：属性以 appId 为粒度聚合为并集列表，各维度分别在该 appId 的属性列表内匹配。下推若改为「要求同一条属性项同时满足所有维度」，会把「不同维度由不同属性项满足」的 appId 误剔除，而候选集即最终可读行范围，复核阶段无法再补回（结果少数据）。

### 3.3 响应

```json
{
  "code": 0,
  "list": [ { "id":2837, "node":"", "engProject":"", "depProject":"area-prod-224326-dep",
              "ppApplication":"area", "apolloAppId":"area",
              "depProjects":["area-prod-224326-dep"],
              "middlewareType":"mysql", "connectAddr":"areacode.mysql.vcpinner.cn:13302", "...": 全字段 } ],
  "pageTotal": 1418
}
```

> 注：实际响应仅含 `code / list / pageTotal` 三个顶层字段（与《[curl-接口测试文档.md](curl-接口测试文档.md)》§3 校正一致）。`pageTotal` = 候选关系行数（示例为折叠口径 = 当前快照全量行数 1418；**默认展开时为 5266**），属性补充不扩行。
> 上例 `id`（2837）为 DB 自增主键；**file 模式下恒为 `0`**，此时「内存倒序 / 升序」只体现为行序（见《[运维关系拓扑图方案.md](运维关系拓扑图方案.md)》§3.3）。
> 多值列表字段为空时整体不输出（`omitempty`）：上例 `engProjects` / `nodes` / `ppApplications` 为空故不出现。字段值随快照与两跳回填变化。

### 3.4 关键点

- **列表视图 = 候选关系行（appId × 中间件）**：每行一条「应用→中间件」关系，`dep_project/eng_project/node/pp_application` 四列由跳①（ADR）×跳②（DPR）在**查询期作为 appId 属性补充**（单值取首值 + 多值列表字段），**折叠口径下**行数与行序不变，`total` = 候选关系行数（不放大；**默认展开口径按部署点扩行，`pageTotal` = 5266**，见 §3.2「口径分支」），含 namespace/config_key 溯源字段
- **过滤下推 + 复核缺一不可**：`relationFilterApps(appAttrQuery)` 只收窄候选，`filterAttachRows` 才是最终判定（判定粒度为 appId）
- 与 `/graph` 的区别：list 返回明细（可溯源、可分页），graph 返回聚合结果（可直接渲染）
- 完整字段口径与来源见《[运维关系拓扑图方案.md](运维关系拓扑图方案.md)》§3.3「字段转换来源」

## 4. 接口二：拓扑图 `GET /graph`

### 4.1 请求参数（Query）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `env` | string | - | 环境过滤 |
| `depProject` | string | - | **appId 属性**：部署项目名（**模糊**；下推 + 属性补充后复核） |
| `engProject` | string | - | **appId 属性**：工程项目名（**精确**；下推 + 属性补充后复核） |
| `node` | string | - | **appId 属性**：机房/节点（**精确**；下推 + 属性补充后复核） |
| `ppApplication` | string | - | **appId 属性**：PP 应用名（**精确**；下推 + 属性补充后复核） |
| `middlewareType` | string | - | 中间件类型过滤 |
| `syncDate` | string | 最新快照 | 快照日期 |
| `source` | string | 无（默认 `db` 优先，不可用回退 `file`） | 数据源覆盖 `db\|file` |
| **`expandDepNode`** | bool | **`true`（默认展开）** | **部署点展开开关**（`*bool` 三态）：不传 / `1` / `true` → 展开，应用节点粒度 = `appId + 部署项目 + 节点`（id 形如 `app:{appId}\|{部署项目}\|{节点}`）；显式 `0` / `false` → 折叠为 appId 粒度（id 形如 `app:{appId}`），属性多值聚合为列表 |

> 四属性参数与 `/list` 同口径（`GraphQuery` / `OperationTopologyListReq` 字段一致，均由 `appAttrQuery` 承载）。
> `expandDepNode` 亦与 `/list`、`/detail` 同口径（`/list`、`/detail` 同名参数见各自小节）；**不传即展开**是其默认行为，折叠必须显式传 `0`。

### 4.2 处理逻辑

```
1. syncDate 为空 → LatestSyncDate(env)
2. 过滤下推 relationFilterApps(attr) 收窄候选 → 取全量行 → attachAppAttrs 两跳属性补充 → filterAttachRows 复核（判定粒度为 appId，属性任一命中即保留该 appId 的全部关系行）
   · 下推与复核同口径：属性按 appId 聚合为并集列表（DepProjects/EngProjects/Nodes/PpApplications），
     各维度分别在该 appId 的属性列表内匹配（不做「同一条属性项同时满足所有维度」的误剔除）
3. 按 sync_date + env + node + middlewareType 内存过滤
4. 内存聚合（见 4.3）
5. 无节点时返回"暂无数据"提示
```

> **口径分支（`expandDepNode`）**：上列第 2 步为**折叠口径**（显式 `expandDepNode=0`）：属性补充不扩行、复核走 `filterAttachRows`。**默认展开**时改为按部署点扩行（`expandByDeploySlot`，行即部署点粒度、属性取单值），复核走 `filterSlotRows`；两种口径的节点/边规模差异见 §4.3-① 与《[运维拓扑.md](运维拓扑.md)》§4.5。

### 4.3 拓扑聚合规则（内存实现，核心）

对每一行关系做两次 map 合并：

```
① 应用节点：按 appKey 合并（appKeyOf 随 expandDepNode 分支）
   展开（默认，不传 / 1 / true）：appKey = apollo_app_id + "|" + 部署项目 + "|" + 节点，id = "app:" + appKey（一个部署点一个节点）
   折叠（expandDepNode=0）：appKey = apollo_app_id（缺失回退 dep_project），id = "app:" + appKey
   携带：node / engProject / depProject / ppApplication（跳①×跳② 查询期属性补充，单值取列表首值）
        + 多值列表 depProjects / engProjects / ppApps / nodes / apolloAppId（折叠态保留，展开态清空）
   同一 appId 多行属性取并集，不因属性多值分裂节点（**折叠态**；展开态按部署点分裂为多节点，故 `application` 节点数 108 → 240、`edges` 756 → 2943）
   > 注：展开只在查询期做、不落库（唯一索引不含 dep_project / node，落库展开必撞索引）
   ApolloHosts：归属的 Apollo 实例（套）去重列表 [{id, name}] ← 实例为顶层归属维度
   同一应用跨多套实例出现 → 本节点带多条实例归属，但只生成 1 个节点

② 中间件节点：按 (middleware_type + connect_addr) 合并  ← 防拓扑爆炸的关键
   id = "mw:" + middlewareType + ":" + connectAddr
   携带：mwType / addr / mwProject
   同一中间件被多个应用连接 → 只生成 1 个节点（扇入）

③ 边：应用→中间件，edgeSet 去重（同一对只保留一条）
   kind = "depend"
   （host→app 的实例归属边不在此生成，前端依据应用节点 ApolloHosts 渲染虚线归属层）

④ 汇总：遍历边，统计每个中间件节点被多少应用依赖
   depCount（角标数字）+ appIds（被依赖应用清单，排序）

⑤ 实例汇总：遍历应用节点 ApolloHosts 收集本次快照出现的实例（套）列表
   resp.ApolloHosts（按 id 排序，供前端实例筛选下拉/归属层）
```

> 注：`data.counts` 为**与当前过滤条件一致**的列表规模汇总（模型 `GraphResp.Counts`）：`apolloHosts`=返回 `apolloHosts` 数组长度；`application`/`middleware`=返回 `nodes` 中对应 `category` 的个数；`edges`=返回 `edges` 条数；`nodes`=返回节点总数（=application+middleware）。**仅 `/graph` 返回该字段**（list/detail/middlewareTypes/sync、sync/status、sync/logs 均无）；无数据（空图）时全部为 0。
> 上例 `counts` 为**折叠口径（`expandDepNode=0`）**；**默认展开**时同条件（`env=PRO`、最新快照）实测 `application` 240 / `middleware` 341 / `edges` 2943 / `nodes` 581（2026-09-20 快照），且应用节点 id 形如 `app:{appId}|{部署项目}|{节点}`。两种口径完整对照见《[运维拓扑.md](运维拓扑.md)》§4.5。

### 4.5 关键点

- **聚合全部在 Go 内存完成**：file 源直接全量取内存行聚合；DB 源（后续版）SQL 只负责取行。聚合逻辑与数据源解耦，可复用（前端渲染、导出、扩展过滤都基于同一份聚合）
- **中间件按「类型+地址」合并**是防拓扑爆炸的核心：多个应用连同一个 `ehome-pro.mysql.ehomeinner.cn:13302`，图中只生成一个 MySQL 节点
- 节点 id 规范 `app:{...}` / `mw:{...}` 是前端渲染与交互（点击/hover/搜索）的稳定标识
- 数据量评估：折叠口径（449 节点 / 756 边）实测 ~35ms；**默认展开口径规模更大（581 节点 / 2943 边，2026-09-20 快照）**，万级以上需考虑字段裁剪/结果缓存
- 节点视觉与交互规范见《[运维关系拓扑图方案.md](运维关系拓扑图方案.md)》§6

## 5. 接口三：手动同步 `POST /sync`（异步提交）＋ 状态轮询 `GET /sync/status`

> **为什么异步**：全量同步是**分钟级长任务**（真实环境几百应用 × 多 namespace，几十秒~数分钟），走 HTTP 网关/负载均衡（LVS/Tengine 默认几十秒超时）必然 504。故 `/sync` 只负责**提交**（立即返回），后台 goroutine 执行采集，调用方**轮询** `/sync/status` 获取进度与结果——彻底绕开网关超时。
>
> 服务端：handler 调 `StartSyncTask(trigger)` → 启动 goroutine 执行 `syncOperationTopology(trigger, progress回调)`；任务期间进度实时写入进程内单例 `currentSyncTask`，`/sync/status` 读取快照返回。`syncOperationTopology` 内部持 `syncMu`，与每天 01:30 cron（走 `SyncOperationTopology()` 公共入口、无进度上报）**天然互斥排队**，不会双跑。cron/启动自检等同步调用不受影响（进度回调为空时不产生开销）。

### 5.1 处理逻辑（六阶段概览）

| 阶段 | 动作 | 关键点 |
|---|---|---|
| ⓪ 关系同步（跳①） | 关系接口一次拉全量（`paginator=false` + `pageSize=-1`）→ 与库内数据比对，**有变化才整表替换** `app_dp_relation` + 回写镜像 → 失效内存索引 | 先于主表采集执行；无变化跳过替换（不删不写）；整体成或整体降级（保留上一版数据）；成败经 `relationErr`/`relationMsg` 上报（见 §5.2、§12） |
| ① 查套 | 接口1 `getApolloHostInfo` → Apollo 套列表（`host.id` = apolloHostId） | 可选 `APOLLO_HOST_NAME` 过滤套名；并发探活 30s 预算，不可用套跳过 |
| ② 查应用 | 逐套调接口2 `apollo/apps` → 应用列表 | 兼容 `data` 数组 / `{total,items}` 两种结构；组装「套 × 环境 × 应用 × namespace」扫描任务 |
| ③ 抓取解析 | 8 worker 调接口3 `apollo/namespace`，每个配置项跑双路径解析规则 → 关系记录 | context 预算默认 60s；**含全名单猜测时自动放大至 5m**；超时 → `partial=true` + `unfinishedApps` |
| ④ 快照对比 | 与更早快照（`PreviousSnapshot`）做差集 | 输出 `newRelations` / `lostRelations` |
| ⑤ 替换快照 | 结束时刻一次性落盘 | **分档决策**（见 §11.6）：整批成功 → 原子替换；预算截断且已有旧快照 → 保留不覆盖；个别应用失败 → 仍落盘并继承旧行 |

> 各阶段详细实现（发现/解析/组装/去重/落盘）见 §11。扫描名单由 **ns 学习定向**（§14）决定：无记录 → 固定全名单首扫 `bootstrap`；有记录 → 只扫「历史命中集 + application」`targeted`；超期 → 全名单兜底重猜 `recheck`。

> **进度上报**（异步任务场景）：各阶段通过进度回调把「阶段文案 + 完成度」写入任务状态——`percent` 0~100，探活/拉应用等无定量阶段为 `-1`；扫描阶段按已完成 namespace 请求数/任务总数计算（`正在扫描配置 d/N`）；collector 每收一批同时上报规模统计 `stats`（hosts/apps 组装后即定，middleware 按 类型+地址 去重、relations 随解析实时增长）。`/sync/status` 返回 `stageText`/`percent`/`stats` 供前端渲染进度条与统计卡（详见 5.5）。

> **并发互斥**：`syncOperationTopology` 全程持 `syncMu` 互斥锁——定时任务与手动 `/sync` 同时触发时排队执行，避免同日重复整桶替换竞争写坏快照文件。同步执行期间接口 `/list` `/graph` 读取不受影响（读的是文件已落盘的快照桶）。

### 5.2 响应

**① 提交响应 `POST /sync`（立即返回）：**

```json
{
  "code": 0,
  "data": {
    "started": true,
    "message": "同步任务已提交，请轮询 /operationTopology/sync/status 获取结果",
    "state": { "running": true, "triggerBy": "手动同步(页面/sync接口)", "startTime": "2026-09-08 16:00:00", "stageText": "任务已提交，等待执行", "percent": 0, "costMs": 5 }
  },
  "msg": "同步任务已提交"
}
```

- `started=true` 已提交；`started=false`（已有任务执行/排队）时同样轮询即可，无需重复提交。

**② 状态响应 `GET /sync/status`（轮询，data = SyncTaskState）：**

```json
{
  "code": 0,
  "data": {
    "running": true,
    "triggerBy": "手动同步(页面/sync接口)",
    "startTime": "2026-09-08 16:00:00",
    "costMs": 214000,
    "error": "",
    "stageText": "正在扫描配置 456/1077",
    "percent": 42,
    "stats": { "hosts": 8, "apps": 359, "middleware": 156, "relations": 2810 },
    "result": null
  },
  "msg": "操作成功"
}
```

| 字段 | 含义 |
|---|---|
| `running` | 是否有任务在执行；`false` 后 `stageText`/`percent` 清空，`stats` 保留最终值，`result` 为最终结果 |
| `stageText` / `percent` | 阶段文案 / 完成度（0~100；`-1`=该阶段无定量进度），供前端进度条展示 |
| `stats` | 规模统计（运行中实时、完成即最终）：`hosts` Apollo 套数、`apps` 应用数（组装后即定）、`middleware` 中间件节点数（类型+地址 去重）、`relations` 连接关系条数；供前端弹窗统计卡展示 |
| `result` | 完成后非空：`SyncResult`（hostCount/appCount/namespaceCount/insertCount/partial/newRelations…，去重与无中间件相关字段见下） |

**`result`（SyncResult）关键字段：**

| 字段 | 含义 |
|---|---|
| `relationRows` / `relationWrote` | 跳① 本次拉取关系行数 / 是否执行了「清空 + 重写」（数据无变化跳过替换时为 `false`，属正常） |
| `relationErr` / `relationMsg` | 跳① 是否**异常**（`true` 需运维介入）/ 结果说明；异常时日志总览与 `resultText` 以 `【异常】` 标注，且**不阻断主表同步** |
| `nodeStats` | `map[中间件类型]int`：按「类型+地址」**去重**的中间件节点数（与拓扑图节点口径一致） |
| `typeStats` | `map[中间件类型]int`：各类型**关系数**（含实例重复，未按地址去重，与 `nodeStats` 并存对照） |
| `nsTargeted` / `nsBootstrap` / `nsRecheck` | ns 扫描策略三元组计数（定向 / 首扫 / 兜底重猜），见 §14 |
| `noMiddlewareCount` / `noMiddlewareApps` | 无中间件应用数量 / 明细 `[{appId, appName}]`（按 appId 升序），位于 result JSON 末尾 |

**跳① 关系同步成败口径（`relationErr`）**：

| 情形 | `relationErr` | 语义 |
|---|---|---|
| 正常落库 / 接口未启用 / 拉取 0 行 / 无 DB 连接（仅写镜像） | false | 正常或正常降级，不报错 |
| 上游拉取失败 / 关系表 `app_dp_relation` 缺失 / 写库失败（事务回滚） | **true** | 异常，需运维介入（表缺失即 AutoMigrate 未建表，检查 DB 连接与权限；`operation_topology` 与 `app_dp_relation` 由启动 AutoMigrate 自动创建，`deploy_pinpoint_relation` 不纳入 AutoMigrate、由运维按 `docs/业务数据/deploy_pinpoint_relation.sql` 自建/导入） |

**`noMiddlewareCount`/`noMiddlewareApps` 判定口径（重要）**：统计本次**已实际执行过 namespace 拉取**（任意 ns 有返回即算，404 也算）但**未解析出任何中间件关系行**的应用；**排除**「未完成应用」（拉取失败）与「未执行应用」（预算截断未轮到，无法判定）——**没扫到的应用不算“无中间件”**。

日志体现：同步结束如数量 >0，打印整块「本次同步 · 无中间件应用清单（已扫描未发现中间件关系）共 N 个（不含未完成/未执行应用）」并按 appId+应用名逐行列出；日志末尾「本次同步 · 结果总览」块内新增一行汇总「无中间件应用 N 个（已扫描未发现中间件关系）：appId1（名1）, …（最多示例 5 个）」（日志链路见 §8.1 / §9）。

### 5.3 关键点

- **并发 + 预算控制**：8 worker + context 超时（默认 60s；**含全名单猜测任务——首扫 bootstrap/兜底重猜 recheck——自动放大至 5m**，定向 targeted 回归默认），超时返回 partial 不阻塞任务（容错设计）
- **进度可观测**：异步任务每个阶段写入 `stageText`/`percent`，轮询即得真实进度（非模拟）
- **快照覆盖分档**（详见 §11.6）：① 整批成功 → 原子替换；② **预算截断**且已有旧快照 → **保留旧快照不覆盖**，避免半成品顶替好数据；③ **任务全部执行但个别应用失败 → 仍整批落盘**，失败应用的上版快照行并入本次（方式 B 继承），避免“个别失败→长期不落盘→快照停在旧版”；空产物 → 不覆盖
- **幂等**：同一 `appId+实例+环境+类型+地址` 去重，重复执行不会产生重复行（同一 `sync_date` 桶覆盖写入）
- **跳① 关系同步前置**：每次同步先全量拉取关系数据并**与库内现有行做多重集比对**（只比业务列，时间列不参与），**有变化才清空替换** `app_dp_relation`（事务回滚保底），无变化跳过不删不写，避免表内无谓膨胀；**异常不阻断主表**；关系接口未启用/拉取 0 行时保留上一版数据，避免误清空

## 6. 接口四：同步日志读取 `GET /sync/logs`

> 用途：读取最近同步（手动 `/sync` 或每日定时任务）**落盘的日志文件**，排障不必登录服务器翻盘。日志由 `tplog` 模块**按天落盘**为 `YYYY-MM-DD.log`（默认目录 `api/tprel/logs`，可用环境变量 `TPREL_LOG_DIR` 覆盖，见 §9 日志规范）；一天内多次同步累积在同一文件，读该文件即得当天完整同步链路。Handler：`GetSyncLogs`（[api/operation_topology_api.go](../api/operation_topology_api.go)）。

### 6.1 请求参数（Query）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `date` | string | 否 | 日志日期 YYYY-MM-DD；缺省自动选**最近一天有日志**的文件 |
| `download` | string | 否 | `"1"`/`"true"` 时以 `text/plain` **附件下载**该日志完整内容，不返回 JSON |

`date` 已做**严格正则（YYYY-MM-DD）+ 目录穿越双重防护**（解析后路径必须仍位于日志目录内，见 6.2 步骤 3）。

### 6.2 处理逻辑

```
1. 列日志目录内可用文件清单（YYYY-MM-DD.log，日期倒序，最多 30 条）
2. date 缺省 → 取清单首项（最近一天）；目录为空 → 返回 code=7「暂无同步日志（日志目录为空）」
   date 非空但格式非法 → 返回 code=7「date 参数格式非法（应为 YYYY-MM-DD）」
3. 拼 date+".log" 并校验解析后路径仍位于日志目录内（防目录穿越）；
   文件不存在 → 返回 code=7「该日期无同步日志: YYYY-MM-DD」
4. 展示模式：读文件内容（≤256KB 全量返回；更大只取尾部 256KB，truncated=true）
   download=1：以附件（Content-Type: text/plain）返回完整文件，不返回 JSON
```

### 6.3 响应（展示模式）

`data` 字段：

| 字段 | 含义 |
|---|---|
| `date` | 命中日期（YYYY-MM-DD） |
| `file` | 文件名（`YYYY-MM-DD.log`） |
| `sizeBytes` | 文件字节数 |
| `content` | 日志内容（**展示模式只取最近 256KB**，超长时 `truncated=true`；完整内容请用 `download=1`） |
| `files` | 可用日志文件清单 `[{date, file, sizeBytes}]`（日期倒序，最多 30 条） |

```json
{
  "code": 0,
  "data": {
    "date": "2026-09-20",
    "file": "2026-09-20.log",
    "sizeBytes": 10621225,
    "content": "...（日志多行文本，展示模式最近 256KB）...",
    "truncated": true,
    "files": [
      { "date": "2026-09-20", "file": "2026-09-20.log", "sizeBytes": 10621225 },
      { "date": "2026-09-19", "file": "2026-09-19.log", "sizeBytes": 1330729 },
      { "date": "2026-09-18", "file": "2026-09-18.log", "sizeBytes": 6650566 },
      { "date": "2026-09-17", "file": "2026-09-17.log", "sizeBytes": 1990023 }
    ]
  },
  "msg": "操作成功"
}
```

### 6.4 示例 curl

```bash
# 默认：最近一天有日志的同步日志
curl "http://127.0.0.1:8098/api/external/operationTopology/sync/logs"

# 指定日期
curl "http://127.0.0.1:8098/api/external/operationTopology/sync/logs?date=2026-09-09"

# 下载完整日志（text/plain 附件；curl -OJ 自动落盘为 operation-topology_2026-09-09.log）
curl -OJ "http://127.0.0.1:8098/api/external/operationTopology/sync/logs?download=1"
```

### 6.5 错误返回（code=7）

| 场景 | msg |
|---|---|
| `date` 格式非法 | `date 参数格式非法（应为 YYYY-MM-DD）` |
| 该日期无同步日志 | `该日期无同步日志: YYYY-MM-DD` |
| 日志目录为空（从未同步） | `暂无同步日志（日志目录为空）` |

### 6.6 关键点

- **与日志落盘目录的关系**：日志文件默认在 `api/tprel/logs`（环境变量 `TPREL_LOG_DIR` 可覆盖，见 §9）；本接口按 `YYYY-MM-DD` 对齐每日文件，date 缺省时自动选最近一天，调用方无需关心目录细节
- **与 `/sync` `/sync/status` 的关系**：后两者“产生 + 汇总”同步过程，本接口“读取”过程日志，配合完成同步排障闭环（SyncResult 结构见 §5.2）
- 展示模式截断只影响响应体大小（保留最近 256KB），不影响日志文件本身；需要完整文件一律用 `download=1`

## 8. 定时任务（非接口，但驱动数据）

- 注册：`core/server.go` 写死注册 `0 30 1 * * * ?`（每天凌晨 01:30，`config.apollo.sync_cron` 仅作展示），启动时打印「定时同步已注册」日志

- 入口：`cronTask/operation_topology.go` → 调用 `SyncOperationTopology()`
- 与手动同步共用同一实现，无并发冲突（快照覆盖语义 + `syncMu` 互斥）

### 8.1 定时处理完整日志链路（排障只需看日志）

每天定时触发时，`api/tprel/logs/YYYY-MM-DD.log` 会顺序输出一条完整闭环，可按下面四个关键字检索串联：

| 顺序 | 关键字 | 打印位置 | 记录的关键出入参 |
|---|---|---|---|
| ① 注册 | `定时同步已注册（运维关系拓扑）` | `core/server.go`（服务启动时，仅一次） | `cron`、`syncEnable` |
| ② 触发 | `定时任务被触发` | `cronTask` | `triggerAt`（毫秒）、`cron`、`syncEnable` |
| ③ 执行入口 | `同步入口/同步开始` | `service` | `syncDate`、`envs`、`namespaces`、`workers`、`scanBudget`、`baseUrl` |
| ③ 采集过程 | `请求完成` / `扫描任务组装完成` / `含全名单猜测任务，扫描预算自动放大`（Warn）/ `规则命中` / `解析摘要` / `扫描耗时统计` | `service` | 逐条请求 url/耗时、任务数、bootstrap/recheck 时预算放大（from/to）、key→type 命中、items→rels 出入参、requests/avgMs/maxMs |
| ③ ns 学习/缺失 | `执行计划总览`（ns扫描策略）/ `ns 学习状态已加载` / `ns 学习状态已回写` / `本次同步 · 中间件缺失（namespace 不存在=未接入对应中间件）`（Warn） | `service` | `targeted`（定向）/`bootstrap`（首扫）/`recheck`（兜底重猜）三元组计数；学习文件 keys 数；按应用逐条列出缺失的中间件型 namespace（404=未接入对应中间件） |

## 9. 日志规范

- 模块标识：按链路分流，便于 grep —— `[operation_topology]` 采集/同步/查询主链路、`[dp_relation]` 跳① 关系层（接口/表/镜像加载、属性索引）、`[pinpoint]` 跳② DPR 映射加载、`[datastore]` 数据源路由与降级
- **日志落盘**：`api/tprel/logs/YYYY-MM-DD.log`（模块专用 logger，见 [tplog](../tplog/tplog.go)），默认每日一个文件，跨天自动切换，**自动只保留最近 5 个日志文件**（进程内删除，不用外部 `rm`）；目录可用环境变量 `TPREL_LOG_DIR` 覆盖
- 输出形式：结构化文本 + 可读毫秒时间（`2006-01-02 15:04:05.000`），控制台同步打印
- 同步链路逐步记录：三段“本次同步 ·”清单日志（实例清单 → 应用清单 → 入库中间件清单）→ 请求数 → 解析条数 → partial 标记 → 新增/消失差异 → 快照落盘结果（整批成功 = `已原子替换本地快照`；个别应用失败仍落盘 = `N 条解析 + 失败应用继承 M 行`；预算截断/空产物且已有旧快照 = 保留现有快照，kept=N，见 §11.6）
- 无中间件统计（同步结束时）：数量 >0 时打印整块「本次同步 · 无中间件应用清单（已扫描未发现中间件关系）共 N 个（不含未完成/未执行应用）」并按 appId+应用名逐行列出；「本次同步 · 结果总览」块内新增一行汇总（口径见 §5.2）。日志按天落盘（见上），可由 `/sync/logs` 接口按日期读取/下载（§6）
- 失败场景独立记录：套查询失败、应用列表失败、单任务扫描失败（appId+ns+env+错误）、直写本地快照失败（写文件错误）
- ns 学习与缺失提示：扫描任务组装/执行计划总览日志含 `ns扫描策略`（`学习定向 targeted=N / 首扫 bootstrap=N / 兜底重猜 recheck=N`，未启用 = `固定名单猜测（ns 学习未启用）`）；加载学习文件记 `ns 学习状态已加载`、批末回写记 `ns 学习状态已回写`（回写失败 Warn 不影响本次同步结果）；中间件型 namespace 404 缺失时按应用**逐条 Warn**「本次同步 · 中间件缺失（namespace 不存在=未接入对应中间件）」`appId/name/missingNs`
- 定时任务如此前各环节均在日志中留痕，且定时异常（sessionId 过期、扫描失败、快照落盘失败）均有独立的 Error/Warn 记录，便于次日排障
- **归档日志索引**：端到端验证（正常链路 / DB 降级 / 全降级 / 关系表缺失报错）的归档日志与决定性行号，见 [`logs/README.md`](../logs/README.md)

## 11. 采集链路详解：Apollo 配置 → 本地快照

> 本节详细拆解「`POST /sync`（异步提交触发的）Apollo 采集 → 本地快照」的完整过程（对应实现：[service/apollo_client.go](../service/apollo_client.go) + [service/operation_topology.go](../service/operation_topology.go)）。

### 11.1 一条配置项的旅程

```
Apollo 某应用配置了 spring.datasource.url=jdbc:mysql://db-master:3306/mydb
        │
        ▼ ①发现（3个接口三级遍历）
EasyOps 代理 → 套列表 → 应用列表 → namespace 配置项
        │
        ▼ ②解析（规则匹配 + 地址提取）
key 含 "jdbc:mysql" → 类型=mysql；正则提取 → db-master:3306（密码丢弃）
        │
        ▼ ③组装（映射 + 补充元数据）
+ 实例归属（apolloHostId/apolloHostName：来源于本次扫描的套）+ `pp_application` 占位（ownerFor）+ node/工程/部署预留空值 + env + syncDate + 溯源字段
        │
        ▼ ④去重汇总
appId|实例(hostId/hostName)|env|类型|地址 唯一键去重（实例为顶层归属维度，同应用跨多实例各自保留）
        │
        ▼ ⑤落盘（分档原子替换，见 11.6）
本地文件 operation_topology.json 中当日 sync_date 桶内一行记录
（同日重跑 = 整桶替换；每次同步后只保留最近 topology_snapshot_keep 份日期桶，默认 3，DB 表同口径）
```

### 11.2 第①步：发现（找到所有配置在哪）

三级遍历，对应 `ApolloClient` 的三个方法：

| 级别 | 方法 | 拿到什么 | 关键实现细节 |
|---|---|---|---|
| 1. 有哪些套 | `GetHostList()` | Apollo 套列表，`list[].id` = apolloHostId | code 是**字符串** `"success"`（接口2/3 是数字 200，两者不一致）；`paginator=false` 拿全量 |
| 2. 套里有哪些应用 | `GetApps(hostId)` | appId 清单 | **data 有两种结构**（直接数组 / `{total,items}`），先试数组解析失败再试 items |
| 3. 应用的配置项 | `GetNamespace(...)` | key/value 列表 | 一次只能查 1 个 namespace；**404（HTTP 状态或包装 code）不算错**返回空——大量应用没有 datasource/redis 这类 namespace，属正常，且不打印 ERROR、不记“未完成应用”；404 还驱动 ns 学习**自愈**（从命中集移除该 ns）与「中间件缺失」应用级提示（见 §11.2 任务组装 / §14） |

每个请求带 `Cookie: sessionId=xxx` 鉴权；自签证书场景 `insecure_verify: true` 跳过 TLS 校验。

**发现阶段优化（对齐参考实现 mcp_server.py）：**

```
1. GetHostList() 查套列表
2. ProbeHosts(hosts, 30s) 并发探活所有套（8 worker + TTL 60s 缓存）
   → 标记每套 available/不可用，命中缓存直接复用（并发探活避免串行等待）
3. GetAppsConcurrent(hosts, probe) 并发抓取可用套的应用列表
   → 不可用套 fast-fail 跳过；复用探活时的 apps 缓存，避免 probe+fetch 重复请求
```

**探活超时语义（30s 硬预算）：** `probeCtx` 用 `context.WithTimeout` 包住**整个并发段**（任务发送 goroutine + worker 消费），而不是只包 worker 循环——

```
发送任务时 select { <-ctx.Done() return | ch <- host }   // 超时立即收手，不再往无消费者的通道阻塞发送
超时或取消时 defer close(ch) 仍然执行                  // 保证 worker range 一定能退出，不泄漏 goroutine
wg.Wait() 后 probeCtx.Err()!=nil → 记 timeout 警告      // 超时未完成(CheckedAt 为零值)的套 → 标记不可用
```

这样超时是**真的生效**的：旧实现只对 worker 消费段做 select 超时，任务发送仍可能阻塞在已满的 channel 上；且发送 goroutine 提前 return 时若不 `close(ch)`，worker 会卡死在 `range` 上。同时 `defer cancel()` 保证超时后及时释放上下文资源。

| 优化点 | 参考实现 | 本代码实现 |
|---|---|---|
| 并发探活 | `_probe_hosts_concurrent` | `ProbeHosts`（8 worker + probeCache 60s TTL） |
| 探活超时硬预算 | `futures_wait` pending 判定 | 30s `probeCtx` 覆盖发送+消费全段，超时套标记不可用 |
| 可用套优先/跳过不可用 | `_probe_host_available` | `ProbeHosts` 标记 available，`GetAppsConcurrent` 跳过 |
| 应用列表缓存复用 | `_cached_fetch_apps` | `appsCache`（探活时缓存，供抓取复用） |
| 并发抓取应用列表 | `fetch_proxy_apps_first_available` | `GetAppsConcurrent` |

> 收益：多套场景下，探活和应用抓取均并发，N 套耗时≈单套耗时；不可用套不会造成 N×6s 串行等待，探活预算超时也不会把任务拖死（超时套直接按不可用跳过，不影响其余套）。

**扫描任务组装（`scanTask`）**—— 每套每应用扫哪些 namespace 由 **ns 学习定向**（§14）决定，而非每次固定全名单：

```
学习键 = hostId|env|appId（套 × 环境 × 应用 三元组；同一应用跨套/跨环境各自学习）
planNs 按学习状态选名单：
  无学习记录                 → 固定全名单首扫 bootstrap（本轮建立基线，刷新 lastGuessAt）
  超过 ns_guess_days 未全量    → 固定全名单兜底重猜 recheck（防新增/改名 namespace 漂移）
  其余                       → 只扫“历史命中集 + application” targeted（请求量收敛到真实存在的 ns）
任务数 = 可用套 × 环境 × 应用 × nsList 长度（名单统一受 max_ns_per_app 截断）
例：首扫 2 套(均可用) × 1 环境 × 359 应用 × 3 ns ≈ 1077 个任务；收敛后每个应用只扫命中过的 ns（如仅 application），请求量随之下降
```

### 11.3 第②步：解析（从配置项挖出中间件关系）

**双路径融合解析**：优先按 **key 特征**命中（`matchRule`）；key 不标准时回退按 **value 内容**兜底识别（`matchValueRule`，如 value 直接含 `jdbc:mysql://`、`redis://`、`amqp://` 等），尽力覆盖全量配置，单次扫描完成 key+value 双匹配、不发重复请求。**别名与大小写**：key 匹配对大小写不敏感，规则表内置常见别名/简写（如 kafka 的 `bootstrap.servers`(点) 与 `bootstrap-servers`(横线)、redisson、`spring.data.mongo`(不带 b)、memcache、`zk.`、rabbit/裸 amqp），避免真实配置写法差异导致漏匹配；value 兜底协议变体亦收全（`rediss://`、`amqps://`、`mongodb+srv://`、`memcache://` 等）。完整关键词清单以代码 [middlewareRules](../service/operation_topology.go#L44-L85) 为准。

规则表：

| key/value 特征 | 类型 |
|---|---|
| `spring.datasource` / `jdbc:mysql` | mysql |
| `spring.redis` / `spring.data.redis` / `redis://` / `:6379` | redis |
| `bootstrap-servers` | kafka |
| `rocketmq.name-server` / `rocketmq` | rocketmq |
| `elasticsearch` / `es.cluster` | elasticsearch |
| `spring.data.mongodb` / `mongodb://` | mongodb |
| `memcached` | memcached |
| `zookeeper.address` | zookeeper |
| `nacos.server-addr` | nacos |
| `spring.rabbitmq` / `rabbitmq` / `amqp://` | rabbitmq |

#### 11.3.1 单条配置项 → 关系行（完整流水）

解析以 **namespace 维度**进行（[parseItemsToRelations](../service/operation_topology.go#L287-L361)），而非逐条孤立判断，共 4 步：

```
第1步 建索引 + 前置过滤
   kv 索引：同 namespace 全部 items 建成 key→value 映射，空 key 占位项（真实 Apollo 常见空行）直接跳过
   敏感项排除：isSensitiveKey(key) —— key 含 password/passwd/secret/credential/username/.user/
   access-key/private-key/token 等特征 → 跳过，密码/账号/密钥绝不参与匹配、绝不落库

第2步 双路径定类型（key 特征优先，value 协议兜底）
   路径 A：matchRule(key) 按 key 特征匹配 —— middlewareRules（约 30 条，按类型分组）**按顺序、
           第一个命中即停**；匹配对 key **大小写不敏感**（关键词预编译小写 middlewareKeywords），
           规则内置别名/简写（bootstrap.servers 点/横、redisson、spring.data.mongo、memcache、
           zk.、rabbit/裸 amqp 等）；顺序敏感，宽泛词必须放在同组精确词之后（见 §12 注意事项 2）
   路径 B（A 未命中才走）：matchValueRule(value) 按 value 内容兜底 —— 用独立精简的 valueRules，
           只认明确的连接协议（jdbc:mysql、mysql://、redis://、rediss://、mongodb://、
           mongodb+srv://、amqp://、amqps://、memcached://、memcache://、zookeeper://），
           不复用 key 型宽泛词，避免 value 恰好含业务词误判类型；对 value 大小写不敏感
           （value 统一小写 + valueKeywords 小写预编译，热路径不再重复 ToLower）
   两路径都未命中（如 server.port=9000）→ 直接丢弃

第3步 地址提取（只留 host:port）
   a. value 内联 host:port：extractAddrs(value, type) 用正则 ([a-zA-Z0-9.\-_]+):(\d{2,5}) 提取；
      mysql/redis/es/mongodb/rabbitmq/memcached 只取第一个；kafka/rocketmq/zookeeper/nacos
      （multiAddrTypes）取全部地址（去重）
   b. 取不到内联地址时走 host/port 分离：combineHostPort —— key 以主机型后缀结尾
      （.cluster-nodes/.server-addr/.servers/.address/.server/.nodes/.host/.addr，按长度降序匹配）
      且 value 是纯主机名 → 回查同 namespace 的「前缀.port」配置项显式端口；
      仍缺端口 → 用中间件默认端口兜底 defaultPorts（mysql 3306 / redis 6379 / kafka 9092 / ...）
   c. 组合后仍无地址 → 跳过（说明不是连接配置）

第4步 成行 + 溯源 + 去重
   库名增强：extractDbName(value) 取 :// 后第一段路径作为 middleware_db（不参与去重/合并）
   溯源字段：Namespace/ConfigKey 随行落库，供 /list 回查“这条关系从哪个配置项解析来”
   ns 内去重：同 namespace 内按 类型|地址 去重（同一 key 多地址只留唯一行）
   全局去重：整批结束后再按 relationKey()（appId|hostName(缺省#hostId)|env|类型|地址）全局去重，
             与快照 diff、数据库版唯一索引共用同一键
```

**地址提取示例**（正则 `([a-zA-Z0-9.\-_]+):(\d{2,5})`）：

```
jdbc:mysql://db-master:3306/mydb?password=xxx  →  db-master:3306   （密码、库名丢弃）
redis://:pwd@cache:6379/0                      →  cache:6379
broker-1:9092,broker-2:9092                    →  kafka 取全部地址；mysql 只取第一个
```

**安全边界**：只保留 host:port，**丢弃用户名/密码/完整 uri**。配置中的敏感信息不写入快照文件（见《[运维关系拓扑图方案.md](运维关系拓扑图方案.md)》§1 决策 3）。

命中明细可观测：每条命中打 Debug 日志 `规则命中`（appId/ns/key/hitVia=key|value|key+port/type/addrs），每个 ns 解析完打 Info `解析摘要`（items→rels 出入参），小批量关系再打 Debug `关系明细`，供回溯「某条关系由什么配置识别出来」。

#### 11.3.2 并发消费的健壮性设计（防死锁/防泄漏）

```
1. 任务发送 goroutine 用 defer close(taskCh) —— ctx 提前取消时通道仍被关闭，
   worker 的 for range taskCh 一定能退出，不会永久挂起等待任务
2. 失败应用记录用 mutex + unfinishedSet(map) 代替有界 channel —— 失败量大时
   不会因写满 channel 阻塞 worker（旧实现顺序消费场景存在死锁风险）
3. 同步结束再统一锁读 unfinishedSet 转排序 slice，写入 response
```

### 11.6 第⑤步：落盘（分档原子替换）

`DatastoreRouter.ReplaceSnapshot` 在结束时刻一次性落盘，**旧版数据在落盘前保持可查**：

```
① 整批成功 → fileStore.Replace(rows, keep)：整体编码 JSON → tmp 文件 → rename 原子替换
   （已注入 DB 连接时走 `ReplaceSnapshot` 落库 `operation_topology`、并回写本地文件镜像）
   keep = snapshotKeep()：取配置 topology_snapshot_keep（默认 3，<=0 视为默认 3）；
   替换当日桶后按 sync_date 倒序保留最近 keep 份、更早的整桶清理（DB 表与本地文件同口径），
   既留得住「上一版」做前后对比，又不会随每日同步无限堆积
② 预算截断（ctx 超时/存在未执行任务）且已有可用旧快照（更早日期桶或当日已有行）→ 不落盘、保留旧快照，
   提示“已保留现有快照 {date} N 条，本次未覆盖”；仅从未有过任何可用快照时才先落部分数据（首次兜底）
③ 任务全部执行但个别应用失败 → 仍整批落盘：mergeUnfinishedRows 把失败应用的上版快照行并入本次
   （行键 relationKey 不重复、sync_date 改写为当前批；日志“失败应用继承旧快照行”），
   防“个别失败→整批不落盘→快照长期停在旧版”的数据断层（线上曾因 4 个应用持续失败致 1418 行无法落盘）
④ 空产物 → 不覆盖文件，保留当日已有快照（日志 Warn kept=N）
```

> 分档策略的动机：旧版「partial 一律保护」会让「个别应用失败」也整批不落盘，快照长期停在旧版（线上曾致图数据停在首扫 462 条半成品）；分档后只有**预算截断**才保护，个别失败通过「继承旧行」继续落盘。
>
> 裁剪策略见配置项 `topology_snapshot_keep`（《[拓扑查询总体逻辑.md](拓扑查询总体逻辑.md)》§8.3）；只有桶数 **≥** keep 时才裁剪（不足则全留，不做误删）。

## 12. 注意事项（按重要程度排序）

### ⚠️ 高风险

**1. sessionId 有效期（最可能出问题的地方）**

Cookie sessionId 会过期，过期后接口1 返回 `{"code":"fail","message":"未记录的访问"}`。当前**没有自动续期机制**——需要定期更新配置里的 `session_id`，否则每天凌晨的定时任务会静默失败（只有日志有记录）。建议后续加「同步失败告警」。

**2. 规则匹配顺序敏感**

`matchRule` 顺序匹配第一个命中。如果把宽泛的 `{Keyword: "redis"}` 放在 `{Keyword: "spring.redis"}` 前面，key 含 `redisson` 也会命中。**新增规则要加在精确规则之后**（宽泛兜底词放同组最末）；关键词**一律小写**（匹配已对 key/value 大小写不敏感，统一在 [middlewareKeywords / valueKeywords](../service/operation_topology.go#L216-L239) 预编译小写，无需写大写变体）。改完规则请跑 `TestMatchRuleAliasesAndCase` / `TestMatchValueRuleProtocolVariants` / `TestMatchRuleOrderingAndNoFalseHit` 回归。

**3. 误匹配风险**

关键字是 `strings.Contains` 包含匹配，value 里恰好含 `redis://` 的非 Redis 配置会被误收。当前靠「host:port 正则 + 类型合理」兜底，**上线后要抽查解析结果**（`/list` 的 `configKey` 列可溯源）。

### ⚡ 中风险

**4. 404 与其他错误码的区别处理**

接口3 的 404（HTTP 状态或包装 code=404，即 namespace 不存在/未授权）返回空是合理的：**不打印 ERROR「请求失败」/WARN「扫描失败」，也不计入 `unfinishedApps`**，避免 85% 无效日志噪音与误报“未完成应用”；但 503（EasyOps 连不上 Apollo）、504（Apollo 超时）等真实错误仍记入 `unfinishedApps`。看同步结果时区分：`partial=true` 且 unfinishedApps 很多 = Apollo 侧故障，不是数据丢了。

404 在 ns 学习（§14）下还有两个额外作用：① 把该 ns 从学习命中集**移除**（自愈“上次命中、现已删除/改名”的漂移）；② 若 404 的是**中间件型 namespace**（`middlewareNsHints` 名单），批末按应用**逐条 Warn**「本次同步 · 中间件缺失（namespace 不存在=未接入对应中间件）」`appId/name/missingNs`，供区分“没扫到中间件是正常（未接入）还是漏扫（自定义命名空间）”。

**5. 全量扫描的请求量**

namespace 扫描任务数 = 可用套×环境×应用×namespace，10 套(均可用) × 500 应用 × 15 ns ≈ 75000 请求。有同步总预算保护（超时部分完成）。注意：**探活/应用抓取也已并发化**（多套不串行等待），但 namespace 扫描的请求总量随 namespace 数量与应用规模线性增长；全量覆盖策略（双路径融合）下 namespace 数较初版更多、请求量更大，套/应用规模上来后需评估 `scan_budget_sec` / `request_timeout` 是否够用，必要时调大预算或收窄 `scan_namespaces`。启用 ns 学习定向（§14）后，平时只扫「历史命中集 + application」，请求量收敛到**真实存在的 namespace**；全名单猜测仅发生在首扫 bootstrap 与 `ns_guess_days` 到期的 recheck 兜底。

**6. 不可用套的容忍**

并发探活会标记不可用套并从应用抓取中**跳过**（快跳，不产生 N×6s 串行等待），落到 `availableHosts` 字段可核对；若大部分套不可用，多为 sessionId 失效或 EasyOps 侧故障，需优先排查。

**7. 时区与「当日」语义**

`syncDate` 用服务器本地时区。凌晨 01:30 跑的快照日期就是当天；若跨天手动补跑（第二天上午触发），会留昨天快照 + 生成今天新快照——历史 diff 是和「最近一次更早的快照」比的，语义正确但需留意。

**8. 快照文件的保留份数**

每次同步覆盖当日桶，并按 `topology_snapshot_keep`（默认 3）**只保留最近 N 个 `sync_date` 桶**（DB 表与本地文件同口径），更早的整桶清理，不会随每日同步无限增长。保留 3 份即可拿到「上一版」做前后对比（`PreviousSnapshot`）；调大该值可留更长的历史窗口，但行数/文件体积随之线性增长。

**9. 跳① 关系同步异常（看 `relationErr`）**

关系表 `app_dp_relation` 未建、上游关系接口失败或写库事务回滚时，`/sync` 结果与日志总览会以 `【异常】` 标注（`relationErr=true`），但**不阻断主表同步**——主表照常落库，查询期跳① 依次降级到本地镜像、关系接口兜底，最终置空（`ok=false`，读接口按原行返回）。**异常需运维介入**（表缺失先执行 `docs/业务数据/app_dp_relation.sql`）；「接口未启用 / 拉取 0 行 / 无 DB 连接」是**正常降级**，不报错且保留上一版关系数据。判定细则见 §5.2，排查入口见 [`logs/README.md`](../logs/README.md)。

### 💡 设计上已处理的（了解即可）

| 风险点 | 已有保护 |
|---|---|
| 密码泄漏 | 只提取 host:port，用户名/密码不写文件不进日志 |
| 接口超时拖死任务 | 每接口独立超时 + 总预算 context 截断，partial 返回 |
| 重复执行产生脏数据 | 当日桶整桶原子替换（tmp+rename），幂等 |
| 同一关系多来源重复 | 内存去重（relationKey 含实例）；数据库版另有复合唯一索引 `uk_snapshot_relation`（6 列含 `apollo_host_id`）兜底 |
| Apollo 某套挂了 | 该套跳过记日志，不影响其他套；unfinishedApps 留痕 |
| 关系变化无感知 | 每次同步和上次快照 diff，newRelations/lostRelations 记录 |

## 13. 解析·匹配·落盘优化记录（2026-09-02）

针对「采集后的解析 → 匹配 → 落盘」环节的低风险重构与数据层加固：

| 项 | 变更 | 收益 |
|---|---|---|
| ownerFor 预计算 | 组装任务阶段按 appId 只算一次，`scanTask` 携带 owner | 消除 worker 内 (app×ns×env) 次重复映射 |
| 去重键统一 | collector 内联拼接改为统一调用 `relationKey()` | 去重与快照 diff 键不再两处漂移 |
| keyword 小写预编译 | 新增包级 `valueKeywords`（启动时一次 ToLower） | `matchValueRule` 热路径不再重复 ToLower |
| 容量预分配 | `rels`（cap≤8）、`diffRelations` 两个 map（按行数） | 减少 append/map 扩容 |
| 请求耗时汇总 | worker 本地累计 ms，结束后输出 `avgMs/maxMs` 日志 | 定位 Apollo 侧慢请求，无需逐条翻 warn |
| 空结果保留提示 | 本次同步 0 条但当日已有快照时 Warn（`kept=N`） | 避免 `InsertCount=0` 与文件当日实际行数不一致误导前端 |
| 实例纳入唯一键 | `relationKey` 改为实例感知：`appId\|hostName(缺省#hostId)\|env\|类型\|地址`，与数据库版表唯一索引列序对齐 | 去重/diff 与 DB 版唯一键三者统一，同应用跨多实例的相同关系不再互相挤掉 |
| 复合唯一索引（数据库版） | `uk_snapshot_relation(sync_date, apollo_app_id, apollo_host_id, env, middleware_type, connect_addr)`（旧 5 列 → 含实例 6 列），model 已加 `uniqueIndex` tag | **数据库版**的幂等兜底：启用 DB 时由 AutoMigrate 建表 + `EnsureOperationTopologyIndex` 幂等重建；**文件模式无需建索引**，文件去重即依赖 relationKey |

> 说明（数据库版）：旧版 5 列唯一索引（无 `apollo_host_id`）存在时，`EnsureOperationTopologyIndex` 会在启动 AutoMigrate 后幂等重建为 6 列新版（先查 `information_schema.statistics` 比对列集，缺列则 DROP 后按新列序重建），新库/新表直接按新结构创建。唯一索引列序以 `sync_date` 领先（利于快照日期范围查）。MySQL 8.0 下 6 列索引总长 < 3072 字节，可全列建索引；文件模式不涉及。

## 14. ns 学习定向 + 404 自愈（同步优化 D+A 组合 · 2026-09-09 落地）

> 目标：消除「固定 namespace 名单逐个猜测」产生的无效 404 请求（真实环境 85%+ 的 namespace 请求是 404 空结果）——**不改上游网关接口**，纯本地状态学习即可收敛。方案对比/选型过程见《[部署与上线文档.md](部署与上线文档.md)》§13–§18（选型：D 自学习 + A 收窄名单调参，无网关依赖）。

### 14.1 配置（[config/apollo.go](../../../config/apollo.go)）

| 字段 | 默认 | 说明 |
|---|---|---|
| `apollo.ns_learn_enable` | `true`（缺省 nil 视为 true） | 学习定向总开关；显式 `false` = 退回固定名单猜测（日志 `固定名单猜测（ns 学习未启用）`） |
| `apollo.ns_guess_days` | `0` | 学习后**全名单兜底重猜**间隔天数；`<=0` 仅“从未全量跑过”的三元组首扫一次，不做周期重猜 |

### 14.2 学习状态落盘

独立于关系快照（同 `data/` 目录、tmp+rename 原子写；文件缺失/损坏按空集继续，只 Warn 不阻断同步）：

- 文件：`api/tprel/data/operation_topology_learned.json`，结构 `{version:1, updatedAt, apps:{学习键:{namespaces,lastGuessAt}}}`
- 学习键：`hostId|env|appId`（套×环境×应用 三元组；同一应用跨套/跨环境各自学习）
- `namespaces`：历史「查询成功（200，含空空间）」的 namespace 集合（排序去重）；`lastGuessAt`：最近一次全名单猜测日期（YYYY-MM-DD，空 = 从未全量跑过）
- 实现：[service/ns_learn_store.go](../service/ns_learn_store.go)

### 14.3 决策流程（每三元组 `planNs`）

| 学习状态 | 模式 | 本轮扫描名单 | 说明 |
|---|---|---|---|
| 无记录 | `bootstrap` 首扫 | 固定全名单（`scan_namespaces`，受 `max_ns_per_app` 截断） | 建立基线；条目保留（含空壳）并刷新 `lastGuessAt`，供周期计时 |
| `lastGuessAt` 距 today ≥ `ns_guess_days` | `recheck` 兜底重猜 | 固定全名单 | 防“新增/改名 namespace”的漂移（自愈） |
| 其余（有命中记录且未超期） | `targeted` 定向 | 命中集 + `application`（`ensureApplication` 保底，防主配置漏扫） | 请求量收敛到真实存在的 ns |

worker 侧登记（并发写，批末统一合并）：`GetNamespace` 返回 **200（含空空间）→ 并入命中集**；**404 → 记入待移除集**。批末 `merge(hitNs, rmNs, guessedKeys, syncDate)` + `flush()`：**命中集 ∪ 旧集 − 本批 404**；跑过全名单的三元组刷新 `lastGuessAt`；“从未全量跑过且命中集为空”的垃圾条目删除。回写失败仅 Warn，不影响本次同步结果。

### 14.4 可观测性

- `/sync/status` 的 `result` 与日志「结果总览」新增三元组计数：`nsTargeted` / `nsBootstrap` / `nsRecheck`（见 [model/operation_topology.go](../model/operation_topology.go)）
- 「执行计划总览 / 扫描任务组装完成」日志含 `ns扫描策略`：`学习定向 targeted=N / 首扫 bootstrap=N / 兜底重猜 recheck=N`

### 14.5 中间件缺失提示（按应用逐条 Warn）

`middlewareNsHints`（中间件型 namespace 名单，如 `datasource/redis/kafka/…`）命中的 ns 返回 **404 = 该应用未接入对应中间件（或使用了自定义命名空间）**。批末按应用**逐条 Warn**：「本次同步 · 中间件缺失（namespace 不存在=未接入对应中间件）」`appId/name/missingNs`——供排查“没扫到中间件是正常还是漏扫”。非中间件型空间缺失**不提示**，也不产生 ERROR / 不计“未完成应用”。

### 15.6 接口 4：获取 appId ↔ 部署项目关系列表（跳①）


| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `paginator` | bool | 否 | `false` | 固定传 `false`：**上游不分页、直接返回全表** |
| `pageIndex` | int | 否 | `1` | 页码（`paginator=false` 时不生效） |
| `pageSize` | int | 否 | `-1` | **`-1` = 一次取全量**（`pageSize<=0` 均由客户端统一发 `-1`） |

> 上游契约（2026-09-17 生产抓包核实）：`paginator=false` 时服务端不分页、直接返回全表，
> 返回体里的 `pageTotal` 是**总记录数**（实测 1426）而**不是总页数**。
> 故客户端固定传 `paginator=false` + `pageSize=-1`，一次请求即取回全量；
> `pageIndex` / `pageSize` 仅在上游真做分页（`paginator` 生效）时才影响结果。
> 客户端短路逻辑（[service/dp_relation.go](../service/dp_relation.go) `fetchRelationDTOs`）：
> 首次返回行数 ≥ `pageTotal` 即认为已取全、不再发第二次请求；仅当返回行数 < `pageTotal` 时按
> `pageSize` 换算页数补齐，并以 `relation_api_max_pages`（默认 200）兜底防死循环。

```bash
# 全量口径（pageSize=-1，本项目实际使用；一次请求返回 1426 行全表）
```

- 采集期：`SyncAppDpRelation()` 全量拉取 → 过滤 `del_flag` 与空 `apolloAppId`/`deployProjectName` → **与库内现有行做多重集比对（只比业务列，时间列不参与）**：有变化才清空替换落库 `app_dp_relation` 并回写本地镜像、无变化跳过 → 失效内存索引（与拓扑主表同节奏：cron 每日 01:30 / 手动 `/sync`）。
- 查询期：只读「库 → 本地镜像」，接口仅在前两者均无数据时兜底，故查询链路不依赖上游可用性。
- 配置项：`relation_api_enable` / `relation_api_path`（真实值 `/thirdApi/apolloApp/list`）/ `relation_api_page_size`（`-1`）/ `relation_api_ttl` / `relation_api_max_pages`，见《[拓扑查询总体逻辑.md](拓扑查询总体逻辑.md)》§8.2。
- 本地联调：Mock 服务同路径占位实现（`api/tprel/mock/mock_server.py`，端口 18080），契约与本接口一致。

### 15.7 Token 加密解密

接口 1 返回的 `token` 字段是 **EasyOps 加密后**的值，加密密钥就是请求时带的 `sessionId`。

**算法**：原始 token 的每个字符与 sessionId **循环 XOR**，结果再做 **Base64 编码**。

```
encrypted_bytes[i] = token[i] XOR sessionId[i mod len(sessionId)]
encrypted_token   = Base64Encode(encrypted_bytes)
```

**解密**（本模块同算法）：Base64 解码后与 sessionId 循环 XOR 还原。

```python
import base64

def decrypt_token(encrypted_token, session_id):
    decoded = base64.b64decode(encrypted_token)
    return ''.join(
        chr(decoded[i] ^ ord(session_id[i % len(session_id)]))
        for i in range(len(decoded))
    )
```

**使用位置**：在组装 Apollo OpenAPI 客户端时自动调用，**原始 Token 不落库、不落日志、不对外透出**。

### 15.8 超时与容错基线

上游参考实现（`apollo-mcp-server`）的默认值，本模块实现取同量级（`config.apollo` 可调）：

| 配置项 | 默认值 | 作用范围 |
|---|---|---|
| host_list 超时 | 8s | 接口 1 单次请求 |
| host_list 重试 | 1 次（接口 2、3 固定 0 次） | 接口 1 |
| apps 超时 | 6s | 接口 2 |
| namespace 超时 | 6s | 接口 3 |
| 遍历可用套总预算 | 20s | apps/namespace 的 fallback 遍历 |
| 全量扫描总预算 | 60s（全名单猜测时放大至 5m） | 覆盖三接口 |
| 扫描并发 | 8 | 接口 3 并发数 |
| 每应用扫描 ns 数 | 5（本地默认 3） | 接口 3（`max_ns_per_app`） |
| host 探活开关 | 开启 | 标记可用/不可用后跳过无效套 |
| 探活结果缓存 TTL | 60s | 探活缓存 |

**容错**：指定套异常（5xx / 超时）自动切换到第一个探活可用的套；全部套不可用则逐层上抛、同步任务标记 `partial`；总预算耗尽时返回 `partial=true` + `unfinishedApps`，不卡死。

### 15.10 注意事项

1. **apolloHostId ≠ appId**：`apolloHostId` 是 EasyOps 内部 Apollo 服务 ID（接口 1 的 `list[i].id`），`appId` 是 Apollo 应用 ID
2. **Token 解密是内部行为**：本模块只落 `host:port`，不落/不暴露 Apollo OpenAPI Token
3. **敏感配置不落库**：密码、账号、密钥类 key 在解析前置过滤阶段即跳过（见 §11.3.1 第 1 步）
4. **只读**：四个接口均为 GET 只读，不支持增删改
5. **DNS 兜底**：接口 1 若因 EasyOps DNS 解析异常而超时，探活会把所有套标记为不可用 → 快速返回 partial（不会卡死）
