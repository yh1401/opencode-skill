## 2. 第一阶段：数据拉取（采集层）

采集期的目标是「把 Apollo 配置里的中间件连接关系解析成行」。采集本身**不涉及跳①/跳② 关联**，关联只发生在查询期。

### 2.1 数据源清单

| 数据源                                   | 用途                                  | 形态         | 代码                               |
| ------------------------------------- | ----------------------------------- | ---------- | -------------------------------- |
| 接口1 `GET /thirdApi/getApolloHostInfo` | 查 Apollo 套（实例）列表                    | 实时 HTTP    | `ApolloClient.GetHostList`       |
| 接口2 `GET /thirdApi/apollo/apps`       | 查某套下的应用列表（含部门/负责人元数据）               | 实时 HTTP    | `ApolloClient.GetApps`           |
| 接口3 `GET /thirdApi/apollo/namespace`  | 查某应用某 namespace 的配置项 kv             | 实时 HTTP    | `ApolloClient.GetNamespace`      |
| **关系接口**（跳①）                          | appId ↔ 部署项目 全量关系（2026-09-17 实测 `pageTotal=1426`） | 实时 HTTP，分页 | `ApolloClient.GetAppDpRelations` |
| DPR 表（跳②）                             | 部署项目 → PP 应用/node/工程 归属             | DB 或本地镜像   | `service/pinpoint_relation.go`   |

鉴权：所有 HTTP 走 `doGet`，带 `Cookie: sessionId=...`；接口1 返回的加密 token 用「Base64 解码后与 sessionId 逐字节 XOR」解密（`decryptToken`，仅鉴权用、不落库）。

### 2.2 主采集流程（`syncOperationTopology`）

```
1. 接口1 GetHostList()                    → 套列表
2. FilterHostsByName()（可选）            → 按 APOLLO_HOST_NAME 模糊筛选待同步套
3. ProbeHosts() 并发探活（8 worker，TTL 60s）
                                          → 标记可用/不可用，不可用套快跳（fast-fail）
4. GetAppsConcurrent()                    → 可用套并发拉应用列表（复用探活缓存，避免重复请求）
5. ExcludeAppIds 过滤                     → 剔除占位/无效测试应用
6. 组装扫描任务 scanTask{host, env, app, ns}
   · envs        默认 ["PRO"]
   · namespaces  默认 15 个常见特征 namespace（application/datasource/redis/...）
   · ns 学习定向：无记录→全名单首扫 bootstrap；命中集→定向 targeted；超期→兜底重猜 recheck
7. worker 并发执行任务：接口3 GetNamespace(hostId, env, appId, cluster, ns) → items
8. 解析：parseItemsToRelations(app, host, env, ns, syncDate, items, owner)
9. 汇总去重（relationKey）→ 事务落库 / 写本地快照
```

要点：

- **探活 + 应用列表缓存**：接口2 的结果在探活时缓存（`appsCache`），抓取时直接复用，一轮同步内不重复请求。
- **404 是预期态**：namespace 不存在（真实环境约 85% 请求为 404）不打印 ERROR、不重试、不计入「未完成应用」。
- **owner 预计算**：`owners[appId]` 按 appId 只映射一次，避免每个 `(app × ns × env)` 任务重复映射。
- **实例元数据冗余**：`instanceMeta{hostId, hostName, hostAddr, secondProductId, appCount}` 随每条关系行冗余落库，供页面实例归属展示。

### 2.3 解析规则（`parseItemsToRelations`）

对单次 namespace 的 items 逐项解析：

```
items → kv 索引（跳过空 key 占位项）
  ↓ 逐 key
1. isSensitiveKey(key)?  → 命中即跳过（password/secret/token/user…… 绝不落库）
2. matchRule(key)                        ← 按 key 特征匹配（大小写不敏感，顺序命中即停）
   └ 未命中 → matchValueRule(value)      ← value 内容兜底识别（双路径融合）
3. extractAddrs(value, type)             ← value 内联 host:port 提取（如 "a:6379,b:6379"）
   └ 无地址 → combineHostPort(kv, key, value, type)
                                          ← host/port 分离写法：补齐同 ns 的 前缀.port / 默认端口
4. 无地址 → 跳过（地址可提取是成行闸门，纯参数 key 不产生伪关系）
5. 按 类型|地址 在 namespace 内去重 → 生成关系行
```

关联解析规则的关键常量：

- `middlewareRules`：覆盖 10 种中间件（mysql/redis/kafka/rocketmq/elasticsearch/mongodb/memcached/zookeeper/nacos/rabbitmq），同类型内按「精确 → 别名/简写 → 宽泛兜底」排序，顺序命中即停。规则覆盖 10 类，但 2026-09-17 真实数据实际只命中 **7 类**（elasticsearch / kafka / mysql / nacos / redis / rocketmq / zookeeper，见 `/middlewareTypes`）。
- `defaultPorts`：host/port 分离且缺省端口时的兜底端口（redis=6379、mysql=3306……）。
- `hostKeySuffixes`：主机型配置 key 后缀（`.cluster-nodes` / `.server-addr` / `.host` …），按长度降序避免抢先匹配。
- `multiAddrTypes`：值为多地址列表的类型（kafka/rocketmq/zookeeper/nacos）。

**生成的关系行（`OperationTopology`）字段来源**

| 分组    | 字段                                                                              | 来源                                                       |
| ----- | ------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 实例层   | `ApolloHostId/ApolloHostName/ApolloHostAddr/SecondProductId/HostAppCount`       | 接口1 + 探活                                                 |
| 应用层   | `ApolloAppId/ApolloAppName/AppDept/AppOwner`                                    | 接口2                                                      |
| 应用层   | `PpApplication`                                                                 | 采集期占位（`ownerFor`：`appid_owner_map` 可选覆盖，缺省回退应用名）；查询期按跳② 命中覆盖 |
| 应用层   | `Node/EngProject/DepProject`                                                    | **采集期恒为空（预留）**，由查询期 `attachAppAttrs` 作为 appId 属性补充（单值列取首值 + 多值列表字段） |
| 中间件层  | `Namespace/ConfigKey/MiddlewareType/ConnectAddr/MiddlewareDb/MiddlewareProject` | 接口3 + 解析规则                                               |
| 快照/通用 | `Env/SyncDate/Source/Remark/CreateTime/UpdateTime`                              | 运行上下文                                                    |

### 2.4 跳① 关系同步（采集期落库，查询期只读库）

关系接口在**采集期**由 `syncOperationTopology` 触发（与拓扑主表同一节奏：cron 每日 01:30 或手动 `/sync`），
分页循环拉取全量并**与库内数据比对**：有变化才**整表替换落库** `app_dp_relation`（无变化跳过，表内不产生无谓膨胀），
同时回写本地镜像；查询期由 `dpTargets()` 只读
「库 → 镜像」，不再实时打接口（接口仅在库/镜像均无数据时兜底）。详见 §4.2。

```
GetAppDpRelations(path, pageIndex, pageSize)
  · 固定 paginator=false + pageSize=-1（一次取全量）；上游 total 即**总记录数**（非总页数）
  · 首页返回后：total <= 已返回行数 → 判定已取全，直接返回（不发第二次请求）
  · 仅当上游确实分页（返回行数 < total）时，才按 pageSize 换算 pageCount 逐页补齐
  · 换算出的 pageCount > relation_api_max_pages → 截断并 Warn（防 total 异常导致死循环）
  · 任一分页失败 → 整体降级（不做部分采用，保留上一版关系数据）
  · 0 行同样不覆盖（防上游异常清空关系表）
  · 行 → del_flag=true 过滤 → 与库内现有行做**多重集比对**（只比业务列，create_time/update_time 不参与）
      · 一致 → 跳过替换（不删不写，表内行数不变）
      · 不一致 → 清空 + 分批重写 app_dp_relation + 镜像 data/app_dp_relation.json
  · 降维 → relationRow{apolloAppId, apolloAppEnv, deployProjectName, node} 供查询期索引
```

**成败判定与上报口径**（`RelationSyncStat` → `SyncResult.relationRows / relationWrote / relationErr / relationMsg`）：

| 情形 | `relationErr` | `relationMsg` | 日志总览「关系同步」文案 | 语义 |
|---|---|---|---|---|
| 有变化 → 落库 | false | `整表替换落库 N 行` | `整表替换落库 N 行（app_dp_relation）` | ✅ 正常 |
| **无变化 → 跳过** | false | `关系数据无变化，跳过替换落库（表内 N 行）` | 同 msg | ✅ 正常（不做无谓清空重写） |
| 接口未启用（`relation_api_enable=false` / `path` 空） | false | 保留现有关系数据 | 同 msg | ✅ 正常降级（不报错） |
| 拉取返回 0 行 | false | 保留现有关系数据 | 同 msg | ✅ 正常降级（不报错） |
| 无 DB 连接 | false | 仅写本地镜像 | `未落库（无 DB 连接），仅写本地镜像` | ✅ 正常降级（走镜像） |
| 上游拉取失败 | **true** | 保留现有关系数据 + 错误详情 | `【异常】…` | ❌ 异常，需运维介入 |
| 关系表 `app_dp_relation` 缺失 | **true** | 关系表不存在，未落库（启动时 AutoMigrate 未建表，请检查 DB 连接与权限） | `【异常】…` | ❌ 异常，需运维介入 |
| 写库失败（事务回滚） | **true** | 错误详情 + 本次仅写本地镜像 | `【异常】…` | ❌ 异常，需运维介入 |

> 异常**不阻断主表同步**：`SyncResult.resultText` / `/sync/status` 的 `status` 会追加「（关系同步异常）」标注，主表仍正常落库。

接口返回结构（**上游接口**，`code` 为字符串 `"success"`；顶层键 `code / list / pageTotal`，行结构与 `app_dp_relation` 表一一对应）：

```json
{
  "code": "success",
  "list": [
    {
      "id": 1715,
      "del_flag": false,
      "create_time": "2026-09-10 21:14:45",
      "update_time": "2026-09-10 21:14:45",
```

## 3. 第二阶段：快照落库 / 存储

### 3.1 每日快照表 `operation_topology`

- 唯一键 `uk_snapshot_relation = (sync_date, apollo_app_id, apollo_host_id, env, middleware_type, connect_addr)`
  → **实例（套）是顶层维度**：同一应用跨多套实例出现的相同中间件关系分别保留。
- 由 `EnsureOperationTopologyIndex` 在 AutoMigrate 之后校验/重建：gorm 只创建缺失索引、不改造同名旧索引，故此处显式把旧版（不含 `apollo_host_id`）唯一索引重建为含实例归属的新索引。
- ADR 与主表一致**纳入 AutoMigrate**（`initialize/gorm.go` 的 `MysqlTables` 注册 `OperationTopology{}` + `AppDpRelation{}`），服务启动即自动建表（表已存在时只补缺失列/索引，不重建、不删列），无需事先执行 `docs/业务数据/app_dp_relation.sql`（脚本仅供本地建档/导数据参考）；**DPR 不纳入 AutoMigrate**，由运维按 `docs/业务数据/deploy_pinpoint_relation.sql` 自建/导入，程序绝不反向改 DPR 表结构。

### 3.2 差异对比与容错合并

| 函数                                                     | 作用                                                               |
| ------------------------------------------------------ | ---------------------------------------------------------------- |
| `relationKey(r)`                                       | 关系唯一键（收集去重 + 快照对比，与表唯一索引一致）                                      |
| `diffRelations(prev, cur)`                             | 两次快照差集 → `NewRelations` / `LostRelations`（日志与 `/sync` 结果展示）      |
| `mergeUnfinishedRows(all, prev, unfinished, syncDate)` | 个别应用失败时，把上版快照中被失败应用的行并入本批（同步日期改写为当前批），防止「个别失败 → 整批不落盘 → 快照长期停旧版」 |

### 3.3 本地快照与镜像（三份文件）

| 文件                                   | 内容           | 写入时机                                           | 读取时机             |
| ------------------------------------ | ------------ | ---------------------------------------------- | ---------------- |
| `data/operation_topology.json`       | 拓扑主表快照（按 `sync_date` 保留最近 `topology_snapshot_keep` 份，默认 3） | 同步完成后 `ReplaceSnapshot`（替换当日桶 + 原子写 tmp+rename，更早的桶清理）        | file 模式/DB 不可用时  |
| `data/deploy_pinpoint_relation.json` | DPR 镜像（跳②）   | `loadPinpointFromDB` 成功后 `writePinpointMirror` | DPR DB 不可用时      |
| `data/app_dp_relation.json`          | ADR 镜像（跳①）   | `loadRelationFromDB` 成功后 `writeRelationMirror` | 关系接口与 ADR 表均不可用时 |

文件目录默认 `./api/tprel/data`（`defaultDataDir`），均为 `tmp + rename` 原子写，避免读端读到半截文件。

## 4. 第三阶段：查询期——数据源路由与关联属性补充

### 4.1 数据源路由（`DatastoreRouter.resolve`）

| mode       | 行为                                       |
| ---------- | ---------------------------------------- |
| `file`（默认） | 读本地快照；请求 `source=db` 时本次改用 DB，不可达则静默回退文件 |
| `db`       | 固定读数据库                                   |
| `auto`     | DB 优先，连接类错误自动降级文件，冷却期后自动切回               |

- 未注入 DB 连接（`dbStore==nil`）→ 一律走本地文件。
- 仅**连接类错误**触发降级（`isConnErr`：BadConn / connection refused / database is closed …）。
- 读取包装：`ListRows(f)`（分页）、`QueryAll(f)`（`Page=1,PageSize=-1` 全量，供 graph/detail 聚合）。

### 4.2 两跳 join → `dpTargets()` 内存索引

`dpTargets()` 返回 `map["appId|env"] → []dpTarget`，带 TTL 缓存（默认 60s，配置 `relation_api_ttl`）。
数据由**采集期** `SyncAppDpRelation` 落库（§2.4），查询期只读库/镜像：

```
dpTargets()
  ├─ 命中 TTL 缓存 → 直接返回（不加锁重复加载）
  └─ 过期/未加载 → loadRelationRows()（三级降级）
        1. app_dp_relation 表（loadRelationFromDB，过滤 del_flag=0）→ 顺带回写镜像
        2. 本地镜像 data/app_dp_relation.json（loadRelationFromFile）
        3. 仅当 1、2 均无数据（首次启动且尚未同步过）→ 关系接口兜底 fetchRelationRows
        4. 均无 → 返回 nil，ok=false（读接口按原行返回，记 Warn）
        ↓
     joinDpTargets(rows)
        · 按 (appId, 环境, 部署项目) 去重（同一 appId 可跨多 node 出现多行）
        · 用跳② pinpointMap() 反向建「部署项目 → []dpTarget」正排
        · 逐 (appId,环境) 把部署项目映射为 dpTarget{DepProject, EgProject, Node, PpApplication} 属性项列表
        · DPR 未命中该部署项目 → 仅保留 DepProject，其余三列留空（不阻断跳① 结果）
```

落库与索引失效：`SyncAppDpRelation` 检测到变化、完成整表替换后调用 `invalidateRelationIndex()`，
使查询期下一次访问立即重建索引，避免「库已更新、内存仍旧值」。

**环境口径**：索引键用 `apolloAppEnv`（`PRO`/`LPT` 字符串）与 OT 的 `env` 精确对齐；接口的 `env`(int) 仅作补充。

**跳②** **`pinpointMap()`**：DPR 以 `pp_application` 为键（TTL 60s），值 `PinpointOwner{DepProject, EgProject, Node}`（`node_cn` 已下线，不再加载），DB 优先、文件兜底。

### 4.3 属性补充 `attachAppAttrs`

```
attachAppAttrs(rows):
  for r in rows:
     targets = dpTargets()[ r.apollo_app_id + "|" + r.env ]
     if targets 为空:  原样保留 r        ← 不丢行（无关系/无命中/环境不匹配）
     else:
        deps / engs / nodes / pps ← targets 的非空属性收集
        r.DepProjects,  r.EngProjects       = dedupSorted(deps), dedupSorted(engs)
        r.Nodes,        r.PpApplications    = dedupSorted(nodes), dedupSorted(pps)
        r.DepProject / r.EngProject / r.Node / r.PpApplication = 对应列表首值
                                          ← 单值列取属性列表首值（兼容既有前端字段口径）
                                          ← PpApplications 为空时保留采集期占位值，不清空
        append(out, r)                    ← 行数与行序不变、不复制行
```

**属性补充口径**：拓扑数据集**落库**粒度恒为「appId × 中间件」——`dep_project` / `eng_project` / `node` / `pp_application` 都只是 appId 这个组件的**属性**。查询期由 `expandDepNode` 开关决定两种口径（详见《[运维拓扑.md](运维拓扑.md)》§4.5）：

- **折叠**（显式 `0` / `false`）：属性多值聚合为列表（去重升序）、单值列取列表首值，**行数与行序不变**，实现为 `attachAppAttrs`；
- **展开**（**默认**，不传或 `1` / `true`）：按**部署点**（部署项目 × 节点）扩行，行 / 节点粒度变为 `appId\|部署项目\|节点`，实现为 `expandByDeploySlot`。

旧的「一行按 DPR 行展开为 N 行、四列同源」实现会按 DPR 行把关系数据集扩维（与「按部署点」不同：DPR 一行是 `(dep_project, pp_application)`，不等于一个部署点），已废弃。

## 5. 第四阶段：过滤下推与分页

### 5.1 为什么必须「先取全量候选、属性补充后再过滤分页」

属性补充**不改变行数与行序**（一行「应用→中间件」关系仍是一行），但 `depProject` / `engProject` / `node` / `ppApplication` 的最终判定依赖补充后的属性列表；同时为保证分页稳定，读接口仍须先取全量候选。故：

> **任何读接口都必须先取全量候选（`Page=1, PageSize=-1`）→ 属性补充 → 复核 → 再分页/聚合；`total`** **= 候选关系行数（行数不放大）。**

### 5.2 过滤下推（`relationFilterApps`）

拓扑表 `dep_project` / `eng_project` / `node` / `pp_application` 是**预留空列**，无法直接过滤，故把条件翻译成 `apollo_app_id` 集合下推到数据源：

```
relationFilterApps(q appAttrQuery) → ([]appId, ok)      // q = {DepProject, EngProject, Node, PpApplication}
   · 遍历 dpTargets 索引（键 = appId|env，值 = 属性项列表），先按 appId 把各维度属性值聚合成并集列表：
         deps  = [t.DepProject …] / engs = [t.EgProject …] / nodes = [t.Node …] / pps = [t.PpApplication …]
   · 各维度分别在该 appId 的属性列表内匹配（DepProject 模糊包含，其余精确）：
         全部维度命中 → 该 appId 入集合
   · 返回的 appId 集合写入 RowFilter.ApolloAppIdIn
        DB 侧:   WHERE apollo_app_id IN (...)
        文件侧:  matchRow 中 appIds[r.ApolloAppId] 判定
   · ok=false（关系链不可用）→ 调用方回退对原始列过滤（保持旧行为）
```

> **下推必须与复核同口径（appId 级并集）**：不能要求「同一条属性项同时满足所有维度」。
> 否则「属性项1 满足维度甲、属性项2 满足维度乙」的 appId 会被下推误剔除——下推即候选行范围，
> 复核阶段再也拿不到这些行，表现为结果少数据（详见 §5.3 与《接口逻辑说明.md》§3.2 注）。

### 5.3 属性补充后复核（`filterAttachRows`）

下推用的是「该 appId **至少有一个**属性项命中」，而一个 appId 的属性列表可能含多个值 → 复核粒度是 **appId**：该行 appId 的属性列表中任一命中，即保留该 appId 的**全部中间件关系行**，不按属性组合切分关系数据集：

```
filterAttachRows(rows, q appAttrQuery):
   q.DepProject    != "" && !attrHit(r.DepProjects,    r.DepProject,    q.DepProject,    true)  → 剔除  // 模糊
   q.EngProject    != "" && !attrHit(r.EngProjects,    r.EngProject,    q.EngProject,    false) → 剔除  // 精确
   q.Node          != "" && !attrHit(r.Nodes,          r.Node,          q.Node,          false) → 剔除  // 精确
   q.PpApplication != "" && !attrHit(r.PpApplications, r.PpApplication, q.PpApplication, false) → 剔除  // 精确
```

> `attrHit` 优先在属性列表内匹配（模糊/精确），列表为空（关联属性未补充）时回退单值列，保证不误杀。
> **下推只能收窄候选行，不能代替复核。** 这是本方案最容易出错的一点。

### 5.4 内存分页（`pageRows`）

- `pageSize < 0` → 不分页取全量（内部候选撮取用）
- `pageSize == 0` → 默认 20（与数据源层口径一致）
- 行序保持数据源行序；`total = len(属性补充并复核后的候选关系行)`

> **`total` 随 `expandDepNode` 口径变化**：上列「候选关系行数」为**折叠口径**（显式 `expandDepNode=0`，`env=PRO` 实测 1418 = 快照关系行数）；**默认展开**时行已按部署点扩行（`expandByDeploySlot`），`total` = **5266**（2026-09-20 快照；随每日快照变化，以接口返回为准）。见 §4.3 与《[运维拓扑.md](运维拓扑.md)》§4.5。

### 5.5 前端属性筛选（本地，与后端同口径）

`/graph` 返回的应用节点已带 appId 级属性（多值列表 `depProjects` / `engProjects` / `nodes` / `ppApps`，单值 `depProject` / `engProject` / `node` / `ppApp` 为首值）。前端「属性筛选」直接在这四个维度上做**本地即时筛选**，口径与后端 `appAttrQuery` 完全一致：

- 匹配对象取多值列表（列表为空回退单值）；`depProject` 模糊包含，`engProject` / `node` / `ppApplication` 精确相等；**同一维度可多选（任一命中即算该维度命中），维度之间为 AND**；
- 命中的应用**保留其全部依赖**（中间件节点按「其来源应用是否有命中者」保留，实例层按「其名下应用是否有命中者」保留），与后端「命中即保留该 appId 全部关系行」一致；
- 命中的应用**不受前端密度裁剪**（`prepareLayer` 的 `attrKeepCount`），避免筛选结果被裁剪掉；
- 本地筛选无需回传后端；如需服务端裁剪，请求 `/graph` 时带 `depProject` / `engProject` / `node` / `ppApplication` 四参数即可（同一参数可传逗号分隔多值，维度内 OR；两者可叠加）。

> 三个原型页（`prototype/topology_g6.html`、`topology_dagre.html`、`topology_prototype.html`）属性筛选交互一致：四维（部署项目 / 工程项目 / 机房节点 / PP 应用）统一为「输入候选 → 回车加入 chips（可多选）→ 单项 × 或整体清空」；`topology_prototype.html` 无实例层，其「机房节点」同样由属性筛选的 node 维度承担。详见《[前端对接说明.md](前端对接说明.md)》§3.3。

## 6. 第五阶段：详细展示

### 6.1 `/list` —— 关系列表

```
GetOperationTopologyList(req):
  1. req.SyncDate == "" → LatestSyncDateOf(env, source) 取最新快照日期
  2. 组装 RowFilter（syncDate/env/middlewareType/appId/appName/hostName/dept/owner/connectAddr/source）
  3. 部署项目/节点：
       relationFilterApps(req.DepProject, req.Node)
         ok  → f.ApolloAppIdIn = apps, filterApplied = true
         !ok → f.DepProject / f.Node 直接下推（旧行为）
  4. f.Page, f.PageSize = 1, -1        ← 全量候选
  5. rows = attachAppAttrs(q.Rows)     ← 属性补充（多值聚合为列表，不扩行）
  6. filterApplied → filterAttachRows(rows, depProject, node)
  7. return pageRows(rows, req.Page, req.PageSize), int64(len(rows)), source   ← total = 候选关系行数
```

返回字段即 `OperationTopology` 全字段（含属性补充后的单值 `dep_project/eng_project/node/pp_application` 与多值列表 `depProjects/engProjects/nodes/ppApplications`）。

> 上列步骤 5~6 为**折叠口径**（显式 `expandDepNode=0`）：`attachAppAttrs` 只补属性、**不扩行**（`total` = 1418）；**默认展开**时改为 `expandByDeploySlot` 按部署点扩行、复核走 `filterSlotRows`，`total` = **5266**（2026-09-20 快照；随每日快照变化），且 `dep_project` / `node` 为单值、多值列表清空。见 §4.3 与《[运维拓扑.md](运维拓扑.md)》§4.5。

### 6.2 `/graph` —— 拓扑图聚合

```
GetGraph(q):
  1. 定位快照日期（LatestSyncDateOf）；无任何快照 → 返回空图（Nodes/Edges/ApolloHosts 均为 []，非 null）
  2. 节点（机房）过滤同 list：relationFilterApps("", q.Node) 下推
  3. rows = QueryAll(f) → attachAppAttrs(rows) → filterAttachRows(rows, "", q.Node)
  4. 聚合：
       · 应用节点 id = "app:" + appKeyOf(r)        ← 以 apollo_app_id 合并（缺失回退 dep_project）
         同一 appId 多行的属性取并集（depProjects/engProjects/ppApps/nodes），不因属性多值分裂节点
         节点上聚合去重的 ApolloHosts（id/name/host/appCount）
       · 中间件节点 id = "mw:" + type + ":" + addr  ← 按 类型+地址 合并（防拓扑爆炸）
       · 边 "app:…→mw:…" 去重，kind = "depend"
  5. 回填：中间件节点 DepCount / AppIds（被依赖应用清单）
  6. 汇总 ApolloHosts（按 id 排序）、Counts{apolloHosts, application, middleware, edges, nodes}
  7. resp.DataSource = 本次活跃数据源（db|file）
```

### 6.3 `/detail` —— 节点详情

```
GetNodeDetail(q):
  1. rows = QueryAll(syncDate, env) → attachAppAttrs(rows)   ← 图与详情同口径
  2. 全快照内预统计 中间件(类型+地址) → 被依赖应用集合（mwApps，一次遍历）
  3. 按 id 前缀分发：
       app:{appKey}  → 筛选 appKeyOf(r)==key，输出应用本体 + 关联中间件(含 DepCount) + 实例归属
       mw:{type}:{addr} → 筛选同类型同地址，输出中间件本体 + 依赖应用清单(DepCount) + 实例
       host:{hostId}    → 筛选同实例，输出实例本体 + 名下应用清单
  4. 去重合并：d.ApolloHosts / d.Apps / d.Middlewares 各自按 key 去重
```

三类节点的 id 前缀与 `/graph` 完全一致，保证前端「图上点击 → 详情」可直接复用同 id。应用（application）本体与其 `apps` 列表项额外带 4 个多值属性列表（`depProjects`/`engProjects`/`nodes`/`ppApps`），同一 appId 多行取并集，不因属性多值分裂节点。

## 9. 关键设计要点与注意事项

1. **先取全量候选、属性补充后再复核分页**：`/list` 必须全量取候选 → 属性补充 → 复核 → 内存分页；`total` = 候选关系行数（不放大，**折叠口径 1418 / 默认展开 5266**，2026-09-20 快照，见 §4.3）。graph/detail 同理（`QueryAll` + `attachAppAttrs`，展开时 `expandByDeploySlot`）。
2. **下推 + 复核缺一不可**：`relationFilterApps` 只收窄候选，`filterAttachRows` 才是最终判定（判定粒度为 appId，任一属性命中即保留该 appId 的全部中间件关系行）。
3. **降级保不丢行**：跳① 查询期 ADR 表 → 本地镜像 → 接口兜底（仅首次）→ 置空（`ok=false`，读接口按原行返回）；跳② DB → 文件。
4. **不丢行原则**：`attachAppAttrs` 对未命中的行原样保留，绝不因关联失败丢数据。
5. **环境口径统一**：索引键以 `apolloAppEnv` 字符串与 `env` 精确对齐。
6. **id 口径统一**：`appKeyOf` 是图（`app:{appKey}`）与详情（`/detail?id=app:{appKey}`）共用的唯一口径。`appKey` 随 `expandDepNode` 变化——折叠（显式 `0`）为 `apollo_app_id`，**默认展开**为 `apollo_app_id|部署项目|节点`；展开态 id 自带 2 个 `|` 时详情（`/detail`）一律按部署点定位，与图节点一致（见《[运维拓扑.md](运维拓扑.md)》§4.5）。
7. **接口 DTO 不复用表模型**：`del_flag`/`isReleased` 的 bool ↔ TINYINT 差异需单独 DTO。

## 10. 端到端调用链（文字时序）

**采集（每天 01:30 / 手动）**

```
cronTask.SyncOperationTopology()
  └─ service.SyncOperationTopology(trigger)
       └─ syncOperationTopology()
            ├─ SyncAppDpRelation         ← 步骤 0：跳① 关系全量拉取 → 与库内比对，有变化才整表替换落库 ADR + 镜像 + 索引失效
            ├─ GetHostList → FilterHostsByName → ProbeHosts → GetAppsConcurrent
            ├─ 组装 scanTask（host × env × app × ns）+ ns 学习定向
            ├─ worker: GetNamespace → parseItemsToRelations（解析规则）
            ├─ 汇总去重（relationKey）→ diffRelations / mergeUnfinishedRows
            └─ ReplaceSnapshot（DB insert 或 本地文件原子写）
```

**查询（HTTP 读接口）**

```
GET /api/external/operationTopology/{list|graph|detail}
  └─ api.GetOperationTopology{List|Graph|Detail}
       └─ service.GetOperationTopology{List|Graph|Detail}
            ├─ currentRouter().resolve(source)          ← db/file/auto
            ├─ LatestSyncDateOf(env, source)            ← 定位最新快照
            ├─ relationFilterApps(q appAttrQuery)       ← 过滤下推（[dp_relation]）
            ├─ ListRows / QueryAll                      ← 全量候选（Page=1,PageSize=-1）
            ├─ attachAppAttrs                           ← 跳①×跳② 属性补充（多值聚合为列表，不扩行）（[dp_relation]×[pinpoint]）
            ├─ filterAttachRows                         ← 属性补充后复核（判定粒度为 appId）
            └─ pageRows / 聚合                           ← 分页 / 图节点边 / 节点详情
```
