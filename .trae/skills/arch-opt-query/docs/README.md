# arch-opt-query 架构优化智能体（Skill 介绍）

> 版本：2.0.0　|　类型：薄指令层 Skill　|　依赖：`arch-opt-mcp-server`（:8062）

本 skill 是架构优化智能体的**薄指令层**。它负责识别触发场景、编排数据采集工具、组装大模型 Prompt；所有数值计算与阈值判定由配套的 [arch-opt-mcp-server](../../../../arch-opt-mcp-server/docs/README.md) 完成，大模型只负责解释风险、串联影响、组织报告与提出建议。

---

## 一、解决什么问题

传统架构巡检依赖人工翻看监控、逐项对阈值、凭经验总结，存在三个痛点：

1. **口径不统一**：阈值散落在各处，判定标准因人而异。
2. **结论不可溯源**：说不清「这个风险是怎么判出来的」。
3. **建议不落地**：发现问题后给不出可执行的优化方案。

本 skill 将巡检拆成「**确定性判定**（规则引擎）+ **解释与建议**（大模型）」两段，输出一份带证据、带建议、可追溯的架构优化报告。

---

## 二、触发场景

当用户提出以下诉求时，由本 skill 接管：

- 分析某节点（贵州 / 广州4d / 云公司省市节点）的架构风险
- 关注副本冗余、容量瓶颈（CPU 限流 / 内存 / HPA）、负载不均衡
- 排查近期 OOM、容器重启
- 分析服务链路依赖、调用集中度
- 检查省节点宿主机故障域是否集中
- 要求生成架构优化 / 架构巡检报告

---

## 三、六大分析维度

| 维度 | 工具（MCP） | 分析内容 | 判定依据 |
|------|-------------|----------|----------|
| D1 副本数量与可用性 | `mcp_replica` | 期望副本是否满足冗余、可用副本是否低于期望 | `min_replicas`（默认 3） |
| D2 容量瓶颈 | `mcp_capacity` | CPU 限流、内存使用率、HPA 是否达最大副本 | CPU>20%、内存>85%、持续 15min |
| D3 负载不均衡 | `mcp_load_balance` | 同 deployment 内 Pod CPU 最大/平均 > 2 | 持续 15min |
| D4 OOM | `mcp_oom` | 近期 OOMKilled 且存在重启证据 | 窗口默认 7 天 |
| D5 链路依赖 | `mcp_link_dependency` | 模块上下游调用关系与集中依赖 | 阈值待联调制定 |
| D6 故障域 | `mcp_fault_domain` | 项目→云主机→物理宿主机集中度 | 同宿主机即风险；集中>50% |

> 各维度完整 PromQL 与数据来源见 [数据查询对照表.md](../../../../arch-opt-mcp-server/数据查询对照表.md)。

## 四、编排流程

### 场景一：中心节点（贵州 / 广州4d）

```
mcp_module_topology（入口，取 deploy_node + -dep 应用）
        │
        ├─ mcp_replica        D1
        ├─ mcp_capacity       D2
        ├─ mcp_load_balance   D3
        ├─ mcp_oom            D4
        └─ mcp_link_dependency D5（依赖 deploy_node）
        ▼
   汇总四态结果 + 证据 → 组装 Prompt → 大模型生成报告
```

### 场景二：省市节点（云公司相关节点）

```
mcp_node_list（取 ctyun_node_code3）
        │
        ├─ mcp_virtual_structure（宿主机 ↔ 云主机映射）
        ├─ mcp_topology_info（项目 ↔ 云主机部署）
        └─ mcp_fault_domain（汇总集中度）  D6
        ▼
   汇总 → 组装 Prompt → 大模型生成报告
```

### 场景三：全量分析

同时执行场景一 + 场景二，生成完整报告。

## 五、三条铁律

1. **数据不编造**：任何结论必须来自 MCP 工具返回的证据；缺失数据一律标注「信息不足」，不得推断为「无风险」。
2. **数值不越权**：阈值判定由规则引擎完成，大模型不得自行计算或改判；口径调整需改 `thresholds.json`。
3. **建议必匹配**：每条优化建议必须与一个已发现风险（🟥）一一对应，含立即缓解、根治方案、预期收益、前置条件、优先级。

---

## 六、结果四态

| 状态 | 标识 | 报告处理 |
|------|------|----------|
| `risk` | 🟥 | 输出问题卡 + 优化建议 |
| `ok` | 🟩 | 计入「正常项」，简述 |
| `insufficient` | 🟨 | 标注「信息不足」，说明缺口 |
| `not_applicable` | ⚪ | 单独归类，不计入风险/正常 |

---

## 七、报告输出

报告套用《架构优化报告模板》，核心结构：

- **执行摘要**：四态统计（🟥/🟩/🟨/⚪）+ 严重程度分级（P0~P3）
- **巡检范围**：节点与模块清单
- **风险分析**：逐维度输出，每个 🟥 按 **7 字段问题卡**：
  `问题描述` / `证据` / `影响范围` / `严重程度` / `优化建议` / `前置条件` / `优先级`
- **风险汇总**：状态列 + 解决方案摘要
- **优化建议**：按 P0~P3 分组，与风险一一对应
- **附录**：采集时间、规则版本、原始证据、数据覆盖率与限制

Prompt 组装方式见 [references/prompt_template.md](../references/prompt_template.md)。

## 十、设计要点

| 设计 | 目的 |
|------|------|
| 薄指令层 + MCP 分离 | 指令层轻量易改，采集与判定集中可测 |
| 数据与结论分离 | 避免大模型编造数据，结论必须可溯源到证据 |
| 阈值外部化 | 改口径只动 `thresholds.json`，无需改代码/模板 |
| 时间窗口证据 | 持续类规则用 `[15m]` 窗口，不用单次瞬时值 |
| 数据缺口显式化 | 缺失即标 🟨，杜绝「假阴性」 |
| 自动派生应用列表 | D1~D4 缺省时由模块拓扑派生 `-dep` 应用，简化编排 |
