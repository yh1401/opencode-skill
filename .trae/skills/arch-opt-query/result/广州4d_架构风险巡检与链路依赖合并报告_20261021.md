# 第一部分：架构风险巡检（2026-10-20 扫描）

## 1.1 扫描方法与数据覆盖

- 方法：放弃「逐应用×逐规则」（约 1000 次查询），改为**节点级 PromQL 全量扫描**，仅对违规序列定点下钻。
- 数据覆盖：
  - cAdvisor 指标覆盖全量容器（16,335 序列）→ CPU 限流 / 内存 / OOM / 重启可评估；
  - kube-state-metrics **仅覆盖「广州4-harbor」基础设施集群（16 个 Deployment）**；两个业务集群（guangzhou4d-prod、tykj-guangzhou4d-az-prod）无副本 / HPA 指标 → 相关规则「数据不足」；
  - 仅 143 个容器设置了 Memory Limit，内存比值规则对大部分容器不适用；
  - Prometheus 无 `kube_horizontalpodautoscaler_*` 指标。

## 1.2 风险清单

| 编号 | 对象 | 风险 | 级别 | 证据 |
|---|---|---|---|---|
| **R1** | etcd（Pod `etcd-10.135.65.19`，广州4-harbor 集群） | **慢性重启**：近 30 分钟重启 6 次，2 小时趋势每 5 分钟一次，重启原因 Completed | P1（基础设施） | 重启计数范围查询多点采样 |
| **R2** | `seelink-device-center-control-dep`（ns: sl-center-device） | **CPU 限流持续 15 分钟以上**：副本 nnktt 限流 80~86%，副本 m8655 限流 47~51% | P1（核心业务） | 15 点×60s 持续采样 |
| R3 | `security-permission-check-dep` | CPU 限流快照 35.7% | P3（候选） | 仅单点快照，**持续性未验证** |
| R4 | `filebeat` | 大量容器限流 46~81% | P3（候选） | 快照，持续性未验证 |
| R5 | 广州4-harbor 基础设施集群 16 个 Deployment | 副本数 ≤2（`kube_deployment_spec_replicas <= 2` 触发） | P2 | 节点级扫描 |

## 1.3 规则状态总览（8 条规则）

| 规则 | 状态 | 说明 |
|---|---|---|
| deployment_replicas（副本≤2） | **触发** | R5（基础设施集群）；业务集群数据不足 |
| deployment_available | 未触发 | 当时扫描未返回违规序列 |
| cpu_throttle_ratio（CPU 限流） | **触发** | R2 持续；R3/R4 候选 |
| memory_ratio（内存>85%） | 未触发 | 无容器工作集/limit>85%；多数容器无 Limit，部分不适用 |
| hpa_replicas（HPA） | **数据不足** | 无 HPA 指标覆盖 |
| pod_cpu_imbalance | 未覆盖 | 当时未执行 |
| oom_killed（OOM） | 未触发 | 无 OOMKilled |
| restart_increase（重启） | **触发** | R1 etcd |

## 1.4 巡检结论

1. **R2 为最大业务风险**：设备控制核心服务长期 CPU 受限，直接压制设备链路吞吐；
2. **R1 为基础设施慢性风险**：etcd 每 5 分钟重启一次，影响 harbor 集群稳定性；
3. **监控覆盖不足**：业务集群未接入 kube-state-metrics，副本 / HPA / 可用性规则无法评估，属结构性盲区。

2. sl-gateway-dep（L3）承载全节点最大流量，若叠加 R1 所在集群异常，网关层是首要受损点；
3. L1 与 R1/R2 无直接关联，独立跟进。
