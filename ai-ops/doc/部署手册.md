## 0. 最短路径（先跑起来）

```bash

# 2) 确认拓扑快照已就位（随仓库提供，见 2.2）
```

启动后：

| 入口 | 地址 |
|---|---|

| Postgres（宿主） | `127.0.0.1:55432`，库/用户/密码均为 `aiops` |

## 1. 系统组成

```text
浏览器
  │
  ▼
frontend  nginx:80（宿主 5173）
  │  静态资源 + /api 反向代理（服务名 backend:8080）
  ▼
backend   8080  拓扑计算 / 巡检 / 排障 / 告警 / 工单 / 稽核 / MCP 网关
  ├── topo/tprel/data        拓扑快照（只读挂载）
  ├── backend/data           运行状态（JSON 文件，主存储）
  ├── postgres:5432          状态镜像备份（可选，宿主 55432）
  └── MCP 上游
        ├── 默认：mock-mcp（单进程四端口 8888 / 8090 / 8061 / 9201，数据=backend/mockdata）
        └── 可选：真实 pinpoint-mcp / prometheus-mcp / cmdb-mcp / elasticsearch-mcp
```

| 服务 | 容器名 | 宿主端口 | 说明 |
|---|---|---|---|
| `frontend` | aiops-frontend | 5173 → 80 | nginx 静态站，`/api` 反代 backend |
| `backend` | aiops-backend | 8080 | Go 单进程，全部业务能力 |
| `mock-mcp` | aiops-mock-mcp | 8888 / 8090 / 8061 / 9201 | 模拟 pinpoint / prometheus / cmdb / es 四个 MCP |
| `postgres` | aiops-pg | 55432 → 5432 | 文件存储的备份镜像（默认未启用，见第 6 节） |

## 2. 前置条件

### 2.1 软件

| 软件 | 版本要求 | 用途 | 检查命令 |
|---|---|---|---|
| Docker Engine / Docker Desktop | 支持 `docker compose` v2 | 运行四个容器 | `docker compose version` |
| Go | **1.24+**（`backend/go.mod` 声明 `go 1.24`） | 宿主机交叉编译 `aiops-server`、`mockmcp` | `go version` |
| Node.js | 18+，建议 20/22 | 构建前端 `dist` | `node -v` |
| npm | 随 Node | 安装前端依赖 | `npm -v` |
| Python | 3.8+（仅标准库） | 运行 `scripts/seed_demo.py` 造数 | `python3 --version` |
| Chrome | 可选 | `scripts/ui-smoke-chrome.mjs` UI 冒烟 | — |

国内网络建议先配镜像，避免构建卡住：

```bash
go env -w GOPROXY=https://goproxy.cn,direct
npm config set registry https://registry.npmmirror.com
```

### 2.2 拓扑快照（已随仓库提供）

平台启动时必须能读到 `operation_topology.json`，否则后端直接启动失败：

```text
[boot] 拓扑数据源初始化失败: 读取拓扑快照失败: stat /data/tprel/operation_topology.json: no such file or directory
```

快照已随仓库提交在 `ai-ops/topo/tprel/data`，克隆后即可用。目录至少包含：

```text
topo/tprel/data/
├── operation_topology.json          # 必需：拓扑主快照
├── operation_topology_learned.json  # 可选：学习后的拓扑
├── app_dp_relation.json             # 可选：应用↔部署点关系
└── deploy_pinpoint_relation.json    # 可选：部署点↔PP 应用关系
```

`docker-compose.yml` 中 backend 的挂载是相对路径，**相对于 `ai-ops/platform` 目录**：

```yaml
volumes:
  - ../topo/tprel/data:/data/tprel:ro
```

本地（非容器）启动时后端会按顺序自动探测：`ai-ops/topo/tprel/data` → 旧的工作区外布局 `opencode_skill/topo/tprel/data`，一般无需手动设置 `TOPO_DATA_DIR`。

若快照放在别处，用 `TOPO_MODE=file TOPO_DATA_DIR=<绝对路径>` 覆盖。注意：目录不存在时 Docker 会自动创建**空目录**再挂载，后端仍会因找不到 `operation_topology.json` 反复重启，不要被“容器已启动”误导。

### 2.3 端口占用

| 端口 | 用途 | 常见冲突 |
|---|---|---|
| 5173 | 前端 | 本地 Vite dev server 也默认 5173 |
| 8080 | 后端 | 常见 Web 服务 |
| 55432 | Postgres | 一般无冲突（特意避开了 5432） |
| 8888 | mock pinpoint MCP | 真实 pinpoint-mcp 也用它 |
| 8090 | mock prometheus MCP | 真实 prometheus-mcp 常占用 |
| 8061 | mock cmdb MCP | 一般无冲突 |
| 9201 | mock es MCP | 一般无冲突 |

冲突时改 `platform/docker-compose.yml` 的 `ports` 左侧宿主端口即可，例如 `"18080:8080"`；前端仍通过容器网络访问 `backend:8080`，不受影响。但本地 `npm run dev` 的代理固定指向 `127.0.0.1:8080`（见 `frontend/vite.config.ts`），改端口后要同步改。

另：后端排障日志取证默认找宿主 `:8020` 的 `log_analyzer`（compose 已用 `host.docker.internal:8020`，因为 8000 常被占用）。该服务未启动不影响主流程，只影响 `/log-analysis` 页与日志证据步骤。

### 2.4 资源

- 磁盘：约 3 GB（三个基础镜像 + `node_modules` + Go 构建缓存 + 二进制）。
- 内存：建议 4 GB 以上（前端构建 + 四个容器）。
- 网络：首次构建需拉取 `alpine:latest`、`nginx:alpine`、`postgres:16-alpine`，并下载 Go module / npm 包。

## 4. Docker 一键部署（推荐）

### 4.1 执行

```bash
cd ai-ops/platform
chmod +x scripts/docker_up.sh scripts/run_demo.sh
./scripts/docker_up.sh
```

需要重建/更新时重复执行同一条命令即可（脚本每次都重新编译、重新 build 镜像）。

### 4.2 `docker_up.sh` 做了什么

1. 用 `docker version --format '{{.Server.Arch}}'` 判断目标架构（Apple Silicon/ARM → `arm64`，x86 → `amd64`）。
2. `python3 backend/scripts/seed_demo.py`：按 5 条演示链路生成/校正 `backend/mockdata` 下的告警、日志计数、主机指标、CMDB 补齐记录和 `_scenarios.json`（会**写入** `mockdata`，可重复执行）。
3. 在宿主机交叉编译出 Linux 二进制到 `backend/build/`：
   - `aiops-server`（平台后端）
   - `mockmcp`（Mock MCP 上游）
4. 拷贝宿主机 `/usr/share/zoneinfo` 到 `backend/build/zoneinfo`（alpine 镜像没有 tzdata）。
5. 前端：`node_modules` 不存在时 `npm ci`，然后 `npm run build` 产出 `frontend/dist`。
6. `docker compose -f docker-compose.yml up -d --build`，并轮询 `http://127.0.0.1:8080/api/health` 直到就绪（最多约 80 秒）。

> **不要跳过脚本直接 `docker compose up --build`**。两个 Dockerfile 都是“只 COPY 产物”的运行时镜像：
> - `backend/Dockerfile` 需要 `backend/build/aiops-server`、`backend/build/mockmcp`、`backend/build/zoneinfo`
> - `frontend/Dockerfile` 需要 `frontend/dist`
>
> 缺失时会报 `COPY failed: file not found in build context`。

### 4.3 容器状态

以下命令均默认在 `ai-ops/platform` 目录执行：

```bash
docker compose ps
```

期望看到 `aiops-frontend`、`aiops-backend`（healthy）、`aiops-mock-mcp`、`aiops-pg` 四个容器 Up。

### 4.4 常用运维命令

```bash
# 日志
docker compose logs -f backend
docker logs -f aiops-mock-mcp

# 只重启后端
docker compose restart backend

# 停止（保留 PG 数据卷）
docker compose down

# 停止并删除 PG 数据卷（数据不可恢复）
docker compose down -v
```

### 5.6 登录与账号权限

平台使用本地账号 + JWT（HS256，默认 8 小时）鉴权；前端未登录会跳转 `/login`，后端除健康检查与登录接口外全部校验令牌。

**角色与权限**

| 角色 | 读 | 写业务数据 | 工单 | 用户管理 | MCP 控制台 / 告警静默 |
|---|---|---|---|---|---|
| `admin` | 是 | 是 | 认领、指派、改派、处置、关闭、重开 | 增删改查 | 是 |
| `ops` | 是 | 是 | 认领、处置、关闭（仅本人负责的工单） | 只读 | 否 |
| `viewer` | 是 | 否（非 GET 接口一律 403） | 只读 | 否 | 否 |

**工单流转**：`open → assigned → in_progress → resolved → closed`。

- `open` 时任意 `ops` 可认领，`admin` 可指派；
- 认领/指派后只有处理人本人或 `admin` 可开始处置、标记已处置、确认关闭；
- 系统在告警恢复（AutoResolve）时最多把工单推进到 `resolved`，`closed` 必须人工确认；
- `admin` 可改派、可把 `resolved` / `closed` 重开；
- 工单带版本号，并发操作会返回 `409`，前端提示后刷新即可。

**账号管理**

- 首次启动按 `AUTH_INIT_ADMIN_USER` / `AUTH_INIT_ADMIN_PASSWORD` 创建管理员；账号已存在时只校正角色与启用状态，不改密码。
- 演示账号由 `AUTH_DEMO_USERS` 创建，格式 `username:password:role`，逗号分隔；只补建不存在的账号，不会覆盖已改过的密码。`docker-compose.yml` 默认内置 `ops1` / `viewer1` 两个账号，正式环境请置空。
- 登录后可在右上角退出；管理员通过 `POST /api/users` 创建 `ops` / `viewer` 账号，改密、禁用、改角色会立即让旧令牌失效。
- 连续 5 次密码错误锁定 5 分钟。
- 生产环境务必配置 `AUTH_SECRET`（至少 32 位随机串）。未配置时进程启动会生成临时密钥并打印告警，重启后所有令牌失效。
- 同域部署（nginx 反代 `/api`）无需配置 CORS；前后端分离跨域时把前端地址加入 `AUTH_ALLOWED_ORIGINS`（逗号分隔），为空则不下发跨域头。

**公司统一认证（OIDC/SSO）**：代码已预留 `AuthProvider` 接口与 `CorporateProvider` 占位，配置 `OIDC_ISSUER` / `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` / `OIDC_REDIRECT_URL` 后可访问 `/api/auth/sso/authorize` 获取授权地址；完整回调与用户映射需按公司目录对接，当前版本仍以本地账号为准。

## 6. 数据库（Postgres）说明与启用

### 6.1 定位：文件为主，PG 是备份镜像

这点很容易误解，先明确：

- 平台**主存储是 JSON 文件**：`backend/data/<docType>/<docID>.json`（容器内 `/app/data`，宿主目录 `platform/backend/data`）。
- 配置 `POSTGRES_DSN` 后，每次写入会 **best-effort 再写一份** 到 PG 表 `platform_docs`；读取时文件缺失才回退 PG，并回填文件。
- PG 不可用**不会阻塞启动**，也不影响业务；`/api/health` 的 `storage.pgStatus` 会显示 `unavailable: ...`，后台每 15 秒重试。
- 拓扑快照**不存 PG**，永远来自 `topo/tprel/data` 或 topo HTTP 服务。
- `docker-compose.yml` 默认 **PG 容器会启动，但后端 DSN 为空**，即数据库容器在跑、平台并未使用它。

### 6.2 启用

在启动命令前加上 DSN（注意容器内主机名是 `postgres`）：

```bash
cd ai-ops/platform
POSTGRES_DSN='postgres://aiops:aiops@postgres:5432/aiops?sslmode=disable' ./scripts/docker_up.sh
```

或写入 `ai-ops/platform/.env`（compose 会自动读取）：

```dotenv
POSTGRES_DSN=postgres://aiops:aiops@postgres:5432/aiops?sslmode=disable
```

然后重新创建后端容器：

```bash
cd ai-ops/platform
docker compose up -d backend
```

### 6.3 验证

```bash
# 1) 后端视角
curl -s http://127.0.0.1:8080/api/health | python3 -m json.tool
# storage.postgres 应为 true，storage.pgStatus 应为 connected

# 2) 直接进库看表
docker exec -it aiops-pg psql -U aiops -d aiops -c '\dt'
docker exec -it aiops-pg psql -U aiops -d aiops -c \
  "select doc_type, count(*) from platform_docs group by 1 order by 2 desc;"
```

宿主客户端连接参数：`host=127.0.0.1 port=55432 dbname=aiops user=aiops password=aiops`。

> 后端比 PG 先就绪时，`pgStatus` 可能短暂为 `unavailable`；等 PG healthy 后写入会自动恢复，无需重启。

### 6.4 表结构

无需手工建表、也没有迁移脚本；后端首次连上 PG 会自动执行：

```sql
CREATE TABLE IF NOT EXISTS platform_docs (
  doc_type   text        NOT NULL,
  doc_id     text        NOT NULL,
  payload    jsonb       NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (doc_type, doc_id)
);
```

`doc_type` 包括 `alarm_event`、`diagnosis_session`、`ticket`、`inspection_task`、`audit_*`、`knowledge_case`、`identity_app`、`identity_host`、`tool_call_log` 等。

### 6.5 持久化、备份、恢复

- 数据卷：`aiops-pg-data`（实际名字通常为 `aiops-platform_aiops-pg-data`，以 `docker volume ls` 为准），`docker compose down` 不会删除，`down -v` 会删除。
- 密码只在**数据卷初始化时**生效；已有卷再改 `POSTGRES_PASSWORD` 不会改库内密码，需要：

```bash
docker exec -it aiops-pg psql -U aiops -d aiops -c "ALTER USER aiops WITH PASSWORD '新密码';"
```

备份 / 恢复：

```bash
# 备份
docker exec aiops-pg pg_dump -U aiops aiops > aiops-$(date +%F).sql

# 恢复（空库或确认覆盖前先备份）
cat aiops-2026-11-16.sql | docker exec -i aiops-pg psql -U aiops -d aiops
```

### 6.6 从 PG 恢复业务状态

若 `backend/data` 清空但 PG 里仍有数据：保留同一 DSN 启动，平台按 `docType` 读取时会从 PG 回读并回填文件。**列表类接口**在本地目录为空时同样会回退 PG。因此换机迁移时，只要有 PG 备份，也可以不搬 `backend/data`。

## 7. 前端部署细节

- 构建产物：`frontend/dist`，由 `npm run build`（含 `tsc --noEmit` 类型检查）生成。
- 运行方式：`nginx:alpine` + `frontend/nginx.conf`：
  - `/api/` 反代 `http://backend:8080`，`proxy_read_timeout 300s`（排障 SSE 需要）
  - 其余路径 `try_files ... /index.html`，支持 React Router 刷新
  - 用 Docker 内置 DNS `127.0.0.11` 动态解析 `backend`，容器重建换 IP 也不会 502
- API 基地址写死为相对路径 `/api`（`frontend/src/api.ts`），不需要配置域名。
- 可选构建变量：`VITE_LOG_ANALYZER_URL`。不配时 `/log-analysis` 按当前访问主机的 `:8000` 推导 iframe 地址；后端日志取证则用 compose 里的 `LOG_ANALYZER_URL`（默认 `http://host.docker.internal:8020`）。

单独更新前端：

```bash
cd ai-ops/platform/frontend
npm ci          # 首次或依赖变更时
npm run build
cd ..
```

## 8. 后端部署细节

- 单个静态二进制，无 CGO（`CGO_ENABLED=0`），配置全部来自环境变量。
- 入口：`backend/cmd/server`；Mock 上游：`backend/cmd/mockmcp`。
- 启动日志会打印 `addr=... topo=... data=... store=... pg=... mcp=...`，可直接确认配置是否生效。
- 优雅退出：收到 `SIGINT/SIGTERM` 后停止后台循环（告警采集、劣化扫描、巡检调度）并在 5 秒内关闭 HTTP。
- 状态目录 `STORE_DIR`（compose 为 `/app/data`）必须可写；首次启动会自动创建子目录。
- 身份映射（应用/主机统一身份）在启动时**异步重建**，失败只打日志、不阻断服务；重建期间部分页面数据可能稍后才完整。

只重建后端：

```bash
cd ai-ops/platform
./scripts/docker_up.sh          # 会连带重建前端，最稳
# 或只重建后端镜像
docker compose -f docker-compose.yml up -d --build backend
```

> 直接 `docker compose ... up -d --build backend` 前提是 `backend/build` 下的二进制已存在（跑过一次 `docker_up.sh`）。

## 10. 切换 mock / 真实数据（`DATA_MODE`）

数据面由单一开关控制，默认 `mock`：

```bash
# mock（默认）：四路上游指向本机 mockmcp（8888/8090/8061/9201）
DATA_MODE=mock ./scripts/run_demo.sh

# real：不再提供 mock 兜底地址，必须显式给出三路核心上游（ES 可选）
DATA_MODE=real \
PINPOINT_MCP_URL=http://<pinpoint-mcp>:8888/mcp \
PROMETHEUS_MCP_URL=http://<prometheus-mcp>:8090/mcp \
CMDB_MCP_URL=http://<cmdb-mcp>:8061/mcp \
ES_MCP_URL=http://<es-mcp>:9201/mcp \
./scripts/run_demo.sh
```

行为约定：

- `DATA_MODE=real` 时，缺少任一核心 URL 后端**启动即失败**并打印缺失项，避免“以为接了真环境其实还是 mock”；
- `ES_MCP_URL` 为空只打印告警，日志巡检 T10 / 日志证据返回 `NO_DATA`，不阻断启动；
- 开关只作用于数据来源（四路 MCP），控制面（拓扑 / 巡检 / 排障 / 告警 / 工单等）逻辑不变；
- 拓扑快照 `topo/tprel/data` 是真实生产快照，两种模式下都可使用；要走实时拓扑仍需单独设 `TOPO_MODE=http`；
- 当前生效模式可在 `/api/health`、`/api/meta` 的 `dataMode` 字段和页面底部“平台数据底座”看到。

约定：上游需提供 MCP streamable-http 的 `/mcp` 端点（JSON-RPC 2.0，支持 `initialize` / `tools/list` / `tools/call`），工具名与参数口径见 `doc/上游服务接入规范与实施.md`（第二篇 工具目录）。

`docker-compose.yml` 里的 `prometheus-mcp` / `pinpoint-mcp` 是 `real-mcp` profile 的参考实现，但它们：

- 构建/挂载路径在仓库外（`../../promthus-mcp`、`../../pinpoint-mcp`），需把这两个目录放到 `ai-ops` 同级；
- 与 `mock-mcp` 抢占 8888 / 8090。用 `--profile real-mcp` 时先 `docker compose stop mock-mcp`（后端已启动，不依赖其存活），否则端口冲突。

真实上游不可用时，平台不会崩：MCP 探活失败、相关页面降级/返回 `NO_DATA`，可在 `/mcp` 页查看探活与调用日志。

## 13. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 后端容器反复重启，日志 `读取拓扑快照失败 ... operation_topology.json` | 快照目录缺失或挂载路径不对 | 按 2.2 确认 `platform/../topo/tprel/data` 存在且已被挂载 |
| `COPY failed: file not found in build context ... build/aiops-server` | 未跑 `docker_up.sh` 就直接 build | 先执行 `./scripts/docker_up.sh` |
| `bind: address already in use` | 宿主端口被占 | `lsof -i :8090` 等排查；改 compose 端口映射 |
| 前端页面打开但接口 502 | backend 未就绪/崩溃 | `docker logs aiops-backend`；等健康检查通过 |
| `storage.pgStatus: unavailable: ...` | DSN 错误 / PG 未就绪 / 用了 `127.0.0.1` 而非 `postgres` | 容器内必须用服务名 `postgres`；确认 PG healthy |
| `/log-analysis` 提示降级 | log_analyzer 未启动（默认找 `:8020`） | 启动该服务，或改 `LOG_ANALYZER_URL`；不影响其他功能 |
| 告警/巡检结论太多、演示节奏乱 | 定时任务开启 | compose 已设 `INSPECT_CRON_ENABLED=false`；本地模式同样关闭 |
| 改了 `mockdata` 没变化 | mockmcp 启动时一次性加载 | `docker restart aiops-mock-mcp` |
| 时间显示不对/时区报错 | alpine 无 tzdata | 确认 `backend/build/zoneinfo` 已生成并 COPY 进镜像（`docker_up.sh` 负责） |
| 在 Apple Silicon 构建、部署到 x86 服务器 | 脚本按本机 Docker 架构产出二进制 | 在目标架构机器上跑 `docker_up.sh`，或显式调整 `GOARCH` 后重新构建 |
| `npm ci` 卡住 / Go 下载超时 | 外网访问慢 | 按 2.1 配置 npm / GOPROXY 镜像 |

## 附：安全提醒

当前版本已内置**本地账号 + JWT 登录鉴权**（`admin` / `ops` / `viewer` 三级角色、CORS 白名单），但仍有以下限制：

- 传输层没有 TLS，令牌与口令明文经过 HTTP；对外部署必须在 nginx 等入口加 HTTPS 反向代理。
- 默认管理员口令 `admin12345` 与演示账号 `ops1` / `viewer1` 仅用于内网演示；正式环境必须通过 `AUTH_INIT_ADMIN_PASSWORD` 覆盖管理员口令、把 `AUTH_DEMO_USERS` 置空，并配置固定的 `AUTH_SECRET`。
- MCP 控制台与告警静默仅 `admin` 可操作，但仍可直接调用上游工具；上游 MCP 的访问控制需在网关侧另行加固。
- 公司统一认证（OIDC/SSO）仅预留接口与配置占位，尚未完成回调与用户映射。

请只监听内网/本机，不要直接暴露公网。
