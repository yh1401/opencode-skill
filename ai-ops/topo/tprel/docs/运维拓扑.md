> DDL 来源：本地 Docker 库 `devops_automation_test`（容器 `devops_mysql`），为 `SHOW CREATE TABLE` 原样输出。

## 1. 需求概述

拓扑结果每条记录的整体结构：

> 节点，工程项目名，部署项目名，pp 应用名称（可能为空），apollo appid，中间件类型，连接地址，中间件项目名称

目标：`operation_topology` 表的 `node`、`eng_project`、`dep_project` 三列采集期预留空值，`pp_application` 采集期写入占位值（`appid_owner_map` 命中值，否则回退应用名）；四列统一在查询期由两跳关联作为 appId **属性补充**（多值聚合为列表，单值列取列表首值），**不回写 OT**。

## 2. 三表 DDL（主表/ADR 自动建、DPR 运维自建）

> - `operation_topology`（拓扑主表）与 `app_dp_relation`（跳① 关系表）**由程序启动时 AutoMigrate 自动创建**（`initialize/gorm.go` 的 `MysqlTables` 注册这两个模型），生产**无需手工执行**；表已存在时只补缺失列/索引，不重建、不删列。
> - `deploy_pinpoint_relation`（跳② DPR 维表）**不纳入 AutoMigrate**，由运维按 `docs/业务数据/deploy_pinpoint_relation.sql` 自建/导入，程序绝不反向改 DPR 表结构。
> - 本节 DDL 为结构权威定义（字段口径、索引、列宽），`docs/业务数据/*.sql` 供本地建档/导数据参考。

## 3. 三表关联关系

### 3.1 各表参与字段

| 表 | 参与字段 |
| --- | --- |
| `app_dp_relation`（由「app_id 与部署项目关系接口」全量落库） | `project_type`、`project_id`、`deploy_project_id`、`deploy_project_name`、`node`、`apollo_host_id`、`apollo_app_id`、`apollo_app_env` |
| `deploy_pinpoint_relation` | `dep_project`、`pp_application`、`eg_project`、`node`（`node_cn` 已废弃，不再参与） |
| `operation_topology` | `apollo_host_id`、`apollo_host_name`、`apollo_app_id`、`apollo_app_name`、`node`、`eng_project`、`dep_project`、`pp_application` |

> 接口与 `app_dp_relation` 表字段一一对应（`apolloAppId` ↔ `apollo_app_id`、`deployProjectName` ↔ `deploy_project_name`、`apolloAppEnv` ↔ `apollo_app_env`、`del_flag`/`env`/`node`/`apollo_host_id` 同义），可直接把接口返回当作关系行使用。

### 3.2 字段来源

为 `operation_topology` 的 `node`、`eng_project`、`dep_project`、`pp_application` 四字段赋值。四列均为 appId 的**属性**（取自跳② 命中的 `deploy_pinpoint_relation` 记录），查询期聚合为属性列表、单值列取列表首值，**不再按 DPR 行展开扩行**：

- `node` ← `deploy_pinpoint_relation.node`
- `eng_project` ← `deploy_pinpoint_relation.eg_project`
- `dep_project` ← `deploy_pinpoint_relation.dep_project`
- `pp_application` ← `deploy_pinpoint_relation.pp_application`

### 3.3 关联链路

```text
operation_topology.apollo_app_id
        │  ① 关联（=）
        ▼
app_dp_relation.deploy_project_name   ← 采集期由关系接口全量落库；查询期只读库/镜像
        │  ② 关联（deploy_project_name = dep_project）
        ▼
deploy_pinpoint_relation.dep_project ──► 取 node / eg_project / dep_project（pp_application 一并取值）
```

即：`operation_topology.apollo_app_id` 关联 `app_dp_relation.apollo_app_id` 取得 `deploy_project_name`；
再用该部署项目名关联 `deploy_pinpoint_relation.dep_project`，取得 `pp_application`、`eg_project`、`node`，
作为 appId 的**属性**补充到拓扑查询结果的 `node`、`eng_project`、`dep_project`（单值取列表首值，多值走 `nodes`/`engProjects`/`depProjects`/`ppApplications` 列表字段）。

> **跳② 命中值只作为 appId 属性补充，不展开行**：一个 `deploy_project` 在 DPR 中有几行（唯一键 `(dep_project, pp_application)`）就聚合出几个属性值（去重升序），**拓扑数据集行数与行序保持不变**；跳① 未命中时原样保留（`pp_application` 保留采集期占位值）。
> 查询期实现不走 SQL，而是 `dpTargets()` 内存索引 + `attachAppAttrs`，详见《[拓扑查询总体逻辑.md](拓扑查询总体逻辑.md)》§4。

## 4. 拓扑接口查询 SQL

### 4.1 结果字段映射

| 拓扑结果字段 | 来源字段 |
| --- | --- |
| `node` | `deploy_pinpoint_relation.node` |
| `eng_project` | `deploy_pinpoint_relation.eg_project` |
| `dep_project` | `deploy_pinpoint_relation.dep_project` |
| （附带）`pp_application` | `deploy_pinpoint_relation.pp_application` |

### 4.2 查询 SQL

> **口径**：下面是**诊断 SQL**——等价于查询期的两跳内存关联（`dpTargets()` + `attachAppAttrs`）的取数字段口径，用于人工核对关联结果。
> 注意：程序查询期只把命中值作为 appId 属性补充（多值聚合为列表，不扩行），而本 SQL 的 `dpr` 侧一对多会自然产生多行（见 4.3-2）。
> 生产查询走内存关联（见《[拓扑查询总体逻辑.md](拓扑查询总体逻辑.md)》§4），不执行该 SQL。

```sql
-- 【诊断口径】两跳关联，等价于查询期内存关联
SELECT
    ot.apollo_host_id,
    ot.apollo_host_name,
    ot.apollo_app_id,
    ot.apollo_app_name,
    adr.deploy_project_name,
    dpr.node          AS node,          -- 拓扑结果 node
    dpr.eg_project    AS eng_project,   -- 拓扑结果 engProject
    dpr.dep_project   AS dep_project,   -- 拓扑结果 depProject
    dpr.pp_application
FROM operation_topology ot
LEFT JOIN app_dp_relation adr
       ON adr.apollo_app_id = ot.apollo_app_id COLLATE utf8mb4_0900_ai_ci
      AND adr.del_flag = 0
      AND adr.apollo_app_env = ot.env        -- 环境对齐：与程序 dpTargets 索引键 appId|env 一致
LEFT JOIN deploy_pinpoint_relation dpr
       ON dpr.dep_project = adr.deploy_project_name
WHERE ot.sync_date = (SELECT MAX(sync_date) FROM operation_topology)
  AND ot.env = 'PRO'
  AND ot.apollo_app_id = 'apollo-ehome-pro'   -- 按需替换为具体 appId
;
```

### 4.3 注意事项

1. **必须显式 `COLLATE utf8mb4_0900_ai_ci`**（**仅 SQL 诊断口径需要**）：`operation_topology` 的排序规则为 `utf8mb4_unicode_ci`，而 `app_dp_relation` / `deploy_pinpoint_relation` 为 `utf8mb4_0900_ai_ci`，跨表等值 JOIN 若不加 `COLLATE` 会报
   `ERROR 1267 (HY000): Illegal mix of collations (utf8mb4_0900_ai_ci,IMPLICIT) and (utf8mb4_unicode_ci,IMPLICIT) for operation '='`。
   `app_dp_relation × deploy_pinpoint_relation` 两表排序规则一致，无需处理。跳① 改为接口取数、跳② 走内存映射后，该冲突自然消失。
2. **诊断 SQL 的 `dpr` 侧一对多会放大结果行（仅诊断口径）**：
   - 同一 `(apollo_app_id, apollo_app_env)` 在 `app_dp_relation` 中最多 59 行（2026-09-17 实测，1426 行真实数据口径；全表共 198 个 `(appId, env)` 对存在多行，其中 86 组对应多个 `deploy_project_name`）；
   - 同一 `dep_project` 在 `deploy_pinpoint_relation` 中平均 2.84 行、最多 78 行（唯一键为 `(dep_project, pp_application)`）。
   故该 JOIN 的结果可能出现一个 OT 行对应多行。**程序折叠模式（`expandDepNode=0`）不按 DPR 行展开**：命中值只作为 appId 属性补充（多值聚合为列表），数据集行数与候选关系行数一致；展开模式（默认）按**部署点**（部署项目 × 节点）扩行，不等同于按 DPR 行扩行（见 4.5）。若在 SQL 侧需按应用去重，可在外层加 `DISTINCT` 或对 `dpr` 侧用 `GROUP BY`/子查询聚合。
3. **环境对齐（`AND adr.apollo_app_env = ot.env`）必须加，不是可选**：程序侧 `dpTargets()` 的索引键是 `appId|env`（`relationKeyOf`），只取与 `operation_topology.env` 同环境的 ADR 行；诊断 SQL 若不写该条件，会把其它环境的 ADR 行一并关联，口径**宽于**程序，进而放大 `depProjects` 等属性列表。
   - `operation_topology.env` 当前仅有 `PRO`；`app_dp_relation.apollo_app_env` 取值含 `PRO` / `SIT` / `DEV` / `LPT` / `LTP` / `PROBAK` / `UAT`。
   - 2026-09-18 实测（OT 最新 `sync_date`、`env='PRO'`，共 108 个 `(appId, env)` 对）：漏写该条件有 **32 个 appId 的 `depProjects` 被放大**；`engProjects` / `nodes` / `ppApplications` 三个维度**均无变化**（异环境多出的部署项目要么未命中 DPR，要么命中后落到同一 `eg_project`/`node`/`pp_application`）。
   - 放大示例：`ehome` 10 → 7、`ehome-api` 6 → 3、`ehome-public-push` 8 → 5、`ehome-ota` 18 → 17、`auth` / `detect` / `push` / `uni-order` 3 → 2、`bc-bp-message` 2 → 1。
   - `bc-bp-message`（OT `env=PRO`）最直观：ADR 有 2 行（`PRO → bc-platform-manage-dep`、`LPT → bc-platform-message-dep`），不加条件时 `depProjects` 为 2 个、加上后为 1 个（与接口一致）。
   - 本例 `vcp-openapi` 的 3 行 ADR（PRO×2 + LPT×1）恰好同部署项目，故加与不加结果相同（见 4.4.1），但这属巧合，不可据此省略。
4. **覆盖率以同步后的关系表为准**：2026-09-17 真实全量（1426 行）接入后实测，OT 侧（`sync_date=2026-09-17`、`env='PRO'`、1418 行）跳① 命中 **1305/1418 行（92.0%）**、**83/108 个 appId**，仍有 **25 个 appId 未命中**（上游暂无对应关系，属真实缺口）。补数交付与校验 SQL 见《[业务数据/运维关系拓扑图待补充数据说明.xlsx](业务数据/运维关系拓扑图待补充数据说明.xlsx)》，按其「说明」sheet 的校验 SQL-A 复跑即得当前填充率。

### 4.4 示例走查：`vcp-openapi` 属性多值来源（2026-09-18 实测）

| 6 | `tyyy-gz_vcp-openapi_Product_vcp-openapi-prod-145823-` | tyyy-guizhou |
| 7 | `vcp-openapi_Product` | tyyy-guizhou |

- 7 行的 `eg_project` 全为 `vcp-openapi`、`dep_project` 全为 `vcp-openapi-prod-145823-dep`，故 `engProjects` 去重后仍只有 1 个元素。

#### 4.4.3 聚合结果（`attachAppAttrs` + `dedupSorted`）

| 字段 | 值 | 个数 |
| --- | --- | --- |
| `depProjects` | `vcp-openapi-prod-145823-dep` | 1 |
| `engProjects` | `vcp-openapi` | 1 |
| `nodes` | guangzhou4d-prod、shipingyunwan、tyyy-guizhou、tyyy-guizhou3 | **4** |
| `ppApps` | `SPYW-vcp-openapi`、`SPYW_vcp-openapi_Product_…`、`guangzhou4d-prod_vcp-openapi_Product_…`、`tyyy-gz-vcp-openapi`、`tyyy-gz3-vcp-openapi`、`tyyy-gz_vcp-openapi_Product_…`、`vcp-openapi_Product` | **7** |

- 去重升序走 Go 的字节序（`sort.Strings`，大写在前）：`S(0x53) < g(0x67) < t(0x74) < v(0x76)`；`tyyy-gz` 之后 `-`(0x2D) < `3`(0x33) < `_`(0x5F)——接口返回顺序与之一致。

> ⚠️ 单值列 `node` / `ppApp` **不代表该应用实际所在机房 / PP 应用**，仅为兼容旧字段的「属性列表首值」，取值请以 `nodes` / `ppApps` 列表为准。

#### 4.4.4 多值的三个成因

1. **DPR 粒度天然一对多**：唯一键 `(dep_project, pp_application)`，一个部署项目对应多行（全表均值 2.84 行/部署项目、最多 78 行，见 4.3-2）。
2. **同一部署项目铺在多个机房**：本例 4 套 `node`（广州4d生产 / 视频云网 / 云眼-贵州 / 云眼-贵州3），每套机房一套 PP 应用。
3. **PP 应用存在两套命名形态，导致 PP 行数(7) > node 数(4)**：
   - 简称型：`SPYW-vcp-openapi`、`tyyy-gz-vcp-openapi`、`tyyy-gz3-vcp-openapi`、`vcp-openapi_Product`；
   - 全称拼装型：`{node}_{应用名}_Product_{dep_project}-`。
   
   故 shipingyunwan 有 #1+#2、tyyy-guizhou 有 #6+#7 两条，tyyy-guizhou3 的 #4/#5 前缀不同也算两条。

一句话：**属性多值 = 跳① 命中的部署项目在 DPR 中真实存在多行**，属数据语义的正常表现（前端「属性筛选」的维度内 OR 即为此设计）。

#### 4.4.5 用 SQL 直接还原接口的列表字段

```sql
-- 【聚合口径】按 appId 聚合，还原接口的 *列表* 字段
SELECT ot.apollo_app_id,
       GROUP_CONCAT(DISTINCT adr.deploy_project_name ORDER BY adr.deploy_project_name COLLATE utf8mb4_bin) AS dep_projects,
       GROUP_CONCAT(DISTINCT dpr.eg_project  ORDER BY dpr.eg_project  COLLATE utf8mb4_bin) AS eng_projects,
       GROUP_CONCAT(DISTINCT dpr.node        ORDER BY dpr.node        COLLATE utf8mb4_bin) AS nodes,
       GROUP_CONCAT(DISTINCT dpr.pp_application ORDER BY dpr.pp_application COLLATE utf8mb4_bin) AS pp_apps
FROM operation_topology ot
LEFT JOIN app_dp_relation adr
       ON adr.apollo_app_id = ot.apollo_app_id COLLATE utf8mb4_0900_ai_ci
      AND adr.del_flag = 0
      AND adr.apollo_app_env = ot.env            -- 环境对齐（不加会把 LPT/DEV 等一并关联）
LEFT JOIN deploy_pinpoint_relation dpr
       ON dpr.dep_project = adr.deploy_project_name
WHERE ot.sync_date = (SELECT MAX(sync_date) FROM operation_topology)
  AND ot.env = 'PRO'
  AND ot.apollo_app_id = 'vcp-openapi'
GROUP BY ot.apollo_app_id;
```

两个易踩的差异点：

1. **`COLLATE utf8mb4_bin`**：MySQL 默认 `*_ai_ci` 为**大小写不敏感**排序，会把 `guangzhou4d-prod_…` 排到 `SPYW-vcp-openapi` 之前，与接口（Go 字节序）顺序不一致；加 `BINARY` 才对齐。
2. **`adr.apollo_app_env = ot.env`（必须）**：不加该条件时其它环境的 ADR 行会一并 JOIN 进来，属性列表被放大。本例 `vcp-openapi` 因 3 行 ADR 同部署项目、结果不变；但同批数据中 108 个 `(appId, env)` 对里有 **32 个 appId 的 `depProjects` 会被放大**（如 `ehome` 10 → 7、`ehome-api` 6 → 3、`bc-bp-message` 2 → 1），详见 4.3-3。

#### 4.4.6 代码落点

| 环节 | 位置 |
| --- | --- |
| 跳①+跳② 内存关联 → `appId + env → []dpTarget` | `service/dp_relation.go` `joinDpTargets` |
| 属性收集 / 去重升序 / 单值取首值 | `service/dp_relation.go` `attachAppAttrs`、`dedupSorted`、`setFirst` |
| 跳② DPR 映射加载（DB 优先、镜像兜底、TTL 60s） | `service/pinpoint_relation.go` `pinpointMap` |
| DPR 表结构（唯一键 `(dep_project, pp_application)`） | `model/deploy_pinpoint_relation.go` |

### 4.5 部署点展开（默认）与折叠

「部署项目 + 节点」是应用节点的唯一条件：同一 appId 在不同部署项目 / 机房下是**不同的应用节点**。故读接口默认按**部署点**（deploy slot = 部署项目 × 节点）展开；需要合并为「一个 appId 一个节点」时才显式关闭。

**开关**：`expandDepNode`（`*bool`，`/graph`、`/list`、`/detail` 三入口通用）

| 入参 | 行为 |
| --- | --- |
| 不传（`nil`）/ `1` / `true` | **展开（默认）**：应用节点粒度 `appId + 部署项目 + 节点`，一个部署点一个节点，属性为单值 |
| `0` / `false` | **折叠**：应用节点粒度 `appId`，属性多值聚合为列表 |

> 用指针是「三态」的前提：`nil`（不传）必须能与显式 `false` 区分，否则无法「默认展开 + 可关闭」。

**两种口径对比**（2026-09-20 快照、`env=PRO` 实测）

| 指标 | 折叠（`expandDepNode=0`） | 展开（默认，不传 / `1`） |
| --- | --- | --- |
| 应用节点 | 108 | **240**（一个部署点一个节点） |
| 中间件节点 | 341 | 341 |
| 依赖边 | 756 | **2943** |
| `/list` `pageTotal` | 1418 | **5266** |

> 量级随每日快照与两跳回填结果变化；`graph` 的 `counts` / `list` 的 `pageTotal` 以接口返回为准，上表仅作口径比例参考。
> **⚠️ `node` / `engProject` 回填率极低（数据侧待协同，见 §5.1 #5/#6）**：`node` 只取自跳② DPR（`dp_relation.go` 的 `joinDpTargets`，DPR 未命中该部署项目时仅填 `DepProject`），而快照部署项目与 DPR 的 108 个部署项目几乎无交集 → 绝大多数应用节点 `node` 为空串、按 `node` 过滤返回空图；`operation_topology` 快照表自身的 `node` / `dep_project` 两列亦全为空。

- 展开示例：`vcp-openapi` 折叠时为 1 个节点，展开后为 4 个应用节点（1 个部署项目 × 4 套 `node`，见 4.4.2）。
- 应用节点 id：展开后形如 `app:{appId}|{部署项目}|{节点}`，折叠态为 `app:{appId}`。
- 展开只在查询期做、**不落库**：`operation_topology` 唯一索引 `uk_snapshot_relation = (sync_date, appid, host_id, env, type, addr)` 不含 `dep_project` / `node`，落库展开必撞唯一索引。
- 展开后 `dep_project` / `node` / `eng_project` 为单值，多值列 `depProjects` / `nodes` / `engProjects` 清空；`ppApplications` 仍为该部署点下的 PP 应用列表（DPR 唯一键 `(dep_project, pp_application)`，一个部署点天然多个 PP 应用）。

**筛选粒度随模式切换**：折叠态按 appId 的属性列表复核（`filterAttachRows`），展开态行本身已是部署点粒度、按单值列复核（`filterSlotRows`）——同一 appId 的其它部署点行会被剔除，与图节点粒度一致。

**详情 id 自适应**：应用节点 id 自带 2 个 `|`（`app:{appId}|{部署项目}|{节点}`）时后端一律按部署点定位，即使入参写 `expandDepNode=0`——保证「图节点 → 详情」两处口径一致。`mw:` / `host:` 节点 id 不含该信息，其「引用应用列表」粒度只能由入参决定，故前端应与 `/graph` 同值传入。

**代码落点**

| 环节 | 位置 |
| --- | --- |
| 开关判定（`nil` / `true` → 展开） | `service/operation_topology.go` `expandDepNodeOn` |
| 节点合并键 / 图节点 id 后缀 | `service/operation_topology.go` `appKeyOf(r, expandDepNode)` |
| 部署点聚合（按 `(部署项目, 节点)` 去重） | `service/dp_relation.go` `dpSlot` / `deploySlots` |
| 按部署点扩行 | `service/dp_relation.go` `expandByDeploySlot` |
| 部署点粒度筛选复核 | `service/dp_relation.go` `filterSlotRows` |

> 展开模式仍保留 appId 前缀：实测有 6 个部署项目被两个 appId 共用（如 `bms-member-service-dep` 同属 `bms-market-service` 与 `bms-member-service`），纯「部署项目 \| 节点」会把两个不同应用错并成一个节点。

## 5. 实施结论（2026-09-16 已落地）

> 本节原为「接口 vs 落库 / 缓存与降级 / 待确认事项 / 分期实施」的方案评估（2026-09-15），现已全部实施，收敛为结论。

| 议题 | 结论 |
| --- | --- |
| 跳① 取数 | **采集期落库**：cron / 手动 `/sync` 调关系接口一次拉全量（`paginator=false` + `pageSize=-1`）→ 与库内数据比对，**有变化才整表替换落库** `app_dp_relation` + 回写本地镜像（无变化跳过替换）；查询期只读「库 → 镜像」，接口仅在前两者均无数据时兜底 |
| 跳② 取数 | **维持本地表**：DPR 无上游接口，整表加载进内存映射（`pinpointMap`，TTL 60s，DB 优先、文件兜底） |
| 缓存 | `dpTargets()` TTL 60s（`relation_api_ttl`）；采集期落库后 `invalidateRelationIndex()` 立即失效，避免「库已更新、内存仍旧值」 |
| 分页 | **先取全量候选、属性补充后再复核分页**：读接口一律先取全量候选 → `attachAppAttrs` 属性补充（多值聚合为列表，不扩行）→ 复核 → 再分页/聚合，`total` = 候选关系行数（折叠口径 1418 / 默认展开 5266，见 §4.5） |
| 行数口径 | **折叠口径**（`expandDepNode=0`）下，两跳关联只做 appId **属性补充**，**不按 DPR 行展开、不放大行数**；**默认展开口径**下按**部署点**（部署项目 × 节点）扩行（`/list` `pageTotal` = 5266、应用节点 108 → 240，见 §4.5），仍**不等同于按 DPR 行扩行**。跳② 一对一只体现为属性列表的元素个数（单 `dep_project` 在 DPR 中平均 **2.84 行**、最多 **78 行**，故折叠态属性列表可达数十个值），前端渲染按列表字段处理 |
| 可观测 | 日志标识 `[dp_relation]` / `[pinpoint]` / `[datastore]` / `[operation_topology]`；`/sync` 结果含跳① 关系同步明细 |
| 报错口径 | 跳① 异常（上游拉取失败 / 关系表缺失 / 写库失败）在 `/sync` 结果与日志总览**显式报错**（`relationErr=true`、文案前缀 `【异常】`），不阻断主表同步；接口未启用 / 0 行 / 无 DB 连接属**正常降级**（走镜像兜底），不报错 |

> 落地实现、端到端验证与降级验证的完整日志见《[../logs/README.md](../logs/README.md)》。
