## 一、部署实施

适用场景：将主项目 `devops-automation`（Gin 后端，单进程，含 Apolo 配置中心采集与"实例→应用→中间件"拓扑模块）整体部署到生产服务器；或在已有主项目环境中首次启用拓扑模块。

> **数据载体 = MySQL（DB 优先）+ 本地文件镜像**：拓扑三表中，主表 `operation_topology` 与跳① `app_dp_relation` **由启动时 AutoMigrate 自动建表**（表已存在时只补缺失列/索引，不重建、不删列），跳② `deploy_pinpoint_relation` **不纳入 AutoMigrate**，需事先由运维执行 [业务数据/deploy_pinpoint_relation.sql](业务数据/deploy_pinpoint_relation.sql) 自建/导入。DB 未注入/不可用时读接口自动回退本地快照文件 `api/tprel/data/*.json`，**DB 缺失不阻断拓扑查询**（仅降级）。

### 2. 前置准备

- 服务器：Linux x86_64（部署机），内存/磁盘按现网主项目规格；时区 `Asia/Shanghai`（cron 01:30 按服务器本地时间）
- 编译机：Go 1.24+（[go.mod](../../../go.mod#L3)，与部署机可分离）
- 中间件：MySQL 为拓扑模块降级兜底（可用则 DB 优先）。**拓扑主表 `operation_topology` 与跳① `app_dp_relation` 由程序启动时 AutoMigrate 自动创建（表已存在只补缺失列/索引），DPR 维表 `deploy_pinpoint_relation` 不纳入 AutoMigrate、需运维预先按 `业务数据/deploy_pinpoint_relation.sql` 自建/导入**；若因 DB 权限导致建表失败，跳① 同步会在 `/sync` 结果与日志中显式报错（`relationErr=true`），主表同步不受影响
- 网络：服务器可访问 EasyOps 代理（`apollo.base_url`）的出方向 HTTPS
- 运行目录可写：日志 `logs/` 与快照目录 `api/tprel/data/` 需可写
- 静态资源：前端页面目录 `api/tprel/prototype/`（部署时随包或复制到 nginx）

### 3. 数据载体说明（MySQL 优先 + 本地文件镜像）

> 拓扑数据三表落 MySQL：主表 `operation_topology` + 跳① `app_dp_relation` 由启动 AutoMigrate 自动创建；跳② `deploy_pinpoint_relation` 不纳入 AutoMigrate，由运维按 §3.3 的 DDL 自建/导入。
> 每次同步同时回写本地文件镜像 `api/tprel/data/*.json`；读接口 `datastore.mode=auto` 时 DB 优先、不可用回退文件。下表为行级结构说明（表列与文件字段一致）。

#### 3.1 快照文件结构

单 JSON 文件，内容 = 「某 Apollo 实例下某应用 → 其中间件」一条关系（行级字段与下表一致），按 `data:{sync_date:{env:[行…]}}` 分桶：

```json
{ "version": 1, "exportedAt": "2026-09-07 12:32:28", "totalRows": 3816,
  "data": { "2026-09-07": { "PRO": [ { "id":1, "apolloHostId":13, "...": "全字段" } ] } } }
```

- 文件保留多个 `sync_date` 历史桶（对比/回滚用）；同 `sync_date` 重复同步**整批成功才原子替换**（tmp 写入 + rename，不会写坏文件）——partial（部分完成）且本地已有可用旧快照（更早日期桶或当日已有行）时**保留旧快照不覆盖**，仅从未有过任何可用快照时才先落部分数据
- 行序即写入序（等价 DB id asc）；文件加载后常驻内存、按日期/环境分桶，查询只扫内存行
- 每次同步结束后自动刷新；读接口无需重启即读到最新数据

#### 3.3 数据库版说明（已启用）

- 主表/结构/唯一索引 `uk_snapshot_relation(sync_date, apollo_app_id, apollo_host_id, env, middleware_type, connect_addr)` 已在 [model/operation_topology.go](../model/operation_topology.go) 的 `uniqueIndex` tag 中声明，启动 AutoMigrate 自动建表
- 跳① `app_dp_relation` **与主表一致纳入 AutoMigrate**（[initialize/gorm.go](../../../initialize/gorm.go) 的 `MysqlTables` 只注册 `operation_topology` + `app_dp_relation`），启动即自动建表；**跳② `deploy_pinpoint_relation` 不纳入 AutoMigrate**，需运维按《[运维拓扑.md](运维拓扑.md)》§2 的 DDL（[业务数据/deploy_pinpoint_relation.sql](业务数据/deploy_pinpoint_relation.sql)）自建/导入

### 4. 配置准备

#### 4.1 配置加载与优先级

`-c <path>` > 环境变量 `GVA_CONFIG` > 默认 `./config.yaml`（程序运行目录，[core/viper.go L14-40](../../../core/viper.go#L14-L40)）。部署时将生产配置命名为 `config.yaml` 放运行目录（或 `GVA_CONFIG=/data/app/config.yaml`）。

- `system.use-multipoint`：`true` 时启动会初始化 Redis/ES（主项目其它功能需要）；新环境只验证拓扑可先 `false`
- **`apollo` 段整段可省**：配置加载后（[core/viper.go](../../../core/viper.go)）会调用 `config.Apollo.Effective()` 补全代码内建的生产默认值（`base_url` / `session_id` / `relation_api_path`，以及 `sync_enable` / `insecure_verify` / `relation_api_enable` 缺省=true），因此部署配置不写 apollo 段也能直接按真实接口采集
- `redis/zap/kafka/elasticsearch/difyAI/cmdbProxy` 等其它段：沿用现网 config.yaml
- 日志落在 `logs/YYYY-MM-DD.log`（按 zap.director），请确保运行目录可写

#### 4.2 完整配置模板（与拓扑强相关的段）

#### 4.2.1 数据源路由说明（读接口取数语义）

拓扑读接口（list/graph/detail/middlewareTypes）统一经模块内数据源路由（[service/datastore.go](../service/datastore.go)），`mode=auto`：**DB 优先，不可用回退本地文件镜像**。

- **读（DB）**：主表 `operation_topology` 按 `syncDate/env` 过滤取行；跳① `app_dp_relation`、跳② `deploy_pinpoint_relation` 用于查询期两跳关联，作为 appId 属性补充四列（`node/eng_project/dep_project/pp_application`，单值取列表首值 + `nodes`/`engProjects`/`depProjects`/`ppApplications` 多值列表，不扩行）。
- **读（文件降级）**：DB 未注入或查询失败时回退 `api/tprel/data/*.json`；文件加载后常驻内存并按日期/环境分桶，`syncDate` 缺省取最新快照日期；`/list` 内存分页、`/graph`/`detail` 全量聚合；无文件/无数据 → 返回空列表（不报错）。
- **写**：`POST /sync`（**异步提交**，后台采集）采集期间查询仍读**旧版**数据（内存加载后不可变，结束时刻一次性切换）；**整批成功才原子替换**当日快照（DB 走事务内 `DELETE + 批量 INSERT`，文件走 tmp + rename），数据始终完整；partial=true 且已有可用旧数据时**不落盘、保留旧版**（结果提示“已保留现有快照 {date} N 条，本次未覆盖”），仅从未有过任何可用数据时才先落部分；空产物保留当日已有数据。
- **跳① 关系同步（前置阶段）**：接口一次拉全量（`paginator=false` + `pageSize=-1`）→ 与库内现有行比对，**有变化才整表替换落库** `app_dp_relation`（无变化跳过替换，不删不写）+ 回写文件镜像 → 失效内存索引；未启用/拉取 0 行属**正常降级**（保留上一版），拉取失败/表缺失/写库失败属**异常**（`relationErr=true`，日志前缀 `【异常】`），不阻断主表同步。详见《拓扑查询总体逻辑.md》§2.4。
- **性能要点**：数据常驻内存、只保留各 `sync_date` 桶合计可控；列表分页单趟窗口收集（只留当前页，避免整批拷贝）。
- **data 目录建议**：已加入 .gitignore（镜像文件随同步变化，不应进版本库）；首次同步后即生成，无需人工放置文件。

### 6. 数据初始化与接口调用

#### 6.1 首次同步

生产启动**不会**自动采集（本地测试服务的"启动自检"不属于生产）。两种方式：

1. 手动触发（推荐用于首验）：`POST /sync` 为**异步提交**（立即返回，采集在后台执行），随后轮询 `/sync/status` 直到 `running=false` 且 `result` 非空即完成：
   ```bash
   # 提交（鉴权头字段名为 token（JWTAuth 读取），值为 JWT 原文，无 Bearer 前缀）
   curl -X POST http://127.0.0.1:8867/api/external/operationTopology/sync \
        -H "token: <jwt>"
   # 轮询状态直至 running=false（stageText/percent 可看进度，如 "正在扫描配置 456/1077"）
   curl -s http://127.0.0.1:8867/api/external/operationTopology/sync/status \
        -H "token: <jwt>"
   ```
   > 轮询建议间隔 **3~5 秒**：`/sync/status` 与其它 `/api/external` 接口一样，每次请求都会在 `sys_operation_record` 写一行操作日志，秒级高频轮询会持续增加日志表写入。
2. 等每天凌晨 01:30 定时自动执行（受 `apollo.sync_enable` 控制）

#### 6.2 鉴权说明

生产 `/api/external` 组挂 JWT 鉴权（[initialize/router.go L75](../../../initialize/router.go#L75)），拓扑接口与主项目其它 external 接口一致。鉴权头字段名为 **`token`**（[middleware/jwt.go L20](../../../middleware/jwt.go#L20) 读取），值为 JWT 原文、**不带 `Bearer ` 前缀**；token 由现网既有登录接口签发，缺失/失效/过期时 **HTTP 状态码仍为 200**，鉴权失败体现在 body 的 `code`：`{"code":401,"data":{"reload":true},"msg":"未登录或非法访问"}`（后端统一 `c.JSON(http.StatusOK, ...)`，**勿按 HTTP 状态码判断**）。

#### 6.3 接口清单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/external/operationTopology/list | 关系列表（支持 syncDate/env/middlewareType/apolloAppId/appDept/appOwner/apolloAppName 等） |
| GET | /api/external/operationTopology/graph | 拓扑图（实例/应用/中间件节点+边，一次返回全量，供主视图渲染；响应含 `counts` 规模汇总字段，与过滤一致、无数据全 0） |
| GET | /api/external/operationTopology/detail | 节点详情（点击图节点后详情面板拉取；id 与 graph 节点 id 一致） |
| POST | /api/external/operationTopology/sync | 手动同步（**异步提交**：立即返回，采集后台执行；同日幂等覆盖） |
| GET | /api/external/operationTopology/sync/status | 同步任务状态/进度/结果（提交后轮询至 `running=false`；含 `stageText`/`percent` 进度与 `stats` 规模统计） |
| GET | /api/external/operationTopology/sync/logs | 最近同步日志在线读取（`date=YYYY-MM-DD` 可选，缺省自动选最近一天有日志的文件；`download=1` 以附件下载完整日志 text/plain，不返回 JSON） |
| GET | /api/external/operationTopology/middlewareTypes | 中间件类型列表（筛选下拉数据源） |

#### 6.4 主进程定时任务完整清单（唯一 cron 中枢）

项目的 robfig/cron 调度器只有一处：[core/server.go L38-51](../../../core/server.go#L38-L51)（`cron.New()`）。下面 7 项均注册在该实例，不另设调度器；各模块的 `cronTask/` 只是被调用的业务实现（如 tprel 任务带 `apollo.sync_enable` 开关）。

| 表达式 | 时间（服务器本地） | 任务 | 功能 / 开关 |
| --- | --- | --- | --- |
| 0 0 * * * ? | 每天 00:00 | service.InitProvinceGet | 省区数据/缓存刷新（启动时预热一次） |
| 0 0 * * * ? | 每天 00:00 | cronTask.InitAgentDetail | agent 详情缓存初始化（启动时预热一次） |
| 0 0 */5 * * ? | 每 5 小时 0 分 | cronTask.FetchAndCacheUserInfoFromOss | 从 OSS 拉取用户信息并刷新缓存 |
| 0 0 0 */1 * * ? | 每天 00:00:00 | serviceMeeting.GetUser | 会晤用户数据同步 |
| **0 30 1 * * * ?** | **每天 01:30** | **tprelCronTask.SyncOperationTopology** | **运维关系拓扑每日同步；受 `apollo.sync_enable` 控制** |
| 0 0 12 * * ? | 每天 12:00 | PrintGoroutinesToFile | goroutine 堆栈 dump 到 goroutines.log（诊断用） |
| 0 */1 * * * ? | 每分钟 | AlarmSave(true) | 告警轮询保存 |

补充说明：

- **`apollo.sync_enable` 必须显式写 `true`**：cronTask 到点先判断该开关，`false` 则跳过并只记一条日志；config.yaml 不写该字段时零值为 `false`（生产配置模板见 §4.2）。
- **上游必须可用**：EasyOps 代理可达、`session_id` 在白名单内；否则到点会执行但同步失败（日志记录原因）。
- **首次上线当天无数据**：执行时间为每天凌晨 01:30（服务器本地时区，建议 Asia/Shanghai）；当天部署时若 01:30 已过，需等次日或当天先手动 `POST /sync` 拿数据（见 §6.1）。
- **错过不补跑**：01:30 那一刻进程未运行（重启/停机）不会补跑，需等次日或手动触发。
- **多副本部署只允许一台跑**：cron 为进程内注册，多实例并发执行同日快照会整桶替换互相冲突（互斥锁 `syncMu` 仅对本进程有效）；多副本时仅一台配置 `sync_enable: true`。
- 启动即执行的**非定时**初始化（与上述同源、易误认为"另一套定时"）：`initialize.KafkaConsumer()`（[server.go L34](../../../core/server.go#L34)，Kafka 消息消费长驻 goroutine，消息驱动而非定时）；`cache.CacheAllUser(...)`（Redis 用户缓存预热）
- 表达式为 6 段 robfig 格式（秒 分 时 日 月 周）；以上时间均为服务器本地时区
- 若要调整拓扑同步时间，需改 [core/server.go L43](../../../core/server.go#L43)（`config.sync_cron` 仅作展示），其余任务同理在 [server.go L38-51](../../../core/server.go#L38-L51) 内修改

#### 6.5 提供给前端对接的最小信息

### 8. 首日验证清单

日志（`logs/YYYY-MM-DD.log` / `api/tprel/logs/YYYY-MM-DD.log`）：

> 拓扑同步日志由 tplog 按天落盘 `YYYY-MM-DD.log`，缺省目录 `api/tprel/logs`（可用环境变量 `TPREL_LOG_DIR` 覆盖），一天多次同步累积在同一文件。除直接查看文件外，也可通过 `GET /sync/logs` 在线查看/下载最近同步日志（接口与写日志同目录：`date=YYYY-MM-DD` 可选、缺省自动选最近一天，运维可用 `download=1` 拉取完整文件归档排障，接口清单见 §6.3）。

- `同步开始`（triggerBy=cron/手动）→ 逐套探活 → `解析摘要`（hosts/apps/tasks/items）→ `快照落盘`（整批成功 = “已原子替换本地快照（同步期间旧版数据保持可查）”；部分完成/无产物且已有旧快照 = 保留现有快照并提示“已保留现有快照 {date} N 条，本次未覆盖”）→ `同步完成`（rows / new / lost / 耗时）
- 同步链路另有三段“本次同步 ·”整段清单日志：`本次同步 · 实例清单（接口1 查套+探活）`、`本次同步 · 应用清单（接口2 拉应用+组装任务）`、`本次同步 · 入库中间件清单（类型+地址 去重）`，分别逐实例 / 逐 appId / 逐“类型+地址”明示本次入库内容

文件校验（快照 JSON，可并行对比接口响应）：

```bash
python3 - <<'PY'
import json, collections
d = json.load(open('api/tprel/data/operation_topology.json'))
rows = [r for rs in d['data'].values() for env in rs.values() for r in env]
print('totalRows 文件头:', d['totalRows'], '实际:', len(rows))            # 应相等且非 0
dup = [k for k, n in collections.Counter(
    (r['syncDate'], r['apolloAppId'], r['apolloHostId'], r['env'], r['middlewareType'], r['connectAddr'])
    for r in rows).items() if n > 1]
print('重复关系数(应为 0):', len(dup))
# node/engProject/depProject 三列为预留空值，快照内应为空（由查询期两跳关联作为 appId 属性补充，不写回快照）
print('三列非空(应为 0):', sum(1 for r in rows if r.get('node') or r.get('engProject') or r.get('depProject')))
# ppApplication 采集期写入占位值（appid_owner_map 命中值，否则回退 app.Name），故应全部非空
print('ppApplication 空(应为 0):', sum(1 for r in rows if not r.get('ppApplication')))
print('hostAddr 空:', sum(1 for r in rows if not r['apolloHostAddr']))
PY
```

接口：graph 应用节点 id=`app:{apollo_app_id}`、list 过滤生效、重复 sync 行数不变。

### 9. 回滚与常见问题

| 现象 | 处理 |
| --- | --- |
| 定时到点不采数 | 检查 `sync_enable=true`、`session_id` 是否有效、上游是否可达（日志有探活/错误原因） |
| 鉴权失败（**HTTP 200** + body `code:401`） | JWT 缺失/过期，需带合法 token（请求头 `token: <jwt>`，无 Bearer 前缀）；后端统一返回 HTTP 200，须判断 body 的 `code` |
| 上游 https 证书报错 | `insecure_verify: true` |
| 采集拉不动/超时 | 调小 `scan_namespaces`/`max_ns_per_app`，或调大 `scan_budget_sec`/`workers` |
| 需紧急停采 | `sync_enable:false` 重启；查询接口与存量数据不受影响 |
| 数据修正 | `POST /sync`（异步提交）触发重建当日快照，轮询 `/sync/status` 至完成（**整批成功才原子替换**，幂等）；partial 保留场景下保留旧快照不覆盖；历史日期桶保留在文件内 |

## 三、同步接口优化评估与接口申请单

> 版本：v1.0（2026-09-09）
> 范围：`api/tprel` 的 Apollo 配置同步（`POST /sync` + `/sync/status` 轮询）——阶段3「并发抓取解析」
> 目的：解决“固定 namespace 名单逐个猜测查询”导致的低效（请求量大、预算内跑不完、漏扫自定义 ns），评估“一次取全量/先枚举再定向查”等方案并给出实施路径与网关接口申请单。

---

### 13. 背景与问题（基于生产日志实测）

#### 13.1 现网同步数据（2026-09-09 生产批次）

| 项 | 值 | 说明 |
|---|---|---|
| 套规模 | hosts=13（可用 8 / 不可用 5） | 探活后仅对可用套抓取 |
| 应用规模 | apps=734 | 任务组装后确定 |
| 计划任务 | tasks=10276 | = 应用 × 固定 14 个 namespace × env(PRO) |
| 实际请求 | 2556 / 10276（25%） | 预算截断 |
| 未执行任务 | 7720 | 预算内未轮到 |
| 单请求耗时 | avg≈187ms / max≈298~543ms | 网关链路耗时为主 |
| 同步耗时 | ≈66.5s | 预算截断 → partial=true |
| 落盘关系 | 414 条（new=414 / lost=0） | 疑似覆盖不足 |

#### 13.2 扫描窗口日志切片（11:17:06→11:17:36，30 秒）

- 共 2842 行，其中 **2407 行（85%）是 `404 namespace not found`**（ERROR「请求失败」1203 + WARN「扫描失败」1204 双行）；
- 有效请求仅 **93** 个（对应 93 条「解析摘要」，多为 `application` namespace）；
- 即 30s 内 ~93% 的请求都打在“不存在的 namespace”上，属于**设计性浪费**，非故障（无 5xx/超时）。

> 注：该现象对应老版本（404 双行 ERROR/WARN、且 404 被误计“未完成应用”）。新代码已做 404 降噪（哨兵 `errHTTP404`：不刷 ERROR、不重试、不计未完成应用），但**无效请求仍消耗预算与耗时**，属于本轮要解决的核心问题。

#### 13.3 根因

1. **猜测式固定名单**：任务 = 应用 × 固定 14 个 namespace 名逐个查询（`application/datasource/redis/logging/common/rocketmq/kafka/mq/elasticsearch/mongodb/mysql/cache/config/middleware`）。多数应用只存在 `application`（+少量自定义 ns），其余 13 个必然 404；
2. **上游缺少“枚举”能力**：网关只暴露 3 个采集接口（getApolloHostInfo / apps / namespace 单查），无法先获知“某应用真实存在哪些 namespace”，只能猜；
3. **预算 < 全量耗时**：10276 × 187ms ÷ 8 ≈ 240s >> 当前预算（60s）→ 每次必然 partial；
4. **覆盖缺陷**：固定名单会漏扫各团队**自定义 namespace**（名称不在名单内），这部分配置（可能含大量中间件）当前**永远采集不到**——414 条关系存在低估。

### 14. 目标与约束

- **目标**：① 减少无效请求（404 归零或近零）；② 单批在预算内可整批完成；③ 补全自定义 namespace，提升拓扑覆盖率。
- **约束（不可破坏）**：
  - 关系行保留 `namespace` 溯源（[model L39](../model/operation_topology.go#L39)）与 `configKey` 溯源；
  - 新能力不可用时**回退现有固定名单**（可扫性不降级）；
  - 全程单实例互斥、同步期间查询读旧版、整批成功才原子替换的既有语义不变。

### 15. 候选方案对比

| 方案 | 做法 | 请求量(生产) | 整批耗时(8并发) | 404 | 自定义 ns | 上游依赖 | 风险 |
|---|---|---|---|---|---|---|---|
| **0 现状** | 固定 14 ns 逐个猜 | ~10276（有效仅 ~800） | ~240s（预算 60s 只能跑 25%） | 高（~90%） | 漏 | 无 | 每次 partial、覆盖不足 |
| **A 短期收窄名单+调参** | `scan_namespaces` 配高命中子集，预算/并发调大 | ~6600（8 ns 名单） | ~150s（300s 预算可完成） | 仍多 | 仍漏 | 无 | 治标 |
| **B 枚举→定向查（推荐·治本）** | 先 1 次枚举“该 app 的 namespace”，只对存在的 ns 建任务 | **~1600**（734 枚举 + ~900 定向） | **~35s**（60s 内整批完成） | ≈0 | **全覆盖** | **新增 1 个枚举接口** | 低；枚举失败回退固定名单 |
| **C 一次全量导出** | 一次返回该 app 全部配置（须按 ns 归属返回） | ~734 | 依赖响应体 | 0 | 全覆盖 | 新增全量导出接口 | 高：单响应体大易超时；无 ns 归属丢溯源 |

#### 15.1 方案说明

**方案 A：短期收窄名单 + 调大预算/并发**
- 依据生产 `typeStats`（rocketmq 222 / mysql 89 / redis 55 / kafka 30 / nacos 10 / es 8）挑选“application + 高命中中间件 ns”作为 `scan_namespaces`；
- 把 `scan_budget_sec` 提到 300、`workers` 提到 16；
- 优点：当天可生效、零代码、零依赖；缺点：仍无法覆盖名单外自定义 ns。

**方案 B：枚举 → 定向查（推荐主方案）**
- 任务组装前，每个应用先发 1 次枚举请求拿到“真实存在的 namespace 集合”，只对存在项（∪{application} 兜底）建扫描任务；
- 请求量从 10276 → 约 1600，降 ~85%；404 → ≈0；**自定义 ns 全覆盖**；
- 本地改造见 §4；需网关新增 1 个只读枚举接口（申请单见 §6）。

**方案 C：一次全量导出**
- 若网关提供“单应用全量配置导出”且**按 namespace 分组返回**，则请求量最小（~734）；
- 风险：单应用可达数千 items 的大 JSON，网关超时/体积限制风险高；若不分组返回将丢失 `namespace` 溯源，与约束冲突。本期不建议，等 B 稳定后视网关能力再评估。

**方案 D：自学习名单（无新接口的过渡）**
- 每次同步后记录“（套, 应用）命中过的 ns 集合”，下次只扫命中集合 + application；
- 适合暂时无法申请接口时的增量优化；首轮仍需全猜一次，多 env/多套场景收敛收益大（单 PRO env 收益有限）。

> ✅ **已落地（2026-09-09，D + A 组合，零上游依赖）**：
> - **D 学习定向**：新增配置 `ns_learn_enable`（缺省 true，false=退回固定名单猜测）、`ns_guess_days`（周期全名单兜底重猜，防新增/改名 ns 漂移）；学习键 `hostId|env|appId`，批末合并（200 命中 ∪ 旧集 − 404）+ 刷新 `lastGuessAt`，状态独立落盘 `data/operation_topology_learned.json`（tmp+rename 原子写、读取失败按空集继续）。收敛后请求量 ≈ 真实存在的 ns 集合，404 归零。实现：代码 [service/ns_learn_store.go](../service/ns_learn_store.go) + [service/operation_topology.go](../service/operation_topology.go)（planNs/命中登记/中间件缺失 Warn），行为与日志观测详见《接口逻辑说明.md》§14。
> - **A 名单收窄+调参**：本地/测试配置已收窄为 3 个高命中 ns（application/datasource/redis）并 `max_ns_per_app=3`，生产可按需同法调整。
> - 观测：`/sync/status` 结果与日志输出 `nsTargeted`（定向）/`nsBootstrap`（首扫）/`nsRecheck`（兜底重猜）三元组计数。

#### 20.1 /sync/status result 新增字段

| 字段 | 类型 | 说明 |
|---|---|---|
| noMiddlewareCount | int | 本次“无中间件应用”数（口径见下） |
| noMiddlewareApps | [{appId, appName}] | 无中间件应用清单，按 appId 升序 |

#### 20.2 新增 GET /sync/logs（读日志接口）

- 作用：在线查看/下载最近同步日志。日志由 tplog 按天落盘 `YYYY-MM-DD.log`，缺省目录 `api/tprel/logs`（可用环境变量 `TPREL_LOG_DIR` 覆盖），一天多次同步累积在同一文件；接口与写日志同目录。
- 参数：`date`（可选 `YYYY-MM-DD`，缺省自动选最近一天有日志的文件）；`download`（可选 `"1"`/`"true"` → 以附件下载完整日志 text/plain，不返回 JSON）。
- 展示 JSON `data` 字段：`date` / `file` / `sizeBytes` / `content`（仅最近 256KB，超长 `truncated=true`）/ `files`（[{date,file,sizeBytes}] 日期倒序最多 30 条）。
- 错误：date 非法 → code7“date 参数格式非法（应为 YYYY-MM-DD）”；无该日期 → “该日期无同步日志: YYYY-MM-DD”；目录为空 → “暂无同步日志（日志目录为空）”；双重防目录穿越。
- 调用：`curl "http://{IP:端口}/api/external/operationTopology/sync/logs"`；`?date=YYYY-MM-DD`；下载 `curl -OJ "...?download=1"`（需带既有鉴权头，与其它接口一致）。
- **作为新增请求项**：方法 GET，路径 `operationTopology/sync/logs`，读日志类，无写操作；对外若经网关/反代转发 `/api/external`（nginx 反代示例见本文档 §7），需在网关/反代侧放行并登记该路径。

#### 20.3 日志块与结果总览体现

- 无中间件应用数量 > 0 时，日志打印“本次同步 · 无中间件应用清单（已扫描未发现中间件关系）共 N 个（不含未完成/未执行应用）”，逐行列出应用；
- 日志末尾“本次同步 · 结果总览”新增一行“无中间件应用 N 个（…）：appId1（名1）, …”。
