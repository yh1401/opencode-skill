## 0. 结论速览

| 结论 | 说明 |
|---|---|
| 四个服务不是同一种"数据源" | Pinpoint = **调用链/服务地图**；Prometheus = **时序指标+告警**；CMDB = **资产台账**；ES = **日志检索**。它们通过"主机/应用"两个维度缝合成一条证据链。 |
| 平台的唯一入口是统一接入网关 | 所有调用都走 `internal/mcp.Gateway`（白名单/黑名单 + 超时 + 探针 + `tool_call_log` 审计），业务模块不直连服务。 |
| 返回形态三态并存 | 标准 上游返回信封、裸业务 JSON、`content[0].text` 里再套一层 JSON 字符串。平台用 `mcp.ResultOf` / `ContentJSON` 统一归一。 |
| 真正的关联主键只有 4 个 | `applicationName/appId`（应用）、`ip/hostName`（主机）、`instance="IP:port"`（Prometheus 序列）、`traceId`（单次调用）。ES 没有固定业务主键，靠字段约定。 |
| 平台当前消费了 15 个工具 | 四个服务合计 68 个工具，平台实际用到 15 个（Pinpoint 4 / Prometheus 7 / CMDB 1 / ES 3，详见 §8 矩阵与 §9 字段契约）；其余属于"能力已具备、平台未编排"。 |
| 最大缺口是"对齐口径" | 时间戳单位（秒/毫秒/RFC3339）、分页口径（page/size vs limit/offset）、主机标识（IP vs hostName vs node）、Pinpoint 应用名与平台 appId 的映射。 |

### 0.1 标记约定：**★【故障发现】** = 第一步发现问题所用的工具

本文件在 §3.1 / §4.1 / §5.1 / §6.1 的工具介绍列，用 **★【故障发现】** 标出**平台第一步排障 / 发现故障**的入口工具。判据只有一条：**能在无人工介入的情况下，自己产生一个新的问题信号**。

| 发现信号 | 工具 | 判据 | 所在章节 |
|---|---|---|---|
| 告警触发（被动，最快） | `list_alerts` | `state=firing` 且 `severity` 达阈值且未被抑制 | §4.1 告警与规则 |
| 实例不存活 | `query`（`up`） | `up==0`（同主机多条序列取任一为 0） | §4.1 查询类 |
| 资源指标越界 | `host_metrics_realtime` | CPU / 内存 / 磁盘 / TCP 连接数超阈值 | §4.1 主机类 |
| 错误日志激增 | `search` | 时间窗内 `level=error` 计数超基线（前置 `list_indices`） | §6.1 |
| 调用边异常 | `get_server_map_tool` | 边上的错误数、响应时间超阈值 | §3.1 应用/服务地图 |
| 资产缺失或账实不一致 | `cmdb_server_query` | 有监控无资产、有资产无监控 | §5.1 |

共 **6 个**。其余 62 个工具不产生新信号，作用分别是：**定位下钻**（如 `get_transaction_trace_tool`）、**判因**（如 `targets_metadata`、`get_shards`）、**自检**（如 `healthy`、`build_info`）、**治理**（如 `build_app_mapping_tool`）、**禁用**（写操作 5 个）。

> 注意：`list_indices` 是 `search` 的前置索引发现，本身不判定好坏，因此不标记为故障发现；`search` 命中数异常才构成信号。

### 0.2 五步排障流程：每步用什么工具、怎么验证

> 五步是**串行门禁**：每步都有准入条件和降级分支，不满足时回退或降级，禁止跳步直接下结论。
> 表中 `已接` = 平台当前已编排（共 15 个，其中排障链路 12 步、巡检/告警/稽核共用其余）；`未接` = 能力已注册但需按《实施计划》L 系列任务补齐。
> 工具的参数与返回见 §3.1 / §4.1 / §5.1 / §6.1；字段级契约见 §9。

#### 0.2.1 总览

| 步骤 | 核心问题 | 产出物 | 引用工具数 | 其中已接 |
|---|---|---|---|---|
| 1 发现 Detection | 有没有出问题？ | 原始信号 | 6 | 6 |
| 2 确认与定界 Triage | 是真故障吗？归谁？波及多大？ | 确认后的问题单 | 12 | 6 |
| 3 定位 Localization | 断在哪条链、哪个节点？ | 故障点 + 传播路径 | 9 | 2 |
| 4 取证 Evidence | 多严重？从什么时候开始？ | 指标 / 日志 / trace 证据集 | 10 | 6 |
| 5 定因 Root Cause | 为什么发生？如何排除其它可能？ | 根因结论 + 处置建议 | 11 | 1 |

> 引用数含跨步复用（`cmdb_server_query`、`get_server_map_tool`、`query`、`search`、`list_alerts`、`get_transaction_trace_tool`、`analyze_link_topology_tool`），去重后共覆盖 **40 个工具**。

#### 0.2.2 第 1 步：发现（Detection）

判据只有一条：**能在无人工介入的情况下产生新信号**。6 个工具见 §0.1，此处补充「信号形态 + 平台判据」。

| 工具 | 原始信号长什么样 | 平台判据 | 现状 |
|---|---|---|---|
| `list_alerts` | `{Labels:{alertname,instance,severity}, State:"firing", Value:"1"}` | `State=firing` 且 `severity` 达阈值且未被抑制；按 `alertname+instance+severity` 去重 | 已接 |
| `query` | `{instance="IP:9100"} => 0 @[ts]` | 同一主机任一序列 `up==0` 即判不存活；全序列缺失则转第 2 步验真 | 已接 |
| `host_metrics_realtime` | 结构化的 CPU / 内存 / 磁盘 / TCP 数值 | 任一指标越过阈值即 `RISK`；无返回即 `NO_DATA`（不可当健康） | 已接 |
| `search` | `Total results: N` + JSON hits | 单位时间 error 计数 > 基线（基线由前 7 天同小时中位数给出） | 已接 |
| `get_server_map_tool` | serverMap 原始 JSON（节点 + 边 + 错误数 + 响应时间） | 边错误率或 P95 耗时超阈值 | 已接 |
| `cmdb_server_query` | `content[0].text` 内的字符串化 JSON | 有监控无资产 / 有资产无监控，计为账实不一致 | 已接 |

**输出**：`{信号来源, 实体原始标识（IP 或 appName）, 时间窗, 原始数值}`，此时**还不敢定性**。
**前置**：ES 侧需先调 `list_indices`（已接）确认索引存在；Pinpoint 侧时间窗必须是 13 位毫秒。

#### 0.2.3 第 2 步：确认与定界（Triage）

三个子动作必须按序做完，任何一步失败都要走降级分支。

**(a) 验真——排除「采集故障」冒充「业务故障」**

| 工具 | 做什么 | 判定 | 现状 |
|---|---|---|---|
| `healthy` / `ready` | 源是否健康、是否已完成启动 | 任一失败 → 该源 degraded，本批信号整体降级 | 已接（`healthy`，`ready` 未接） |
| `build_info` | 对端身份与版本 | 版本与契约不符 → 停止解析，避免误读字段 | 未接 |
| `targets_metadata` / `list_targets` | 主机是否在抓取目标里、最近抓取是否成功 | target 不存在 = 未纳管；target 存在但抓取失败 = 采集异常；两者都不等于业务故障 | 已接（仅 `targets_metadata`） |
| `series` | 该主机/指标到底有没有序列 | 返回空 → `NO_DATA`，禁止结论为「健康」 | 已接 |
| `get_shards` | ES 分片是否正常 | 有未分配分片 → 日志查不到是集群问题，不是无日志 | 已接 |

**(b) 归属——把 IP 落到平台实体**

| 工具 | 做什么 | 输出 | 现状 |
|---|---|---|---|
| `cmdb_server_query` | 按 IP / 主机名查资产 | `{hostName, 机房, 机型, CPU/内存, 在线状态}` | 已接 |
| `list_applications_tool` | 确认应用是否存在于 Pinpoint | `{applicationName, serviceTypeCode}` | 已接 |
| `get_project_deploy_tool` | 工程与云主机 IP 的部署关系 | `工程 ↔ IP` 双向映射 | 未接 |

处理规则：`instance="IP:port"` 先剥端口，再经 `identity.NormalizeHost` 归一后查 CMDB；CMDB 查无此机 → 标「账实不一致」，**用 IP 继续第 3 步，不阻断**。

**(c) 定界——单点还是批量**

| 工具 | 做什么 | 判定 | 现状 |
|---|---|---|---|
| `get_host_structure_tool` | 云主机与物理宿主机映射 | 多台异常机同宿主 → 判宿主机故障域，不按单机处理 | 未接 |
| `analyze_host_concentration_tool` | 实例是否过度集中 | 集中度高 → 影响面放大，告警级别上调 | 未接 |
| 本地 `identity` 表 | 同机房 / 同应用主机清单 | 由平台本地计算，不再调上游服务 | 已具备 |

**输出（确认后的问题单）**：

```
{ 实体: {ip, hostName, appId, 机房, 负责人},
  级别: critical / warning,
  信号来源: alerts / up / metrics / logs / topo / cmdb,
  时间窗: [start, end]（已统一为秒或 RFC3339）,
  影响面: {主机数, 应用数, 是否同宿主机},
  可信度: confirmed / degraded / no_data }
```

**准入第 3 步**：`可信度=confirmed` 或 `degraded` 且已明确降级原因；`no_data` 直接结案，不进入定位。
**强制降级**：采集侧自检失败 → 生成「采集故障」问题单，**转采集运维，不进业务排障**。这是本流程唯一必须停下的分支。

#### 0.2.4 第 3 步：定位（Localization）

目标：在拓扑上确定「断点在哪、往哪传播」，不解释原因。

| 顺序 | 工具 | 做什么 | 验证点 | 现状 |
|---|---|---|---|---|
| 1 | `list_nodes_tool` → `get_module_topology_tool` | 节点 → 模块 → 工程，界定分析范围 | 返回的工程数与被影响应用数是否吻合 | 未接 |
| 2 | `resolve_analysis_scope_tool` | 批量分析前编排范围，剔除重复与无关应用 | 范围外的应用不出现在后续结果里 | 未接 |
| 3 | `get_server_map_tool` / `get_link_topology_tool` | 取上下游节点与调用边 | 必须能定位到具体边，否则说明时间窗或应用名错 | 已接（仅前者） |
| 4 | `analyze_link_topology_tool` | 图计算：环路、最长路径、影响面、关键依赖 | 与第 2 步的影响面互相印证；不一致要回查范围 | 未接 |
| 5 | `analyze_pinpoint_dependencies_tool` | 真实调用视角的依赖排序（Top N） | 用于确认「关键依赖」而非「配置依赖」 | 未接 |
| 6 | `drag_heatmap_tool` | 按时间 + 耗时框选，收敛到具体事务集合 | 事务数与边上错误数应同量级 | 已接 |
| 7 | `get_chain_topology`（Prometheus 侧） | 交叉验证拓扑 | 两源拓扑不一致 → 走 §12 的权威源收敛，不取平均 | 未接 |

**输出**：`{故障点（节点/应用/边）, 传播路径, 受影响应用清单, 拓扑来源}`。

#### 0.2.5 第 4 步：取证（Evidence）

目标：把「慢 / 错 / 抖」量化成可复核的数字，并建立到 trace 的索引。

| 证据类型 | 工具 | 取什么 | 验证点 | 现状 |
|---|---|---|---|---|
| 时序基线 | `query` / `range_query` / `prometheus_query_tool` | 故障前后同指标对比（后两者用于架构侧多点采样） | 采样点 ≥ 2 才能判趋势，否则 `NO_DATA` | 已接（前两者） |
| 主机资源 | `host_metrics_realtime` / `host_metrics_trend` | 实时值 + 趋势方向 | 瞬时抖动与持续劣化要区分 | 部分（排障用 `range_query` 替代趋势） |
| 规则口径 | `arch_rule_check_tool` | 服务端阈值判定 + 逐目标观测值 | 结论须与自己算的一致，不一致以服务端为准并记录 | 未接 |
| 节点批量 | `analyze_node_runtime_tool` | 一次跑完整个节点多规则 | 避免逐规则调用放大上游压力 | 未接 |
| 日志 | `search` | 错误计数 + 样本报文 | 计数取 `Total results`，`relation=gte` 要标注为下限 | 已接（排障 + 巡检） |
| 指标 → 调用链 | `exemplar_query` | 异常点的 traceId | 无 exemplar 则退化为按时间窗猜应用 | 未接（排障用 `drag_heatmap_tool` 取 `traceIds`） |
| 调用链 | `get_transaction_trace_tool` | 单笔事务的 span 树 | span 耗时之和与边上 P95 应能对上 | 已接 |

**输出**：证据集 `{指标序列, 日志计数与样本, traceId 列表}`，每条证据必须带**时间戳 + 单位 + 来源**，否则不能进证据链。

#### 0.2.6 第 5 步：定因（Root Cause）

目标：给出**唯一**根因假设，并写明被排除的竞争假设。

| 动作 | 工具 | 做什么 | 判定 | 现状 |
|---|---|---|---|---|
| 链内定因 | `get_transaction_trace_tool` | 下钻到方法级，找耗时/异常集中点 | 单一 span 占比 > 50% 视为该 span 为瓶颈 | 已接（根 span 不参与占比计算） |
| 结构定因 | `analyze_link_topology_tool` | 环路 / 关键依赖 / 单点 | 与故障点重合才可采纳 | 未接 |
| 解释「为什么没告警」 | `list_rules` + `list_alerts` | 规则是否加载、是否命中、是否被抑制 | 规则缺失 → 补规则，而非「系统健康」 | 未接 |
| 取数异常判因 | `arch_label_probe_tool` + `metric_metadata` | 标签口径、指标类型是否正确 | counter 当 gauge 用 → 增长率算错，须重算 | 未接 |
| 变更关联 | `project_deployment_query` | 告警前是否有发布/部署 | 时间窗内存在变更 → 列为高优先竞争假设 | 未接 |
| 配置侧核对 | `config` / `flags` | 抓取配置、规则文件、外部标签、启动开关 | 配置变更与故障同时发生要单列 | 未接 |
| 告警通道核对 | `alertmanagers` | 通道是否可达 | 不可达 → 结论附「告警未送达」说明 | 未接 |
| 结论汇总 | `summarize_architecture_findings_tool` | 去重归类、给处置建议 | 仅作素材，最终结论由平台生成 | 未接 |

**输出**：`{根因, 证据引用（traceId / 指标序列 / 日志查询）, 已排除假设及排除理由, 处置建议, 置信度}`。

#### 0.2.7 门禁与降级矩阵

| 卡点 | 触发条件 | 处理 | 是否可继续 |
|---|---|---|---|
| 源不可用 | `healthy` / `ready` 失败 | 该源标记 degraded，跳过其后续所有步骤 | 可继续（记录缺失源） |
| 主机未纳管 | `targets_metadata` 无此目标 | 判「未纳管」，不出「失联」结论 | 可继续，转纳管流程 |
| 主机纳管但抓取失败 | target 存在、`up=0` | 判「主机失联/采集异常」，问题单直接定级 critical，结论指向主机或采集层 | 可继续（不进入业务定因） |
| CMDB 无记录 | `cmdb_server_query` 空 | 标「账实不一致」，用 IP 继续 | 可继续 |
| 全源无数据 | 各源均为空 | `no_data` 结案（问题单 `confidence=no_data`） | 不可继续 |
| 拓扑两源不一致 | Pinpoint 与 Prometheus 拓扑冲突 | 按 `TOPO_AUTHORITY_SOURCE` 取权威源，差异入库 | 可继续 |
| 结论无证据 | 第 5 步无法引用第 4 步证据 | 降级为「疑似」（置信度 ≤0.2），不得标记为已定因 | 不可继续 |

### 0.3 五步流程与平台现状的实现对比（对齐方案）

> §0.2 描述的是**目标流程**；本节描述 **M1–M5 落地后的代码现状**、与原目标的差距及验收结果。
> 代码口径：`ai-ops/platform/backend/internal/diagnose/engine.go`，2026-11-06 快照。

#### 0.3.1 实施后速览

| 口径 | 数量 | 说明 |
|---|---|---|
| 五步流程引用的工具（去重） | 40 | §0.2 各步工具合并去重 |
| 平台整体已接入 | 15 | 含巡检（`inspect`）、告警（`alarm`）、稽核（`audit`）等模块 |
| **排障链路（`diagnose`）实际编排** | **12 个工具调用点 / 10–11 条证据链步骤** | Pinpoint 4：`list_applications_tool`、`get_server_map_tool`、`drag_heatmap_tool`、`get_transaction_trace_tool`；Prometheus 6：`list_alerts`、`query`、`healthy`、`targets_metadata`、`series`、`range_query`；CMDB 1：`cmdb_server_query`；ES 2：`get_shards`、`search`（失败回退本地 log-analyzer）。验真 4 个工具的结果写入 `sourceHealth`，不单独建 `Step`，故 `steps` 少于工具调用数 |

三点口径澄清：

1. **验真已成为独立阶段**（第 3 步），`healthy` / `targets_metadata` / `series` / `get_shards` 的结果写入 `DiagnosisSession.sourceHealth`（4 条记录，前端可逐源查看），**不追加 `Step`**，避免污染证据链计数。
2. **日志证据优先走 ES `search`**（按候选主机过滤），索引不存在、无候选主机或查询失败时才回退本地 log-analyzer，回退原因写入步骤结果。
3. **问题单是第 2 步的显式产出**，字段为 `entity` / `severity` / `signals` / `window` / `impact` / `confidence` / `reason`，`confidence` 取 `confirmed | degraded | no_data`。

#### 0.3.2 改造前的调用顺序（as-is，归档）

`execute()` 改造前为单次串行 6 段，共 5 次上游接口调用：

| 段 | 函数 | 位置 | 调用的工具 |
|---|---|---|---|
| ① 拓扑影响面 | `collectImpact` | `engine.go:249` | 无（本地拓扑数据） |
| ② 应用清单 + 服务地图 | `collectPinpoint` | `engine.go:278` | `list_applications_tool`、`get_server_map_tool` |

三个结构性问题：

- **定因先于取证**：`rank` 在 ⑥ 之前，日志是结论出来后补的附加信息，不是证据链输入。
- **无验真环节**：`up=0` 直接进入候选排序，没有 `healthy` / `targets_metadata` / `series` 判别「采集故障」与「业务故障」。
- **`rank` 隐式耦合**：通过反查 `sess.Steps` 取 `list_alerts` 的 `matchedKeywords`，步骤顺序一变即失效。

#### 0.3.3 已落地的调用顺序（implemented）

```
0) collectImpact      拓扑影响面    —— 产出候选主机与被影响应用（定界初算）
1) collectPrometheus  发现          —— list_alerts + query(up)，up=0 保留标记
2) collectVerify      数据源验真    —— healthy → targets_metadata → series → get_shards
3) collectCMDB        确认与定界    —— cmdb_server_query（归属/在线状态）
4) buildTicket        生成问题单    —— 实体/级别/信号/时间窗/影响面/可信度
5) collectPinpoint    定位          —— list_applications_tool + get_server_map_tool
6) collectRange       取证·基线     —— range_query(node_load1, 近 60m, step=60s)
7) collectTrace       取证·调用链   —— drag_heatmap_tool → get_transaction_trace_tool
8) collectLog         取证·日志     —— ES search（按候选主机）→ 失败回退 log-analyzer
9) rank               定因          —— 证据集驱动：来源数 + 条数 → 置信度
```

与原方案的两处偏差（均为实现时修正）：

1. **验真提前到 CMDB 之前**：先判断「数据源是否可信」，再解释资产/信号，避免用不可信数据做归属判断。
2. **问题单在定位前生成**：第 2 步结束即可定界并开单，后续取证只补充证据，不改变实体与级别（除非出现更严重的信号）。

## 2. 返回形态与平台适配层

### 2.1 三种返回形态

| 形态 | 长什么样 | 典型服务 |
|---|---|---|
| A. 标准 上游返回信封 | `{"content":[{"type":"text","text":"..."}],"structuredContent":{...},"isError":false}` | 大多数 FastMCP / rmcp / go-sdk 工具 |
| B. 裸业务 JSON | 直接 `{"code":200,"data":{...}}` 或数组 | cmdb-mcp-server 在部分路径下、mock 服务 |
| C. 双重编码 | `content[0].text` 本身是**一段 JSON 字符串** | cmdb-mcp-server（`content[0].text` 为 stringified JSON）、Prometheus `query` 系列（text 是文本行） |

### 2.2 平台统一解析

| 函数 | 位置 | 处理逻辑 |
|---|---|---|
| `mcp.ResultOf(raw)` | `internal/mcp/result.go` | 递归拆 `"..."` 裸字符串 → 识别 envelope → `structuredContent` 优先 → text 是合法 JSON 则作为 Payload，否则留在 `Text` |
| `mcp.ContentJSON(raw)` | 同上 | 遍历 `content[]`，取**第一个**能解析为 JSON 的 text 片段（专治 ES 的"统计文案 + JSON"混排） |
| `Result.Preview(max)` | 同上 | 生成落证据链的截断视图：`{bytes, data / preview, truncated, isError}` |
| `DecodeJSON[T]` | 同上 | 泛型解码业务 JSON |

**平台消费原则**：业务代码不直接摸 `content[0].text`，一律走上述适配层；解析失败时保留 `preview` 原文，结论按 `NO_DATA` 处理，绝不当作"健康"。

### 3.2 平台实际消费方式（Pinpoint）

**排障链路（`internal/diagnose/engine.go`）**

```
① list_applications_tool{service_name:"DEFAULT"}
   → 归一为 []PinpointApplication
   → FindPinpointApplication(ids=[pinpointId, appId], names=[pinpointName, appName, appId])
      匹配顺序：ID 精确 → 名称精确 → 名称包含
   → 未匹配：get_server_map_tool 记 skipped，证据链标注"NO_DATA 不等于无异常"

② get_server_map_tool{
     application_name: 匹配到的 Name,
     from_ts: now-window 的 UnixMilli,
     to_ts:   now 的 UnixMilli,
     caller_range: 1, callee_range: 1, bidirectional: true
   }
   → PinpointServerMapOf → 只消费 nodes 数、middlewares 数 + Preview 原文
```

**巡检链路（`inspect/trace_rules.go` T8）**：先用 `apolloAppName` 查，无数据回退 `appId`，最多 2 次；命中条件为 `len(nodes)>0 || len(links)>0`；消费 `links[].from/to/count/errorCount/responseTime` 取 Top N。

**身份映射链路（`identity/identity.go`）**：`list_applications_tool` 结果用于回填平台的 `PinpointAppID` / `PinpointAppName`，建立 `appKey ↔ Pinpoint 应用` 的双向别名。

**留白**：`get_transaction_trace_tool` 完全未被使用 —— 平台没有从 Pinpoint 采集 `traceId` 的入口，因此"单笔慢调用下钻"这条能力断了。这是最值得补的一环。

#### 复杂返回结构详情

##### `range_query`

**介绍**：在 `start_time` 与 `end_time` 之间按 `step` 评估 PromQL，返回区间序列文本。未指定 `step` 时按约 250 个数据点自动计算。

**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| query | string | 是 | — | PromQL 表达式 |
| step | string | 否 | 自动（约 250 点） | Go 时长格式，必须为正，如 `30s`、`5m`、`1h` |
| start_time | string | 否 | `end_time - 5m` | Unix 秒、RFC3339 或相对时长 |
| end_time | string | 否 | 当前时间 | Unix 秒、RFC3339 或相对时长 |
| truncation_limit | int | 否 | 全局配置 | 负数表示本次调用禁用截断 |

**返回结构**：

```json
{
  "result": "{instance=\"192.168.7.66:9100\"} =>\n27.5 @[1782115200.000]\n27.8 @[1782115260.000]",
  "warnings": []
}
```

`result` 是 `model.Matrix.String()` 生成的纯文本（不是结构化 JSON），每条序列为 `{labels} =>` 后接若干行 `value @[timestamp]`；标量结果形如 `scalar: 27.5 @[1782115200.000]`。`warnings` 为上游告警数组或 `null`；发生截断时 `result` 末尾追加中文截断警告。

##### `list_alerts`

**介绍**：调用 `/api/v1/alerts` 返回全部活动告警，结果为 `AlertsResult` 的直接序列化。

**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| 无 | — | — | — | 工具不接受输入参数 |

**返回结构**：

```json
{
  "alerts": [
    {
      "activeAt": "2026-11-05T09:12:00.123456789+08:00",
      "Annotations": {"summary": "CPU 使用率过高"},
      "Labels": {"alertname": "HighCPU", "instance": "192.168.7.66:9100", "severity": "warning"},
      "State": "firing",
      "Value": "27.5"
    }
  ]
}
```

`alerts` 来自 `promv1.AlertsResult`。`activeAt` 有 json tag；`Annotations`、`Labels`、`State`、`Value` 无 json tag，序列化后保持首字母大写。`State` 取值 `pending` 或 `firing`；无告警时为 `{"alerts":[]}`。

```json
  "disk_total_bytes": 1099511627776,
  "disk_usage_percent": 45.2,

  "network_traffic_bytes_per_second": 12582912,
```

##### `host_metrics_trend`

**介绍**：在时间范围内并发执行 12 组 PromQL 范围查询，并额外查询每组序列的最后一个采样值。`node` 与 `ip` 至少提供一个，同时提供且取值不同会报错。

**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|

#### 分页与限额

- `cmdb_server_query` 的 pageSize 默认 15：HTTP 兼容层 `ServerQueryParams.pageSize` 与 `config/param_mappings.json` 的 `page_size_defaults` 均为 15，Mock 响应也按 15 返回；上游服务 inputSchema 本身未声明 default。
- 其余 4 个工具 inputSchema 均声明 `currentPage` 默认 1、`pageSize` 默认 40，且未声明上限。
- pageSize 上限仅由 `cmdb_server_query` 的 inputSchema 声明为 `maximum: 100`（`currentPage` 为 `minimum: 1`）；服务端不做校验或截断，参数原样转发后端，超限后的实际条数由后端决定（平台 identity 模块即传 `pageSize: 200`），源码无法确认后端行为。
- 分页字段归一：`server-public-ip-query`、`product-query`、`project-basis-query` 返回的 `current`/`size` 由 `_normalize_pagination` 改写为 `currentPage`/`pageSize`；`cmdb-server-query` 原生返回 `currentPage`/`pageSize`/`total`/`pages`；`project-deployment-query` 原样返回。
- `productIdList` 路径为本地分页：逐个 productId 拉全量（每页 page_size=100、每产品最多 200 页，即最多 2 万条，并发上限 6），按 id 去重合并后本地切片；其返回 `data` 使用 `size`/`current` 而非 `pageSize`/`currentPage`，`total` 为并集台数；`fields` 仅本地裁剪并附加 `data._trimmedFields`，不改变 `total`/`pages`。

|---|---|---|---|---|
| `index` | string | 是 | 无 | 索引名或模式，支持 `logs-*`、逗号分隔多个 |
| `fields` | string[] | 否 | 无（不注入 `_source`） | 需要返回的字段名列表，合并进 `_source` |

```json
[
  { "type": "text", "text": "Total results: 128, showing 2." },
  { "type": "text", "text": "[{\"@timestamp\":\"2026-11-05T10:00:00Z\",\"level\":\"error\",\"host\":\"api-01\",\"message\":\"timeout\"},{\"@timestamp\":\"2026-11-05T10:00:01Z\",\"level\":\"warn\",\"host\":\"api-02\",\"message\":\"retry\"}]" },
  { "type": "text", "text": "Aggregations results:" },
  { "type": "text", "text": "{\"by_level\":{\"buckets\":[{\"key\":\"error\",\"doc_count\":9}]}}" }
]
```

说明：`Total results` 文案仅在「无聚合」或「有命中」时输出，命中为空时该文案缺省；无命中且仅有聚合时，`content[]` 只有聚合文案与聚合 JSON。`hits.total` 缺失时文案中的总数为 `unknown`。

##### `list_indices`

**介绍**：调用 `GET /_cat/indices/<index_pattern>?format=json&h=index,status,docs.count`，只返回三列。该工具不做聚合，返回条数与模式命中数一致。
**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `index_pattern` | string | 是 | 无 | 索引通配模式，如 `*`、`logs-*`、`a-*,b-*`；无命中时返回 `Found 0 indices:` 与空数组 |

**返回结构**：

```json
[
  { "type": "text", "text": "Found 2 indices:" },
  { "type": "text", "text": "[{\"index\":\"logs-2026.11.05\",\"status\":\"open\",\"docs.count\":\"1024\"},{\"index\":\"logs-2026.11.04\",\"status\":\"open\",\"docs.count\":\"998\"}]" }
]
```

说明：`docs.count` 由 cat API 以字符串返回，反序列化为数字后再序列化，字段名保持带点的 `docs.count`；取该字段时需按原键名访问。

#### 字段约定与平台配置

- 本服务不定义任何业务 schema，`search`、`esql` 的全部分组、时间过滤与字段名都由调用方拼装，ES 侧索引映射才是唯一事实来源；`get_mappings` 是唯一可用于前置校验字段的工具。
- 默认索引模式由平台以 `ES_LOG_INDEX=logs-*` 约定，`list_indices` 的 `index_pattern`、`search`/`esql` 的索引部分都按该值填充；索引名不符时表现为 `list_indices` 返回 `Found 0 indices:`，或 `search` 报索引不存在。
- 时间字段由 `ES_LOG_TIME_FIELD=@timestamp` 约定，用于 `range` 过滤与 `sort`；字段不符时 `range` 查询命中为空或报 `unrecognized field`，时间维度聚合分桶为空。
- 级别字段由 `ES_LOG_LEVEL_FIELD=level`、主机字段由 `ES_LOG_HOST_FIELD=host` 约定，用于 term 聚合与过滤；实际字段名为 `log.level`、`severity`、`host.name` 等时，按约定名过滤或聚合得到空桶，且不报错。
- 上述 `ES_LOG_*` 变量只作用于平台侧的提示词与调用参数，源码未读取它们；服务自身仅读取 `ES_URL`、`ES_API_KEY`、`ES_USERNAME`、`ES_PASSWORD`、`ES_SSL_SKIP_VERIFY`（默认 `false`）、`ES_REQUEST_TIMEOUT_SECS`（默认 `30`），另有 `MCP_TOOL_PREFIX` 会给工具名加前缀。
- 连接层默认值以源码为准：请求超时 30 秒，超时或 ES 返回非 2xx 时工具以错误内容返回，不返回部分结果；配置 `MCP_TOOL_PREFIX` 后工具名变为「前缀 + 原名」，按原名调用将命中不到工具。

**平台已编排（2 / 5）**：`list_indices`（T10 前置索引发现）、`search`（T10 错误日志计数 / 排障日志证据）；`get_mappings` 作为字段名动态发现手段保留，`esql` 与 `get_shards` 未编排。

### 6.2 关键约束与平台消费方式（T10）

**关键约束**：ES 没有固定业务 schema。平台通过环境变量约定字段（`ES_LOG_TIME_FIELD=@timestamp`、`ES_LOG_LEVEL_FIELD=level`、`ES_LOG_HOST_FIELD=host`），真实集群字段不同就必须改配置，否则 T10 恒为 `NO_DATA`。

**平台消费方式（T10 日志错误）**

```
① list_indices{index_pattern: "logs-*"}  → esIndexNames：JSON 数组优先，其次 "Found N indices:" 文案
   为空 → NO_DATA（"ES 中不存在匹配的日志索引"），不逐台主机刷噪音

② search{index, query_body}：
   {
     "size": 0, "track_total_hits": true,
     "query": {"bool": {
        "filter": [{"range": {"@timestamp": {"gte": "now-15m"}}}],
        "must": [
          {"query_string": {"query": "level:(ERROR OR FATAL OR error OR fatal)", "lenient": true}},
          {"query_string": {"query": "host:\"<host>\"", "lenient": true}}
        ]
     }}
   }

③ esTotalHits：先匹配 "Total results: N"，再取 hits.total（数字或 {value} 两种形态）
   > threshold(20) → RISK；≥ threshold*5 → P1；否则 NOT_TRIGGERED
```

### 7.2 平台的身份归一规则

```
NormalizeHost(x):
  - 去空格、转小写
  - 去掉 :port（Prometheus instance 常见 IP:9100）
  - 去尾部 '.'（DNS 反解结果）

Host 实体同时持有：
  Key（归一键）、IPs[]、HostNames[]、Addrs[]、Apps[]、MiddlewareTypes[]、CMDB ID

匹配顺序（MatchRecord）：
  精确 IP → 精确 hostName → 别名表 → 全等 key
```

## 9. 逐工具字段契约（平台流转接口细化）

### 9.1 公共调用壳

平台**所有**上游接口调用都收敛到同一签名，业务模块只关心 `server / tool / args`：

```
Gateway.Call(ctx, server, tool, args) (json.RawMessage, error)
```

| 环节 | 规则 | 失败后果 |
|---|---|---|
| 注册检查 | `server` 必须在 `Servers()` 返回的已注册列表内 | 返回 `unknown server` |
| 名单检查 | 先 deny 后 allow；`server/*` 通配 | 返回 `tool denied` |
| 超时 | 每次调用独立 `context.WithTimeout(MCP_TIMEOUT_MS)` | 记 `CallLog{OK:false, Error:"context deadline exceeded"}` |
| 审计 | `CallLog{Server, Tool, Args, OK, Error, LatencyMs, At}` 进环形日志，`/api/mcp/logs` 可查 | 不影响业务 |
| 证据留痕 | `domain.Step{No, Source, Tool, Title, Status(ok/warn/error/skipped), Args, Result, LatencyMs, Error, At}` | `skipped` 不阻断后续步 |
| 结果收录 | `Result.Preview(4096)` 截断后写入 `Step.Result`，超限标 `truncated:true` | 原文保留在预览里，避免解析失败丢证据 |

`source` 实际取值有 6 个：`topo`（本地快照）、`pinpoint`、`promthus`、`cmdb`、`rule`（本地规则判定）、`log`（外部日志分析器）。`domain.Step` 的注释只列了前四个，实现已扩展；前端证据链按 `source` 渲染分组，新增工具必须归入这 6 类之一。

### 9.4 `promthus.list_alerts`

| 项 | 内容 |
|---|---|
| 调用点 | 排障 step③；告警采集（定时轮询） |

### 9.5 `promthus.query`（up 存活）

| 项 | 内容 |
|---|---|
| 调用点 | 排障 step④；巡检 T7 |
| 请求 | `{"query":"up{instance=~\"^10\\.1\\.2\\.3(:[0-9]+)?$|^10\\.1\\.2\\.4(:[0-9]+)?$\"}"}` |
| 查询构造 | `identity.UpQuery(hosts)`：每个 host 经 `NormalizeHost` → `regexp.QuoteMeta` → 包成 `^host(:[0-9]+)?$` → 去重后用 `|` 连接；全部为空则**不发起调用** |
| 返回形态 | **文本行**：`{instance="10.1.2.3:9100", job="node"} => 1 @[1756143048]`，时间戳为**秒** |
| 必读字段 | `metric.instance`（必须能 `NormalizeHost` 后命中主机别名表）、`value`（`1` 存活 / `0` 失联） |
| 平台结构 | `map[hostKey]float64`（当前实现为覆盖写：同一主机多序列时**最后一条生效**；建议改为"任一为 0 即判失联"） |
| 前置条件 | ① `node_exporter` 已纳管；② `instance` 标签是 `IP` 或 `IP:port`；③ 标签值能被 `NormalizeHost` 归一 |
| 缺失行为 | 无匹配序列 → `NO_DATA`（提示"可能未纳管或标签不一致"），**不判健康**；序列命中但 `instance` 归属校验失败 → 丢弃该序列 |
| 下游流转 | ① T7 Finding；② 作为 `collectCMDB` 的 `up` 入参，与 CMDB `state` 交叉验证 |

> **严格归属校验**：PromQL 用正则做"候选召回"，平台再用 `aliasToHost[NormalizeHost(instance)] == 当前主机 Key` 做"精确归属"，避免 `10.1.2.3` 误吃 `10.1.2.30` 的序列。

### 9.8 `cmdb.cmdb_server_query`

| 项 | 内容 |
|---|---|
| 调用点 | 排障 step⑤；巡检 T9；稽核对账；身份映射全量构建 |

### 9.9 `elasticsearch.list_indices` + `elasticsearch.search`

| 项 | `list_indices` | `search` |
|---|---|---|
| 调用点 | 巡检 T10 第 1 步 | 巡检 T10 第 2 步（逐主机） |
| 请求 | `{"index_pattern":"logs-*"}` | `{"index":"logs-*","query_body":{...}}` |
| 返回 | `content[]`：`Found N indices:` + JSON 数组 `[{index,status,docs.count}]` | `content[]`：`Total results: N` + ES 原生 `hits.total{value,relation}` / `hits.hits[]` |

| 请求体固定结构 | — | `size:0`（不取明细，只要计数）、`track_total_hits:true`、`bool.filter[range.<timeField>.gte="now-15m"]`、`bool.must[query_string(level), query_string(host)]`、两处 `lenient:true` |

| 前置条件 | ① `ES_MCP_URL` 非空（否则整个 T10 `NO_DATA`）；② 索引存在；③ 三类字段名与真实 mapping 一致（换集群必须核对，可用 `get_mappings` 自检） |
| 缺失行为 | 无索引 → 一次性 `NO_DATA`（**不做逐主机查询**，避免噪音）；解析失败 → `NO_DATA`；查询失败 → `NO_DATA` |
| 判定 | — | `total > 20` → `RISK`；`total ≥ 100`（5×阈值）→ `P1`；否则 `NOT_TRIGGERED` |

### 9.10 排障链路新增工具（M2–M5）

> 调用点：`internal/diagnose/engine.go`。以下 8 个工具在 M2–M5 接入，排障链路工具调用点由 8 个扩为 12 个（另 4 个为原有 `list_alerts` / `query` / `cmdb_server_query` / `list_applications_tool`）；验真 4 个工具不建 `Step`，会话证据链为 10–11 条。

| 工具 | 调用点（`execute()` 顺序） | 请求要点 | 必读字段 | 缺失 / 失败行为 |
|---|---|---|---|---|
| `promthus.healthy` | 第 3 步 验真 | 无参 | 任意 2xx 且 envelope 无 `isError` | 调用失败 → `sourceHealth[promthus]=unavailable`；后续 Prometheus 结论封顶 0.5 |
| `promthus.targets_metadata` | 第 3 步 验真 | `{"match_target":"<host>"}` | `data.activeTargets[].labels.instance`、`health`、`lastError` | 无此 target → `degraded`，detail 记「未纳管」；target 存在但 `health!=up` → `unavailable` |
| `promthus.series` | 第 3 步 验真 | `{"match[]":"up{instance=~\"<host>.*\"}"}` | `data[]`（非空即证明序列存在） | 空数组 → 该主机 `NO_DATA`；本步只写 `checks`，不阻断 |
| `promthus.range_query` | 第 5 步 取证（基线） | `{"query":"node_load1{instance=~\"...\"}","start":RFC3339,"end":RFC3339,"step":"60s"}` | `data.result[].values[][]`（秒级时间戳 + 数值） | 采样点 <2 → 判无数据；前后 1/3 均值比 ≥1.3 → 记「持续劣化」 |
| `pinpoint.drag_heatmap_tool` | 第 5 步 取证（链路入口） | `{"application_name":..., "from":13位毫秒,"to":13位毫秒}` | `traceIds[]`（取首个非空） | 无 `traceIds` → 跳过 trace，不伪造证据 |
| `pinpoint.get_transaction_trace_tool` | 第 5 步 取证 + 第 6 步 定因 | `{"trace_id":"<id>"}` | 根 span `elapsed`；子 span `executionMilliseconds` + `parentId`（兼容嵌套 `callStack` 与扁平数组） | 无 span → 跳过；非根 span 占根 `elapsed` ≥50% → 判「调用链瓶颈」并定级 `critical` |
| `elasticsearch.get_shards` | 第 3 步 验真 | 无参 | 分片 `state`（`STARTED` 正常）、`unassigned` 计数 | 存在未分配分片 → `sourceHealth[es]=degraded`，日志空结果不当作「无日志」 |
| `elasticsearch.search` | 第 5 步 取证（日志） | `{"index":"logs-*","query_body":{size:0,track_total_hits:true,range + query_string(host)}}` | `hits.total.value`；`relation=gte` 记下限 | 无候选主机 → **直接跳过**（防默认命中）；查询失败 → 回退本地 `log-analyzer`；两者皆失败 → `logErrors=0` 且不进证据集 |

**与巡检 T10 的差异**：排障侧 `query_string` 的 host 子句按候选主机列表拼成 `host:"h1" OR host:"h2" ...`，且必须先有候选主机；巡检侧逐主机查询。两者共用 `esTotalHits` 解析。

**降级口径**：`degradedSources()` 同时统计 `degraded` 与 `unavailable`；命中时排序后**所有候选置信度一律封顶 0.5**，问题单 `confidence=degraded`，会话 `status` 最多为 `investigating`，不会进入 `root_caused`。

## 10. 上下游流转条件矩阵

### 10.1 九条关键流转边

| # | 上游 | 上游字段 | 必要条件（硬门禁） | 转换 / 校验 | 下游 | 断裂表现与兜底 |
|---|---|---|---|---|---|---|
| E1 | 拓扑快照 | `middlewares[].connectAddr`、`apps[].apolloAppId/Name` | 地址非空且可解析 | `NormalizeHost`：去空格/小写/去 `:port`/去尾部 `.` | `scopeHost.Key`、`identity_host` | 无法归一 → 主机被丢弃；`hosts` 为空 → T7/T9/T10/T11 全部 `NO_DATA` |
| E2 | 拓扑 + Pinpoint | `apolloAppId`、`apolloAppName`、`pinpointName` | `list_applications_tool` 返回非空 | 三段匹配：ID 精确 → 名称精确 → 名称包含 | `get_server_map_tool.application_name` | 未命中 → step `skipped`，排障其余步骤继续 |
| E3 | 主机键 | `Host.Key` | 非空且是 IP/主机名 | `PromQLInstanceRegex` → `^host(:[0-9]+)?$` | `up{instance=~"..."}` | 正则为空 → 不发请求；无序列 → `NO_DATA` |
| E4 | Prometheus 序列 | `metric.instance` | 能归一且归属当前主机 | `aliasToHost[NormalizeHost(instance)] == Key` | `up` map | 归属失败 → 丢弃该序列（防前缀误匹配） |
| E5 | 主机键 | `Host.Key` | 是 IP（域名排后） | `cmdb_server_query{ip, pageSize:5}` | `cmdbAsset` / T9 | 无记录 → `P1`；无 `state` → `NO_DATA`；最多 5 台 |
| E6 | 主机键 | `Host.Key` | ES 索引存在 + `host` 字段名匹配 | `query_string: host:"<host>"`（短语，`lenient`） | T10 日志计数 | 无索引 → 全局 `NO_DATA`；字段不匹配 → 单机 `NO_DATA` |
| E7 | CMDB 记录 | `state` | 字段存在 | `0` 在线，其余非在线；`4/6` 升 `P1` | T9 / 稽核结论 | 缺 `state` → `NO_DATA`，不猜 |
| E8 | Prometheus `up` + CMDB `state` | `up`（0/1）、`state`（0/…） | 两源都命中同一主机 | 交叉判定（见 10.2） | 根因方向 | 任一源缺失 → 只给单源结论，不交叉 |
| E9 | 告警 labels | `labels.instance` | 可归一为主机 | `Host = NormalizeHost(instance)` | 拓扑节点 → `depApps` 影响面 | 无主机 → 影响面为空，告警仍入库 |

### 10.2 `up` × `state` 交叉判定矩阵（排障核心结论）

| Prometheus `up` | CMDB `state` | 平台结论 | 指向 |
|---|---|---|---|
| 1 | 0 在线 | 健康 | — |
| **0** | **0 在线** | **账实不符 / 失联**：资产说在线，心跳已断 | 网络、宿主机、agent 掉线；优先查物理层 |
| 1 | ≠0 非在线 | **账实不符**：CMDB 说非在线，实际仍有心跳 | CMDB 未及时更新（流程问题），需回写 |
| **无序列** | 0 在线 | **未纳管监控** | `NO_DATA`，禁止判健康；补 node_exporter |
| **无序列** | 无记录 | **双重缺失** | 拓扑数据可疑或资产未录入，`P1` |
| 0 | 无记录 | **疑似黑户/脏数据** | 先查 CMDB 录入，再查拓扑来源 |

### 10.3 巡检四态与流转阻断

| 判态 | 触发条件 | 是否进入报告 | 是否建工单 | 是否影响下一轮 |
|---|---|---|---|---|
| `NOT_TRIGGERED` | 数据齐全且未超阈值 | 是（正常项） | 否 | 否 |
| `RISK` | 数据齐全且超阈值 | 是（风险项） | 是（按严重级别） | 是（持续风险） |
| `NO_DATA` | 未配置上游服务 / 未配置 ES / 无主机 / 查询失败 / 无序列 / 字段缺失 | 是（**显式标注**） | 否 | 是（需人工补数据源） |
| `NOT_APPLICABLE` | 规则不适用该对象（如非 IP 主机做 CMDB 反查） | 是（跳过说明） | 否 | 否 |

> 四态互斥，优先级 `NO_DATA > RISK > NOT_TRIGGERED`：只要拿不到数据，就绝不允许输出"正常"。

## 12. 失败与降级矩阵

| 失败类型 | 典型错误 | 平台判定 | 证据链 `Status` | 是否继续 |
|---|---|---|---|---|
| 服务未启动 | `connection refused` | 该步不可用 | `error` | 继续其余步 |
| 超时 | `context deadline exceeded` | 该步 `NO_DATA` | `error` | 继续 |
| 工具未注册 | `unknown server` | 该数据端整体不可用 | `skipped` | 继续 |
| 工具被禁 | `tool denied` | 与未注册同 | `skipped` | 继续 |
| 业务 `isError` | 服务端 `isError:true` | 该步失败 | `error` | 继续 |
| 返回解析失败 | JSON/文本都无法识别 | `NO_DATA`，保留 `preview` | `warn` | 继续 |
| 返回空集合 | `[]` / `records:[]` | 视工具语义：告警=无告警；资产=账实不符（`P1`） | 按语义 | 继续 |
| 字段缺失 | 无 `state` / 无 `instance` | `NO_DATA`，**不猜默认值** | `warn` | 继续 |
| 末尾截断 | `Preview.truncated=true` | 结论仍基于结构化字段；原文仅预览 | `ok` | 继续 |

> 统一原则：**上游数据是证据源，不是决策源**。任何数据缺失只降低结论置信度，平台用四态显式表达，不把"查不到"翻译成"没问题"。

## 13. 数据流转链路（四条主链）

### 13.1 身份映射链（所有其它链路的地基）

```
拓扑快照（data/platform/topo/*.json）
   ↓ 抽出 connectAddr / apolloAppId / apolloAppName
[应用键] [主机键]（NormalizeHost 去端口/小写/去尾点）
   ↓
pinpoint list_applications_tool ──► 回填 PinpointAppID/PinpointAppName（别名双向登记）
   ↓
cmdb cmdb_server_query（全量分页 200×5）──► 回填 IP / hostName / CMDB ID / 机房
   ↓
（可选）DNS 正反解
   ↓
identity_app / identity_host 落盘 + 内存索引（appAlias / hostAlias）
```

产出物：`/api/identity/{stats,apps,hosts,resolve}`。后续排障、巡检、稽核的所有"主机反查"都依赖这张表，否则会出现"Prometheus 有、CMDB 查无"的假风险。

### 13.2 排障证据链（12 个工具调用点 / 10–11 条步骤）

```
请求（中间件类型 + 地址 / 应用）
  → 拓扑影响面（本地快照，不调上游服务）
  → ① Prometheus 活跃告警 ── list_alerts
  → ② Prometheus 目标存活 ── query(up)
  → ③ 数据源验真（M2，不建 Step，写 sourceHealth）── healthy / targets_metadata / series / get_shards
  → ④ CMDB 资产归属       ── cmdb_server_query（×≤5 主机）
  → ⑤ Pinpoint 应用清单   ── list_applications_tool
  → ⑥ Pinpoint 服务地图   ── get_server_map_tool
  → ⑦ 指标基线            ── range_query（采样点 <2 即 NO_DATA）
  → ⑧ 热力图取 traceId    ── drag_heatmap_tool
  → ⑨ 单笔调用链          ── get_transaction_trace_tool（非根 span ≥50% 判瓶颈）
  → ⑩ 日志证据            ── es.search（失败回退本地 log_analyzer）
  → ⑪ 规则排序 / 证据定因（置信度 = 0.25 + 0.10×来源数 + 0.02×条数，封顶 0.9）
  → 归档：会话 + 问题单（DiagnosisTicket）+ 自动建工单/知识库

证据互证逻辑：
  Prometheus up=0 且 CMDB state=0（在线）→ "资产显示在线但心跳丢失"，指向网络/宿主机
  Prometheus 查无序列 且 CMDB 有记录     → "未纳管监控"，判 NO_DATA 而非健康
  CMDB 查无记录 但拓扑有依赖             → P1 账实不符
  子 span 占根 elapsed ≥50%              → 调用链瓶颈，问题单 critical
  任一源 degraded/unavailable            → 所有候选置信度封顶 0.5，禁止 root_caused
```

### 13.3 巡检链（四态：NOT_TRIGGERED / RISK / NO_DATA / NOT_APPLICABLE）

```
拓扑行 → collectScopeHosts（按被依赖应用数降序，≤20 台）
  → 批次缓存 hostMCPCache（同主机同批次只查一次）
     ├─ T7  up            → prometheus.query
     ├─ T9  CMDB 一致性   → cmdb.cmdb_server_query
     ├─ T10 日志错误      → es.list_indices + es.search
     └─ T11 指标阈值      → prometheus.host_metrics_realtime
  → Finding（含 Evidence / Impact）→ 巡检报告 → 工单
```

**四态原则**：查询失败、无序列、无索引一律 `NO_DATA`，绝不降级成"正常"。这是平台跨服务数据质量的核心约束。

### 13.4 告警 → 自动排障 → 工单 → 知识库

```
prometheus.list_alerts ─┐
Alertmanager /api/v2/alerts ─┤→ mergeAlerts（同 fingerprint 合并，补抑制态）
prometheus.range_query（劣化扫描）─┘
        ↓
   fingerprint 幂等 upsert（ticket / alarm_event）
        ↓
   四规则准入（firing / 未抑制 / P1 / 无关联会话）
        ↓

        ↓

```

## 14. 缺口与对齐建议

### 14.1 数据口径缺口

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | `from_ts/to_ts` 平台传 **UnixMilli**，Prometheus 侧时间却是**秒**/RFC3339 | Pinpoint 与 Prometheus 时间窗对不上，证据时间轴错位 | 在网关适配层统一「内部毫秒、出口按工具转」；对 pinpoint 明确 ms 契约并加断言 |
| 2 | `list_alerts` 的 Alert 字段**首字母大写、无 json tag** | 平台若按小写解析会全空 | 当前依赖 Go `encoding/json` 的大小写不敏感匹配才通过（脆弱）；建议服务端补 json tag，平台侧保留 `PromAlert` 兼容层 |
| 3 | Prometheus `query` 返回 `result` 为**文本行** | 需要正则/手工解析，易漏 | 计划性切换到 `data.result` 结构；网关侧已有 `PrometheusQuery/Samples` 双解析，保留但收敛 |
| 4 | CMDB 返回 `content[0].text` 双重编码 | 直接 `json.Unmarshal` 失败 | 已用 `ResultOf` 处理；建议 CMDB 直接返回 `structuredContent` |
| 5 | 分页口径不统一（CMDB `currentPage/pageSize` vs Prometheus `limit` vs Pinpoint `limit`） | 批量任务难以统一预算控制 | 引入统一 `QueryBudget`（最大条数/最大页数/总超时） |
| 6 | ES 无固定 schema | T10 依赖 4 个环境变量，换集群即失效 | 启动时调 `get_mappings` 自检字段，缺失则在巡检报告里显式提示"字段未对齐" |
| 7 | 主机标识四套并存（IP / IP:port / hostName / node） | `instance` 前缀匹配易误配 | 保持 `NormalizeHost` + 严格归属二次校验；新增主机必须先落 identity |
| 8 | 应用标识两套（Pinpoint applicationName / EasyViews projectName / 平台 appId） | 排障可能匹配错应用 | 用 `build_app_mapping_tool` 的思想做一张三方映射表，落 identity；模糊包含匹配降级为"候选"而非"命中" |
| 9 | ES 上游服务默认不注册（`ES_MCP_URL` 为空） | 日志巡检恒 `NO_DATA` | 部署清单里把 ES 作为"可选但建议"项显式标注，避免误读为"无日志异常" |
| 10 | `up` 聚合为覆盖写（`up[host] = value`） | 同一主机多个 exporter 序列时，最后一条掩盖前一条的 0 | 改为"任一序列为 0 即失联"，或在 `map` 中保留切片后聚合 |

### 14.2 能力编排缺口（工具已有、平台未用）

| 优先级 | 能力 | 用哪个工具 | 价值 |
|---|---|---|---|
| P0 | 单笔慢调用下钻 | pinpoint `get_transaction_trace_tool` | 从"服务级"下钻到"单次请求"，补齐排障最后一公里 |
| P0 | 指标 ↔ 链路打通 | prometheus `exemplar_query` | 拿到 exemplar 里的 traceId，与上一条形成闭环 |
| P1 | 变更关联 | cmdb `project_deployment_query` | 排障时自动比对"故障前是否有发布"，直接给出变更嫌疑 |
| P1 | 架构风险常态化 | pinpoint `analyze_link_topology_tool` + `analyze_host_concentration_tool` | 环依赖、长调用链、宿主机集中部署，从"事后排障"提前到"事前体检" |
| P2 | 外网暴露面 | cmdb `server_public_ip_query` | 与安全/合规打通 |
| P2 | ES 字段自发现 | es `get_mappings` | 消除硬编码字段配置 |
| P3 | 规则治理 | prometheus `list_rules` | 规则覆盖率 / 空规则 / 长期不触发规则盘点 |

### 14.3 建议的平台侧目标数据模型

```
AppIdentity
  appId, apolloAppId, apolloAppName
  pinpointAppId, pinpointAppName
  easViewsProjectName, deployNode
  cmdbProjectId, cmdbProductId
  hosts[]

HostIdentity
  key（归一键）
  ips[], hostNames[], addrs[]
  cmdb: {id, node(机房), state, operA, operB, usingBy, environment, specification, productProjectList}
  prom: {instance[], up, cpuUsage, memUsage, diskUsage, load, ...}
  es:   {index, errorCount(lookback), lastLogAt}
  pinpoint: {middlewareType, instanceCount}

Evidence（统一证据条目）
  source, tool, args, latencyMs, status(ok/error/skipped)
  window {from, to, unit}
  payloadPreview（≤4KB）+ 关键指标摘要
```

这套模型能把四个服务的返回**收敛成两类实体（应用、主机）+ 一条证据**，而不是让每个业务模块各自解析各家的 JSON。
