### 0. 术语与判态

| 术语 | 含义 |
|---|---|
| 上游 | 数据提供方：Pinpoint / Prometheus(+Alertmanager) / CMDB / ES，或平台内部产出键（拓扑、身份表） |
| 下游 | 数据消费方：落盘集合、规则判定、接口响应、前端页面 |
| 硬门禁 | 不满足则**不允许**发起调用或不允许流转，必须显式判态 |
| 软条件 | 不满足只降低置信度，流程继续 |
| 判态 | `NOT_TRIGGERED` / `RISK` / `NO_DATA` / `NOT_APPLICABLE`；优先级 `NO_DATA > RISK > NOT_TRIGGERED` |
| DF-nn | 数据流编号，用于跨文档引用 |

### 2. 统一接入层契约

#### 2.1 调用壳（A1 A2 A5）

| 项 | 契约 |
|---|---|
| 签名 | `Gateway.Call(ctx, server, tool, args) (json.RawMessage, error)` |
| 注册名 | `pinpoint` / `prometheus` / `cmdb` / `es`（仅这四个） |
| 传输 | streamable HTTP（MCP 协议），端点 `.../mcp` |
| 超时 | 单次 `context.WithTimeout(MCP_TIMEOUT_MS=8000)`；巡检批次 `INSPECT_MCP_TIMEOUT_MS=5000` |
| 名单 | 先 deny 后 allow；deny 命中即 `tool denied`；生产 `MCP_ALLOW_TOOLS` 按服务收敛 |
| 审计 | `CallLog{Server,Tool,Args,OK,Error,LatencyMs,At}` → `GET /api/mcp/logs` |
| 截断 | `Result.Preview(4096)`，超限标 `truncated:true` |

**硬约束**：业务模块禁止直连 HTTP；新增工具必须先在本文补齐"五段式"（上游条件 / 请求 / 响应 / 映射 / 断裂判态）。

#### 2.2 三种返回形态归一（A3）

| 形态 | 特征 | 归一 |
|---|---|---|
| 上游返回信封 | `{content:[{type:"text",text}],isError}` | `mcp.ResultOf` → `{Text,Payload,IsError}` |
| 裸业务 JSON | 直接对象/数组 | `mcp.ContentJSON` → `[]byte` |
| 文本内再套 JSON | `content[0].text` 是 JSON 字符串（CMDB） | `ResultOf` → `Payload` 二次 `Unmarshal` |

**统一顺序**：`ResultOf` 判 `IsError` → 取 `Payload` → 服务专用解析 → 失败转 `NO_DATA` 并保留 `preview`。

#### 2.3 字段口径（A4 F1 F2）

| 维度 | 统一口径 | 各服务差异 |
|---|---|---|
| 时间戳 | 平台内部**毫秒** | Pinpoint 收毫秒；Prometheus `query` 返秒、`range_query` 收 RFC3339；ES 用 `now-15m` |
| 主机键 | `NormalizeHost`：去空格 → 小写 → 去 `:port` → 去尾点 | CMDB 用 `ip`；Prometheus 用 `instance`；ES 用 `host`；Pinpoint 用 `middlewares[].name` |
| 应用键 | `appId / apolloAppId / apolloAppName / pinpointAppName` | Pinpoint 只认 `applicationName` 原值 |
| 状态码 | 巡检四态 | CMDB `state` 是资产状态，不是巡检判态 |
| 空集合 | 按工具语义解释，**不默认健康** | 告警空=无活跃告警；资产空=`P1` 账实不符 |

#### 2.4 失败 → 判态（A3 G3）

| 失败 | `Step.Status` | 业务判态 | 是否继续 |
|---|---|---|---|
| `connection refused` / 超时 | `error` | `NO_DATA` | 继续 |
| `unknown server` / `tool denied` | `skipped` | 数据端不可用 | 继续 |
| `isError:true` | `error` | 该步失败 | 继续 |
| JSON/文本均解析失败 | `warn` | `NO_DATA` + `preview` | 继续 |
| 空集合 | 按语义 | 见各服务 | 继续 |
| 字段缺失 | `warn` | `NO_DATA`，**不猜默认值** | 继续 |

#### 2.5 幂等 / 并发 / 重试（新增，I2 H6）

| 场景 | 约定 |
|---|---|
| 排障调用 | 每个会话每工具**最多调用 1 次**，不重试；失败即 `error` |
| 巡检调用 | 批次内同一 `(server, tool, hostKey)` 只调用 1 次（`hostMCPCache`） |
| 告警入库 | 按 `fingerprint` upsert，重复推送不改事件数 |
| 超时重试 | 不自动重试；由下一轮轮询/巡检自然补偿 |
| 并发 | 巡检单协程顺序执行；跨会话并发由网关连接池控制 |

#### 2.6 安全边界（新增）

| 约束 | 说明 |
|---|---|
| 只读 | 平台只消费查询类工具；`MCP_DENY_TOOLS` 必须保留 5 个写操作（`delete_series,clean_tombstones,snapshot,reload,quit`） |
| 凭据 | URL 中如带 token，不得写入 `Step.Args` / `CallLog.Args` |
| 数据出域 | 证据链只存 `Preview(4096)`；原始响应不得落盘到前端可下载路径 |
| 越权 | 多租户查询必须以 `tenantId` 过滤，工具参数中不传其他租户标识 |

### 3. Pinpoint 契约

#### 3.1 上游前置条件（B1 B2）

| # | 条件 | 不满足后果 |
|---|---|---|
| P-1 | `PINPOINT_MCP_URL` 可达，Pinpoint Web/Agent 正常 | ① 直接 `skipped` |
| P-2 | 目标应用已注册采集（有 Agent 上报） | 清单命中但服务地图空窗 |
| P-3 | `service_name` 正确（默认 `DEFAULT`） | 返回空应用清单 |
| P-4 | 时间窗内存在采样 | 服务地图 `NO_DATA` |
| P-5 | 平台已完成应用三方映射 | 无法把 `appId` 翻译为 `applicationName` |

#### 3.2 `list_applications_tool`（B1 B3）

**请求**

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `service_name` | string | 是 | `DEFAULT` | 项目组/服务名 |
| `clear_cache` | bool | 否 | false | 强制刷新缓存 |

**响应**

| 项 | 契约 |
|---|---|
| 路径 | `Payload` 数组，或 `{applications}` / `{applicationList}` / `{data}` |
| 必读 | `applicationName`（必）、`applicationId`（必） |
| 可选 | `serviceTypeName`、`serviceTypeCode` |
| 别名 | `applicationName\|appName\|name`、`applicationId\|appId\|id` |
| 平台结构 | `[]mcp.PinpointApplication{ID,Name,ServiceTypeCode,ServiceTypeName}` |

```json
[{"applicationName":"order-api","applicationId":"order-api^1780000000",
  "serviceTypeName":"SPRING_BOOT","serviceTypeCode":1210}]
```

**映射**

| 源字段 | 归一 | 平台字段 | 下游 |
|---|---|---|---|
| `applicationName` | 去空格；空则整条丢弃 | `.Name` | `identity_app.PinpointAppName`（DF-01） |
| `applicationId` | 去空格 | `.ID` | `identity_app.PinpointAppID` |
| `serviceTypeName` | 直取 | `.ServiceTypeName` | 排障展示 / T8 消歧 |

**下游硬依赖**：`get_server_map_tool.application_name` 只能取本工具 `Name` 原值。

**断裂判态**

| 情形 | 判态/动作 |
|---|---|
| 空数组 | `skipped`；② 记 `skipped` + "应用清单未匹配，调用链证据缺失（NO_DATA 口径）" |
| 单条缺 `applicationName` | 丢弃该条 |
| 调用失败 | `error`，不阻断 |

#### 3.3 `get_server_map_tool`（B2 G1 H2）

**请求**

| 字段 | 类型 | 必填 | 默认 | 单位 |
|---|---|---|---|---|
| `application_name` | string | 是 | — | 必须为 3.2 原值 |
| `from_ts` | int | 是 | — | **Unix 毫秒（13 位）** |
| `to_ts` | int | 是 | — | **Unix 毫秒** |
| `caller_range` | int | 否 | 1 | 上游层数 |
| `callee_range` | int | 否 | 1 | 下游层数 |
| `bidirectional` | bool | 否 | true | 双向 |
| `was_only` | bool | 否 | false | 仅 WAS |
| `service_type_code` | int | 否 | — | 同名消歧 |
| `service_type_name` | string | 否 | — | 同名消歧 |

**响应**

| 路径 | 字段 | 类型 | 必读 |
|---|---|---|---|
| `nodes \| nodeData \| node_data \| applicationData` | `applicationName` | string | 是 |
| 同上 | `serviceType` / `instanceCount` | string / int | 否 |
| `middlewares` | `name` / `type` | string | 否 |
| `links \| linkData` | `from \| source \| caller` | string | 是 |
| 同上 | `to \| target \| callee` | string | 是 |
| 同上 | `count` / `errorCount` / `responseTime` | int / int / float | 否 |

```json
{"nodes":[{"applicationName":"order-api","serviceType":"SPRING_BOOT","instanceCount":2}],
 "middlewares":[{"name":"mysql-prod-01","type":"MYSQL"}],
 "links":[{"from":"gateway","to":"order-api","count":1820,"errorCount":3,"responseTime":42.5}]}
```

**映射与流转**（DF-02）

| 源字段 | 平台结构 | 下游 |
|---|---|---|
| `nodes[]` | `.Nodes` | 排障"服务节点 N 个"；证据链原文 |
| `middlewares[]` | `.Middlewares` | 与拓扑中间件对齐 |
| `links[].errorCount/responseTime` | `.Links` | T8 按异常量/耗时取 Top N → `RISK` |
| 未知字段 | `.Raw` | 解析失败不阻断，仅降置信度 |

**有数据判据**：`len(Nodes)>0 || len(Links)>0`；否则 `NO_DATA`。

**断裂判态**

| 情形 | 判态 |
|---|---|
| `from_ts/to_ts` 传秒 | 空窗 → `NO_DATA`（Args 保留时间窗便于复核） |
| 应用名非原值 | 空/报错 → `NO_DATA` |
| 窗口内无采样 | `NO_DATA` |

### 4. Prometheus 契约

#### 4.1 上游前置条件（C1–C4）

| # | 条件 | 不满足后果 |
|---|---|---|
| M-1 | `PROMETHEUS_MCP_URL` 可达 | 全部步骤 `skipped` |
| M-2 | `node_exporter` 已纳管，`instance` 为 `IP` 或 `IP:port` | `up` 无序列 → `NO_DATA` |
| M-3 | 告警规则已配置 | `list_alerts` 空 = 无活跃告警（合法） |
| M-4 | 指标名与 `host_metrics_realtime` 约定一致 | 四项全缺 → `NO_DATA` |
| M-5 | 需抑制态时 Alertmanager `/api/v2/alerts` 同源可达 | 缺 `silenced/inhibited` |
| M-6 | exemplar 采集开启（仅 K1 用） | `exemplar_query` 空 |

#### 4.2 `list_alerts`（C1 I1 I2）

**请求**：`{}`（全量活跃告警）

**响应**

#### 4.3 `query`（up 存活，C2 H1）

**请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | `up{instance=~"^h1(:[0-9]+)?$\|^h2(:[0-9]+)?$"}` |

**构造硬规则**：`NormalizeHost` → `regexp.QuoteMeta` → `^host(:[0-9]+)?$` → 去重 → `|` 连接；全空不发起调用。

**响应**

| 形态 | 样例 | 解析 |
|---|---|---|
| 文本行 | `{instance="10.1.2.3:9100"} => 1 @[1756143048]` | 时间戳为秒 |
| 结构 | `data.result[].metric / value[1]` | `PrometheusSamples` |

**映射与流转**（DF-04）

| 源字段 | 校验 | 平台结构 | 下游 |
|---|---|---|---|
| `metric.instance` | `aliasToHost[NormalizeHost(instance)] == Host.Key`，否则丢弃 | `map[hostKey]float64` | T7；`collectCMDB` 的 `up` 入参 |
| `value` | 1 存活 / 0 失联 | 同上 | 与 `state` 交叉判定 |

**聚合规则（J10 修正）**：同一主机多条序列 → **任一为 0 即判 0**（失联）；不得覆盖写。

**断裂判态**

| 情形 | 判态 |
|---|---|
| 无匹配序列 | `NO_DATA`（未纳管/标签不一致），不判健康 |
| 归属校验失败 | 丢弃该序列 |
| PromQL 全空 | 不调用 → `NO_DATA` |

> 反例锁：`10.1.2.3` 不得吃掉 `10.1.2.30`。

#### 4.4 `host_metrics_realtime`（C3 H5）

**请求**：`{"node":"10.1.2.3"}`（也接受 `ip`）

**响应**

| 路径 | 说明 |
|---|---|
| `Payload.metrics` / `Payload.data.metrics` / 平铺 | 指标键值 |

| 字段 | 类型 | 单位 | 必读 |
|---|---|---|---|
| `cpuUsage` | float | % | 是 |
| `memUsage` | float | % | 是 |
| `diskUsage` | float | % | 是 |
| `netConnections` | int | 个 | 是 |
| 其余（cpuCores/load/netTraffic/diskIO/tcpOverflow…） | — | — | 否 |

**判定**

| 指标 | 阈值 | `P1` 升级 |
|---|---|---|
| CPU | > 85% | ≥ 95% |
| 内存 | > 85% | ≥ 95% |
| 磁盘 | > 90% | ≥ 95% |
| TCP 连接 | > 5000 | ≥ 2×（10000） |

**流转**（DF-05）：`metrics` + `thresholds` → `Finding.Evidence`；`depApps` → `Finding.Impact` → 报告/工单。

**断裂判态**：`Metrics` 空 / 四项全缺 → `NO_DATA`；部分缺失只判存在项并标注。

**解析**：`esIndexNames` 先试数组，再退回文案。

#### 6.3 `search`（E2 H4）

**请求**

|---|---|---|---|
| `index` | string | 是 | 与 `list_indices` 一致 |
| `query_body` | object | 是 | 固定结构见下 |

```json
{"size":0,"track_total_hits":true,
```

#### 9.2 `up` × `state` 交叉判定

| `up` | CMDB `state` | 结论 | 指向 |
|---|---|---|---|

| 0 | 无记录 | **疑似黑户/脏数据** | 先查 CMDB 录入 |

### 10. 关键时序

#### 10.1 排障（G1–G4）

```
POST /api/diagnose/sessions {appId | middlewareType+addr}
  → topo.ImpactByApp                    （本地｜影响面）
  → resolveAppIdentity                  （identity_app）
  → C1 list_alerts                      门禁：无
  → C2 query(up)                        门禁：候选主机非空
  → 【M2 验真】healthy → targets_metadata → series → E5 get_shards
                                        门禁：DIAG_VERIFY_ENABLED；失败写 sourceHealth 并降级
  → D2 cmdb_server_query                门禁：主机是 IP，≤5 台
  → B1 list_applications_tool           门禁：appId 非空；未命中 → 后续 Pinpoint 步骤 skipped
  → B2 get_server_map_tool              门禁：① 命中
  → C4 range_query                      门禁：候选主机非空；采样点 <2 判 NO_DATA
  → B4 drag_heatmap_tool                门禁：② 有数据；无 traceIds 则跳过 trace
  → B5 get_transaction_trace_tool       门禁：traceId 非空；非根 span ≥50% 判瓶颈
  → E2 search（ES，失败回退本地 log-analyzer） 门禁：候选主机非空
  → buildTicket → rank（证据集推导置信度）
  → SSE /api/diagnose/sessions/:id/stream
```

> 共 12 个上游接口调用点（Pinpoint 4 / Prometheus 6 / CMDB 1 / ES 2）。验真 4 个工具的结果写入 `sourceHealth`（`healthy`/`targets_metadata`/`series` 三条 promthus 记录 + `get_shards` 一条 es 记录），**不单独追加 `Step`**，因此会话 `steps` 通常为 10–11 条。`DIAG_VERIFY_ENABLED=false` 时写一条 `skipped` 记录，其余流程不变。

#### 10.2 巡检（H1–H6）

```
POST /api/inspect/tasks/:id/run
  → collectScopeHosts（≤ MAX_HOSTS，按被依赖应用数降序）
  → hostMCPCache（同主机同批次只查一次）
      T7  → C2 query(up)
      T9  → D2 cmdb_server_query
      T10 → E1 list_indices（一次） + E2 search（逐主机）
      T11 → C3 host_metrics_realtime
  → Finding（四态 + Evidence + Impact）
  → GET /api/inspect/runs/:id/report
```

#### 10.3 告警闭环（I1–I4）

```
POST /api/alarms/poll（或 webhook）
  → C1 list_alerts + Alertmanager /api/v2/alerts
  → mergeAlerts（fingerprint 合并，补抑制态）
  → fingerprint 幂等 upsert
  → 四道准入
  → POST /api/diagnose/sessions（复用 10.1）
  → root_caused → 工单 / 知识库
```

### 14. 上游契约变更管理

| 场景 | 检测方式 | 处理 |
|---|---|---|
| 上游字段改名 | 解析成功率下降、`NO_DATA` 上升 | 先补别名（不改业务），再通知上游 |
| 上游新增字段 | 无需处理 | 需要用时走"五段式"补契约 |
| 时间单位变更 | 服务地图空窗 / 曲线错位 | 在 A4 适配层修正，不改调用方 |
| 分页上限调整 | 覆盖度下降 | 调 `IDENTITY_CMDB_PAGES` / `PAGE_SIZE` |
| ES mapping 变更 | T10 单机全 0 | E3 自检报警 + 会话内提示 |
| 工具被上游下线 | `tools/list` 缺失 | 网关启动自检记录缺失工具，功能判 `NO_DATA` |

**原则**：契约变更只允许在网关适配层吸收（A3/A4），业务模块（G/H/I）不得因上游字段变化而改动。

### 15. 报文样例（可直接作为测试 fixture）

> 样例用于断言解析路径与字段口径，**值可替换，形态不可替换**。与 §13 验收断言一一对应。

#### 15.1 Pinpoint

**`list_applications_tool` — 形态 A（envelope + text 内套 JSON 字符串）**

```json
{"content":[{"type":"text","text":"[{\"applicationName\":\"order-api\",\"applicationId\":\"order-api^1780000000\",\"serviceTypeCode\":1210,\"serviceTypeName\":\"SPRING_BOOT\"}]"}],"isError":false}
```

| 断言点 | 期望 |
|---|---|
| `ResultOf` | `Payload` = 数组，长度 1 |
| `Name/ID` | `order-api` / `order-api^1780000000` |
| 缺 `applicationName` 的条目 | 丢弃，不报错 |

**`get_server_map_tool` — 形态 B（裸业务 JSON，字段走别名）**

```json
{"nodes":[{"applicationName":"order-api","serviceTypeName":"SPRING_BOOT","instanceCount":2}],
 "middlewares":[{"name":"mysql-prod-01","type":"MYSQL"}],
 "links":[{"fromApplicationName":"gateway","toApplicationName":"order-api",
           "callCount":1820,"errorCount":3,"avgResponseTime":42.5}]}
```

| 断言点 | 期望 |
|---|---|
| 节点路径 | `nodes` 命中，`Nodes` 长度 1 |
| 边别名 | `fromApplicationName/toApplicationName/callCount/avgResponseTime` 全部可解 |
| 空窗样例 | `{"nodes":[],"links":[]}` → `NO_DATA`，**不得**判 `NOT_TRIGGERED` |

#### 15.2 Prometheus

**`list_alerts` — 形态 A（大写 `Value` 是已知坑）**

```json
{"alerts":[{"labels":{"alertname":"HostDown","instance":"10.1.2.3:9100","severity":"critical"},
            "annotations":{"summary":"主机不可达"},
            "state":"firing","activeAt":"2026-11-05T10:00:00Z","Value":"1"}]}
```

| 断言点 | 期望 |
|---|---|
| `labels.instance` → `Host` | `10.1.2.3`（去端口、小写） |
| `fingerprint` | `hostdown\|10.1.2.3:9100\|critical` |
| 缺 `severity` | 回落 `info`，仍入库 |

**`query`（up）— 形态 C（纯文本行，时间戳为秒）**

```
{instance="10.1.2.3:9100", job="node"} => 1 @[1756143048]
{instance="10.1.2.3:9101", job="node"} => 0 @[1756143048]
```

| 断言点 | 期望 |
|---|---|
| 聚合 | 同一主机两条序列 → **判 0（失联）**，覆盖写是缺陷 |
| 归属 | 若 `aliasToHost` 无 `10.1.2.3` 映射，两条均丢弃 → `NO_DATA` |
| 反例 | `{"instance":"10.1.2.30:9100"} => 1` 不得把 `10.1.2.3` 判活着 |

**`host_metrics_realtime` — 形态 A（`metrics` 平铺）**

```json
{"node":"10.1.2.3","metrics":{"cpuUsage":91.2,"memUsage":78.4,"diskUsage":93.1,
 "netConnections":12030,"load1":3.1,"cpuCores":8}}
```

| 断言点 | 期望 |
|---|---|
| 判定 | CPU 91.2 > 85、磁盘 93.1 > 90、连接 12030 ≥ 2×5000 → `RISK` + **`P1`** |
| `Evidence` | 含 `metrics` 与 `thresholds` 两组值 |
| 四项全缺 | `{"node":"10.1.2.3","metrics":{}}` → `NO_DATA` |

**`range_query` — 形态 A（matrix）**

```json
{"status":"success","data":{"resultType":"matrix","result":[
 {"metric":{"__name__":"node_cpu_usage","instance":"10.1.2.3:9100"},
  "values":[[1756142700,"42.1"],[1756143000,"78.6"]]}]}}
```

| 断言点 | 期望 |
|---|---|
| 时间单位 | `values[][0]` 为**秒**，平台内部转毫秒 |
| 单点 | `values` 只有 1 项 → `NO_DATA`（采样点不足） |
| 增长率 | `(78.6-42.1)/((1756143000-1756142700)/60)` = 73/分钟，用于劣化规则 |

#### 15.3 CMDB

**`cmdb_server_query` — 形态 C（双层编码，必须二次 `Unmarshal`）**

```json
{"content":[{"type":"text","text":"{\"code\":200,\"message\":\"success\",\"fail\":false,\"data\":{\"records\":[{\"id\":\"cmdb-1001\",\"ip\":\"10.1.2.3\",\"hostName\":\"vm-order-01\",\"node\":\"华东-云公司-A\",\"state\":0,\"operA\":\"zhang.san\",\"operB\":\"li.si\",\"environment\":\"prod\",\"specification\":\"8C16G\"}],\"total\":1,\"currentPage\":1,\"pageSize\":5,\"pages\":1}}"}]}
```

| 断言点 | 期望 |
|---|---|
| 二次解码 | `ResultOf.Payload` 再解 → `data.records` |
| `state=0` | `Online=true`，与 `up=1` 组成健康象限 |
| `state=4/6` 且被应用引用 | 判 `P1`（报废/清退仍在承载） |
| 无 `state` 字段 | `NO_DATA`，**不猜默认在线** |
| 空记录 | `records:[]` → `P1` 账实不符 |

#### 15.4 Elasticsearch

**`list_indices` — 形态 C（文案 + JSON 混排）**

```json
{"content":[{"type":"text","text":"Found 2 indices:\n[{\"index\":\"logs-app-2026.11.05\",\"status\":\"open\",\"docs.count\":\"128340\"},{\"index\":\"logs-gateway-2026.11.05\",\"status\":\"open\",\"docs.count\":\"99210\"}]"}]}
```

**`search` — 形态 C（统计文案 + 原生 hits）**

```json
{"content":[{"type":"text","text":"Total results: 37\n{\"hits\":{\"total\":{\"value\":37,\"relation\":\"eq\"},\"hits\":[]}}"}]}
```

| 断言点 | 期望 |
|---|---|
| 计数 | 优先正则 `Total results: (\d+)` → 37 |
| `relation=gte` | 样例改为 `{"value":10000,"relation":"gte"}` → 报告标注"计数为下限" |
| 阈值 | 37 > 20 → `RISK`；≥100 → `P1` |
| `total=0` | 有效值，判 `NOT_TRIGGERED`，不是 `NO_DATA` |

### 0. 结论速览

| 结论 | 说明 |
|---|---|
| 四个服务不是同一种"数据源" | Pinpoint = **调用链/服务地图**；Prometheus = **时序指标+告警**；CMDB = **资产台账**；ES = **日志检索**。它们通过"主机/应用"两个维度缝合成一条证据链。 |
| 平台的唯一入口是统一接入网关 | 所有调用都走 `internal/mcp.Gateway`（白名单/黑名单 + 超时 + 探针 + `tool_call_log` 审计），业务模块不直连服务。 |
| 返回形态三态并存 | 标准 上游返回信封、裸业务 JSON、`content[0].text` 里再套一层 JSON 字符串。平台用 `mcp.ResultOf` / `ContentJSON` 统一归一。 |
| 真正的关联主键只有 4 个 | `applicationName/appId`（应用）、`ip/hostName`（主机）、`instance="IP:port"`（Prometheus 序列）、`traceId`（单次调用）。ES 没有固定业务主键，靠字段约定。 |
| 平台当前消费了 15 个工具 | 四个服务合计 71 个工具，平台实际用到 15 个（Pinpoint 4 / Prometheus 7 / CMDB 1 / ES 3，详见 §8 矩阵与 §9 字段契约）；其余属于"能力已具备、平台未编排"。 |
| 最大缺口是"对齐口径" | 时间戳单位（秒/毫秒/RFC3339）、分页口径（page/size vs limit/offset）、主机标识（IP vs hostName vs node）、Pinpoint 应用名与平台 appId 的映射。 |

#### 0.1 标记约定：**★【故障发现】** = 第一步发现问题所用的工具

本文件在 §3.1 / §4.1 / §5.1 / §6.1 的工具介绍列，用 **★【故障发现】** 标出**平台第一步排障 / 发现故障**的入口工具。判据只有一条：**能在无人工介入的情况下，自己产生一个新的问题信号**。

| 发现信号 | 工具 | 判据 | 所在章节 |
|---|---|---|---|
| 告警触发（被动，最快） | `list_alerts` | `state=firing` 且 `severity` 达阈值且未被抑制 | §4.1 告警与规则 |
| 实例不存活 | `query`（`up`） | `up==0`（同主机多条序列取任一为 0） | §4.1 查询类 |
| 资源指标越界 | `host_metrics_realtime` | CPU / 内存 / 磁盘 / TCP 连接数超阈值 | §4.1 主机类 |
| 错误日志激增 | `search` | 时间窗内 `level=error` 计数超基线（前置 `list_indices`） | §6.1 |
| 调用边异常 | `get_server_map_tool` | 边上的错误数、响应时间超阈值 | §3.1 应用/服务地图 |
| 资产缺失或账实不一致 | `cmdb_server_query` | 有监控无资产、有资产无监控 | §5.1 |

共 **6 个**。其余 62 个工具不产生新信号，作用分别是：**定位下钻**（如 `get_transaction_trace_tool`）、**判因**（如 `targets_metadata`、`get_shards`）、**自检**（如 `healthy`、`build_info`）、**治理**（如 `build_app_mapping_tool`）、**禁用**（写操作 5 个）。

> 注意：`list_indices` 是 `search` 的前置索引发现，本身不判定好坏，因此不标记为故障发现；`search` 命中数异常才构成信号。

##### 0.3.2 改造前的调用顺序（as-is，归档）

`execute()` 改造前为单次串行 6 段，共 5 次上游接口调用：

| 段 | 函数 | 位置 | 调用的工具 |
|---|---|---|---|
| ① 拓扑影响面 | `collectImpact` | `engine.go:249` | 无（本地拓扑数据） |
| ② 应用清单 + 服务地图 | `collectPinpoint` | `engine.go:278` | `list_applications_tool`、`get_server_map_tool` |
| ③ 告警 + 目标存活 | `collectPrometheus` | `engine.go:381` | `list_alerts`、`query`（`up`） |
| ④ 资产归属 | `collectCMDB` | `engine.go:502` | `cmdb_server_query` |
| ⑤ 根因排序 | `rank` | `engine.go:749` | 无（纯本地规则） |
| ⑥ 日志证据 | `collectLogEvidence` | `engine.go:873` | log-analyzer（非上游服务） |

三个结构性问题：

- **定因先于取证**：`rank` 在 ⑥ 之前，日志是结论出来后补的附加信息，不是证据链输入。
- **无验真环节**：`up=0` 直接进入候选排序，没有 `healthy` / `targets_metadata` / `series` 判别「采集故障」与「业务故障」。
- **`rank` 隐式耦合**：通过反查 `sess.Steps` 取 `list_alerts` 的 `matchedKeywords`，步骤顺序一变即失效。

##### 0.3.3 已落地的调用顺序（implemented）

```
0) collectImpact      拓扑影响面    —— 产出候选主机与被影响应用（定界初算）
1) collectPrometheus  发现          —— list_alerts + query(up)，up=0 保留标记
2) collectVerify      数据源验真    —— healthy → targets_metadata → series → get_shards
3) collectCMDB        确认与定界    —— cmdb_server_query（归属/在线状态）
4) buildTicket        生成问题单    —— 实体/级别/信号/时间窗/影响面/可信度
5) collectPinpoint    定位          —— list_applications_tool + get_server_map_tool
6) collectRange       取证·基线     —— range_query(node_load1, 近 60m, step=60s)
7) collectTrace       取证·调用链   —— drag_heatmap_tool → get_transaction_trace_tool
8) collectLog         取证·日志     —— ES search（按候选主机）→ 失败回退 log-analyzer
9) rank               定因          —— 证据集驱动：来源数 + 条数 → 置信度
```

与原方案的两处偏差（均为实现时修正）：

1. **验真提前到 CMDB 之前**：先判断「数据源是否可信」，再解释资产/信号，避免用不可信数据做归属判断。
2. **问题单在定位前生成**：第 2 步结束即可定界并开单，后续取证只补充证据，不改变实体与级别（除非出现更严重的信号）。

>
> **指标双通道**：`pinpoint-mcp` 内部的 `prometheus_query_tool`、`arch_metric_query_tool`、`arch_rule_check_tool`、`arch_label_probe_tool` 直连 `PROMETHEUS_BASE_URL`，与 `promthus-mcp` 的 `query`/`range_query` 构成两条可达路径，且截断与命名空间过滤策略不同。平台侧以 `promthus-mcp` 为指标权威源，`pinpoint-mcp` 的取数工具仅供架构分析内部使用。

### 2. 返回形态与平台适配层

#### 2.1 三种返回形态

| 形态 | 长什么样 | 典型服务 |
|---|---|---|
| A. 标准 上游返回信封 | `{"content":[{"type":"text","text":"..."}],"structuredContent":{...},"isError":false}` | 大多数 FastMCP / rmcp / go-sdk 工具 |
| B. 裸业务 JSON | 直接 `{"code":200,"data":{...}}` 或数组 | cmdb-mcp-server 在部分路径下、mock 服务 |
| C. 双重编码 | `content[0].text` 本身是**一段 JSON 字符串** | cmdb-mcp-server（`content[0].text` 为 stringified JSON）、Prometheus `query` 系列（text 是文本行） |

#### 2.2 平台统一解析

| 函数 | 位置 | 处理逻辑 |
|---|---|---|
| `mcp.ResultOf(raw)` | `internal/mcp/result.go` | 递归拆 `"..."` 裸字符串 → 识别 envelope → `structuredContent` 优先 → text 是合法 JSON 则作为 Payload，否则留在 `Text` |
| `mcp.ContentJSON(raw)` | 同上 | 遍历 `content[]`，取**第一个**能解析为 JSON 的 text 片段（专治 ES 的"统计文案 + JSON"混排） |
| `Result.Preview(max)` | 同上 | 生成落证据链的截断视图：`{bytes, data / preview, truncated, isError}` |
| `DecodeJSON[T]` | 同上 | 泛型解码业务 JSON |

**平台消费原则**：业务代码不直接摸 `content[0].text`，一律走上述适配层；解析失败时保留 `preview` 原文，结论按 `NO_DATA` 处理，绝不当作"健康"。

**入参时间单位速查（易错项）**

| 服务 | 工具范围 | 时间入参格式 | 单位 |
|---|---|---|---|
| Pinpoint | `get_server_map_tool`、`drag_heatmap_tool`、`get_transaction_trace_tool#focus_timestamp` | 整数时间戳 | **毫秒** |
| Pinpoint | `prometheus_query_tool#ts/start_ts/end_ts`、`arch_metric_query_tool#end_ts` | 整数时间戳 | **秒** |
| Pinpoint | `get_link_topology_tool#minute`、`analyze_link_topology_tool#minute` | 整数 | **分钟** |
| Prometheus | `query#timestamp`、`range_query#start_time/end_time`、`series`、`label_*`、`host_metrics_trend` | Unix 秒 / RFC3339 / 相对时长（`5m`、`1h30m`） | 三者皆收 |
| Prometheus | `query` / `range_query` 的返回 `values` | 浮点时间戳 | 秒 |
| Elasticsearch | `query_body` 内 `range` | ES 日期数学（`now-15m`）或 ISO8601 | 字符串 |

平台内部统一用**毫秒**，调用前必须按上表换算，禁止把毫秒直接传给 Prometheus 的 `*_time`。

#### 3.2 平台实际消费方式（Pinpoint）

**排障链路（`internal/diagnose/engine.go`）**

```
① list_applications_tool{service_name:"DEFAULT"}
   → 归一为 []PinpointApplication
   → FindPinpointApplication(ids=[pinpointId, appId], names=[pinpointName, appName, appId])
      匹配顺序：ID 精确 → 名称精确 → 名称包含
   → 未匹配：get_server_map_tool 记 skipped，证据链标注"NO_DATA 不等于无异常"

② get_server_map_tool{
     application_name: 匹配到的 Name,
     from_ts: now-window 的 UnixMilli,
     to_ts:   now 的 UnixMilli,
     caller_range: 1, callee_range: 1, bidirectional: true
   }
   → PinpointServerMapOf → 只消费 nodes 数、middlewares 数 + Preview 原文
```

**巡检链路（`inspect/trace_rules.go` T8）**：先用 `apolloAppName` 查，无数据回退 `appId`，最多 2 次；命中条件为 `len(nodes)>0 || len(links)>0`；消费 `links[].from/to/count/errorCount/responseTime` 取 Top N。

**身份映射链路（`identity/identity.go`）**：`list_applications_tool` 结果用于回填平台的 `PinpointAppID` / `PinpointAppName`，建立 `appKey ↔ Pinpoint 应用` 的双向别名。

**留白**：`get_transaction_trace_tool` 完全未被使用 —— 平台没有从 Pinpoint 采集 `traceId` 的入口，因此"单笔慢调用下钻"这条能力断了。这是最值得补的一环。

### 4. Prometheus 上游服务（36 个工具）

> **36 的口径**：这是并集。`--mcp.tools=all` 且 `--prometheus.backend=prometheus` 时为 35 个；`list_stores` 仅在后端为 `thanos` 时注册（同时移除 `alertmanagers/config/wal_replay_status/reload/quit`）。`reload`、`quit` 默认不注册，需显式开启生命周期开关。核心集 `core` 仅 9 个：`docs_list/docs_read/docs_search` + `query/range_query/metric_metadata/label_names/label_values/series`。
>
> **返回形态**：`query` / `range_query` / `exemplar_query` 的返回是 `{"result":"<字符串>","warnings":[...]}`，`result` 内为 `model.Value.String()` 文本行（如 `{instance="1.2.3.4:9100"} => 27.5 @[1782115200.000]`），**不是 JSON**；平台侧必须按文本解析，不能直接 `json.Unmarshal`。

##### 复杂返回结构详情

###### `range_query`

**介绍**：在 `start_time` 与 `end_time` 之间按 `step` 评估 PromQL，返回区间序列文本。未指定 `step` 时按约 250 个数据点自动计算。

**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| query | string | 是 | — | PromQL 表达式 |
| step | string | 否 | 自动（约 250 点） | Go 时长格式，必须为正，如 `30s`、`5m`、`1h` |
| start_time | string | 否 | `end_time - 5m` | Unix 秒、RFC3339 或相对时长 |
| end_time | string | 否 | 当前时间 | Unix 秒、RFC3339 或相对时长 |
| truncation_limit | int | 否 | 全局配置 | 负数表示本次调用禁用截断 |

**返回结构**：

```json
{
  "result": "{instance=\"192.168.7.66:9100\"} =>\n27.5 @[1782115200.000]\n27.8 @[1782115260.000]",
  "warnings": []
}
```

`result` 是 `model.Matrix.String()` 生成的纯文本（不是结构化 JSON），每条序列为 `{labels} =>` 后接若干行 `value @[timestamp]`；标量结果形如 `scalar: 27.5 @[1782115200.000]`。`warnings` 为上游告警数组或 `null`；发生截断时 `result` 末尾追加中文截断警告。

###### `list_alerts`

**介绍**：调用 `/api/v1/alerts` 返回全部活动告警，结果为 `AlertsResult` 的直接序列化。

**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| 无 | — | — | — | 工具不接受输入参数 |

**返回结构**：

```json

      "Annotations": {"summary": "CPU 使用率过高"},
```

`alerts` 来自 `promv1.AlertsResult`。`activeAt` 有 json tag；`Annotations`、`Labels`、`State`、`Value` 无 json tag，序列化后保持首字母大写。`State` 取值 `pending` 或 `firing`；无告警时为 `{"alerts":[]}`。

#### 4.2 平台实际消费方式（Prometheus）

| 场景 | 工具 | 参数 | 消费字段 | 产出 |
|---|---|---|---|---|
| 告警采集 | `list_alerts` | `{}` | `labels`（`alertname`/`instance`/`host`/`severity`…）、`annotations`、`state`、`startsAt`、`value` | 告警指纹幂等入库 |
| 排障·目标存活 | `query` | `up{instance=~"<host>.*"}` | `result[].metric.__name__`、`metric.instance`、`value[1]` | `up` map：主机 → 0/1 |
| 巡检 T7 | `query` | `up{instance=~"<alias>.*"}` | 同上；只认 `__name__=="up"` | 存活 RISK / NOT_TRIGGERED / NO_DATA |
| 巡检 T11 | `host_metrics_realtime` | `{node: host}` | 12 项指标（CPU/内存/磁盘/负载…） | 阈值判定 |
| 劣化扫描 | `range_query` | `{query, start_time:RFC3339, end_time, step:"300s"}` | `data.result[0].metric.__name__/instance`、`values[]` | 增长率超阈值 → 劣化告警 |
| 业务监控 | `query` | 自定义表达式 | 单值 | 业务指标规则 |
| 质差分析 | `range_query` | 自定义表达式 | P50/P90 时延 | 质差报告 |
| 稽核对账 | `query` | `up{instance=~"<host regex>"}` | 结果条数 >0 即"有心跳" | 佐证 CMDB 状态 |

**指纹与准入**：`list_alerts` 的 `labels` + `annotations` 共同决定 `fingerprint`；平台只对 `firing`、未抑制、且未关联会话的 P1 告警自动建单排障。

**告警双通道**：除 `list_alerts` 外，平台还会直连 Alertmanager `/api/v2/alerts`（不走上游接口），仅用于补全**抑制态与分组**，同一指纹视为同一条告警。

##### 分页与限额

- `cmdb_server_query` 的 pageSize 默认 15：HTTP 兼容层 `ServerQueryParams.pageSize` 与 `config/param_mappings.json` 的 `page_size_defaults` 均为 15，Mock 响应也按 15 返回；上游服务 inputSchema 本身未声明 default。
- 其余 4 个工具 inputSchema 均声明 `currentPage` 默认 1、`pageSize` 默认 40，且未声明上限。
- pageSize 上限仅由 `cmdb_server_query` 的 inputSchema 声明为 `maximum: 100`（`currentPage` 为 `minimum: 1`）；服务端不做校验或截断，参数原样转发后端，超限后的实际条数由后端决定（平台 identity 模块即传 `pageSize: 200`），源码无法确认后端行为。
- 分页字段归一：`server-public-ip-query`、`product-query`、`project-basis-query` 返回的 `current`/`size` 由 `_normalize_pagination` 改写为 `currentPage`/`pageSize`；`cmdb-server-query` 原生返回 `currentPage`/`pageSize`/`total`/`pages`；`project-deployment-query` 原样返回。
- `productIdList` 路径为本地分页：逐个 productId 拉全量（每页 page_size=100、每产品最多 200 页，即最多 2 万条，并发上限 6），按 id 去重合并后本地切片；其返回 `data` 使用 `size`/`current` 而非 `pageSize`/`currentPage`，`total` 为并集台数；`fields` 仅本地裁剪并附加 `data._trimmedFields`，不改变 `total`/`pages`。

**平台已编排（1 / 5）**：仅 `cmdb_server_query`（排障资产证据 / 巡检 T9 / 稽核 C1–C3 / 身份映射）；另外 4 个虽已实现，但需 `MCP_ENABLED_TOOLS` 显式开启才会注册到网关。

### 6. Elasticsearch 上游服务（5 个工具，全只读）

#### 6.1 工具契约总表

> 参数列格式 `名称:类型`，`*` 表示必填。本服务全部为只读工具，返回走上游接口 `content[]`，常见形态是「一行统计文案 + 一段 JSON」混排，平台需用 `ContentJSON` 取第一个可解析片段。

| 工具 | 介绍 | 请求参数 | 返回参数 |
|---|---|---|---|
| `list_indices` | 按索引模式列出索引名、健康状态、文档数与存储大小。是日志检索的前置步骤，用于确认索引是否存在；每批次只调一次，禁止逐主机调用。 | `index_pattern:string*` | 文案 + JSON 混排：`index`、`status`、`docs.count` |
| `get_mappings` | 获取指定索引的字段映射（字段名、类型、是否可聚合）。用于动态发现时间 / 级别 / 主机字段的真实名称，替代硬编码配置，是日志巡检前的字段自检手段。 | `index:string*` | 文案 + JSON 混排：`mappings.properties.<字段>.type` 及其余映射属性 |
| `search` | **★【故障发现】** 用 Query DSL 检索索引，支持字段筛选、查询体与聚合。返回「固定文案 + JSON」混排，计数优先取 Total results，兜底 hits.total，并需标注 relation 是否为 gte。 | `index:string*`、`fields:string[]`（可选，无默认）、`query_body:object*`（可传 JSON 字符串） | 文案 + JSON 混排：`Total results` 文案、命中 `_source` 数组、`Aggregations results` 文案与聚合对象 |
| `esql` | 执行 ESQL（管道式查询语言），返回列定义与行数据。适合探索性分析；结果依赖索引当前状态、不易复现，平台不作为证据链来源。 | `query:string*` | 文案 + JSON 混排：固定文案 `Results` + 由 `columns` 拼键的行对象数组 |
| `get_shards` | 获取全部或指定索引的分片分布、主副状态与未分配原因。用于把「查不到日志」判定为集群 / 分片问题，避免误报为无数据。 | `index:string`（可选，缺省即全部索引） | 文案 + JSON 混排：`index`、`shard`、`prirep`、`state`、`docs`、`store`、`node` |

##### 复杂返回结构详情

###### `search`

**介绍**：调用 `POST /<index>/_search`，请求体即 `query_body`，可含 `query`、`size`、`from`、`sort`、`aggs` 等任意 DSL。传入 `fields` 时服务端把字段名并入 `_source`（已有数组则追加，非数组则覆盖），用于收窄返回体。
**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `index` | string | 是 | 无 | 索引名或模式，支持 `logs-*`、逗号分隔多个 |
| `fields` | string[] | 否 | 无（不注入 `_source`） | 需要返回的字段名列表，合并进 `_source` |
| `query_body` | object | 是 | 无 | 完整 DSL 对象；也接受 JSON 编码的对象字符串，非对象或非法 JSON 直接报错 |

**返回结构**：`content[]` 内各项均为 text 类型，JSON 片段是序列化字符串：

```json
[
  { "type": "text", "text": "Total results: 128, showing 2." },
  { "type": "text", "text": "[{\"@timestamp\":\"2026-11-05T10:00:00Z\",\"level\":\"error\",\"host\":\"api-01\",\"message\":\"timeout\"},{\"@timestamp\":\"2026-11-05T10:00:01Z\",\"level\":\"warn\",\"host\":\"api-02\",\"message\":\"retry\"}]" },
  { "type": "text", "text": "Aggregations results:" },
  { "type": "text", "text": "{\"by_level\":{\"buckets\":[{\"key\":\"error\",\"doc_count\":9}]}}" }
]
```

说明：`Total results` 文案仅在「无聚合」或「有命中」时输出，命中为空时该文案缺省；无命中且仅有聚合时，`content[]` 只有聚合文案与聚合 JSON。`hits.total` 缺失时文案中的总数为 `unknown`。

###### `list_indices`

**介绍**：调用 `GET /_cat/indices/<index_pattern>?format=json&h=index,status,docs.count`，只返回三列。该工具不做聚合，返回条数与模式命中数一致。
**请求参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `index_pattern` | string | 是 | 无 | 索引通配模式，如 `*`、`logs-*`、`a-*,b-*`；无命中时返回 `Found 0 indices:` 与空数组 |

**返回结构**：

```json
[
  { "type": "text", "text": "Found 2 indices:" },
  { "type": "text", "text": "[{\"index\":\"logs-2026.11.05\",\"status\":\"open\",\"docs.count\":\"1024\"},{\"index\":\"logs-2026.11.04\",\"status\":\"open\",\"docs.count\":\"998\"}]" }
]
```

说明：`docs.count` 由 cat API 以字符串返回，反序列化为数字后再序列化，字段名保持带点的 `docs.count`；取该字段时需按原键名访问。

##### 字段约定与平台配置

- 本服务不定义任何业务 schema，`search`、`esql` 的全部分组、时间过滤与字段名都由调用方拼装，ES 侧索引映射才是唯一事实来源；`get_mappings` 是唯一可用于前置校验字段的工具。
- 默认索引模式由平台以 `ES_LOG_INDEX=logs-*` 约定，`list_indices` 的 `index_pattern`、`search`/`esql` 的索引部分都按该值填充；索引名不符时表现为 `list_indices` 返回 `Found 0 indices:`，或 `search` 报索引不存在。
- 时间字段由 `ES_LOG_TIME_FIELD=@timestamp` 约定，用于 `range` 过滤与 `sort`；字段不符时 `range` 查询命中为空或报 `unrecognized field`，时间维度聚合分桶为空。
- 级别字段由 `ES_LOG_LEVEL_FIELD=level`、主机字段由 `ES_LOG_HOST_FIELD=host` 约定，用于 term 聚合与过滤；实际字段名为 `log.level`、`severity`、`host.name` 等时，按约定名过滤或聚合得到空桶，且不报错。
- 上述 `ES_LOG_*` 变量只作用于平台侧的提示词与调用参数，源码未读取它们；服务自身仅读取 `ES_URL`、`ES_API_KEY`、`ES_USERNAME`、`ES_PASSWORD`、`ES_SSL_SKIP_VERIFY`（默认 `false`）、`ES_REQUEST_TIMEOUT_SECS`（默认 `30`），另有 `MCP_TOOL_PREFIX` 会给工具名加前缀。
- 连接层默认值以源码为准：请求超时 30 秒，超时或 ES 返回非 2xx 时工具以错误内容返回，不返回部分结果；配置 `MCP_TOOL_PREFIX` 后工具名变为「前缀 + 原名」，按原名调用将命中不到工具。

**平台已编排（2 / 5）**：`list_indices`（T10 前置索引发现）、`search`（T10 错误日志计数 / 排障日志证据）；`get_mappings` 作为字段名动态发现手段保留，`esql` 与 `get_shards` 未编排。

**源码核对补充（2026-11-13）**

- 无任何业务 schema 约定：索引名、`@timestamp`、`level`、`host` 全靠平台侧 `ES_LOG_*` 环境变量约定，仓库本身只出现 `logs-*` 示例。
- `list_indices` 的 `index_pattern` 必填且无默认值，必须显式传 `*` 或具体模式。
- `search` 的 `index`、`query_body` 均必填；不返回 `_id`、`_score`、`highlight`，只回 `_source`；`fields` 会合并进 `_source`。
- `get_mappings` 只取第一个命中索引，丢弃 settings 与索引名；是字段自发现的唯一手段。
- 返回为**多段 text**：先一行统计文案（`Found N indices:` / `Total results: N, showing M.` / `Found N shards:`），再一段 JSON，整段拼接不是合法 JSON，必须逐段解析。
- 双集群为两进程两端点（9090/9091），工具名相同靠 endpoint 区分；单实例 `url` 为单值，不支持同时连两个集群。

#### 6.2 关键约束与平台消费方式（T10）

**关键约束**：ES 没有固定业务 schema。平台通过环境变量约定字段（`ES_LOG_TIME_FIELD=@timestamp`、`ES_LOG_LEVEL_FIELD=level`、`ES_LOG_HOST_FIELD=host`），真实集群字段不同就必须改配置，否则 T10 恒为 `NO_DATA`。

**平台消费方式（T10 日志错误）**

```
① list_indices{index_pattern: "logs-*"}  → esIndexNames：JSON 数组优先，其次 "Found N indices:" 文案
   为空 → NO_DATA（"ES 中不存在匹配的日志索引"），不逐台主机刷噪音

② search{index, query_body}：
   {
     "size": 0, "track_total_hits": true,
     "query": {"bool": {
        "filter": [{"range": {"@timestamp": {"gte": "now-15m"}}}],
        "must": [
          {"query_string": {"query": "level:(ERROR OR FATAL OR error OR fatal)", "lenient": true}},
          {"query_string": {"query": "host:\"<host>\"", "lenient": true}}
        ]
     }}
   }

③ esTotalHits：先匹配 "Total results: N"，再取 hits.total（数字或 {value} 两种形态）
   > threshold(20) → RISK；≥ threshold*5 → P1；否则 NOT_TRIGGERED
```

### 9. 逐工具字段契约（平台流转接口细化）

#### 9.1 公共调用壳

平台**所有**上游接口调用都收敛到同一签名，业务模块只关心 `server / tool / args`：

```
Gateway.Call(ctx, server, tool, args) (json.RawMessage, error)
```

| 环节 | 规则 | 失败后果 |
|---|---|---|
| 注册检查 | `server` 必须在 `Servers()` 返回的已注册列表内 | 返回 `unknown server` |
| 名单检查 | 先 deny 后 allow；`server/*` 通配 | 返回 `tool denied` |
| 超时 | 每次调用独立 `context.WithTimeout(MCP_TIMEOUT_MS)` | 记 `CallLog{OK:false, Error:"context deadline exceeded"}` |
| 审计 | `CallLog{Server, Tool, Args, OK, Error, LatencyMs, At}` 进环形日志，`/api/mcp/logs` 可查 | 不影响业务 |
| 证据留痕 | `domain.Step{No, Source, Tool, Title, Status(ok/warn/error/skipped), Args, Result, LatencyMs, Error, At}` | `skipped` 不阻断后续步 |
| 结果收录 | `Result.Preview(4096)` 截断后写入 `Step.Result`，超限标 `truncated:true` | 原文保留在预览里，避免解析失败丢证据 |

`source` 实际取值有 6 个：`topo`（本地快照）、`pinpoint`、`promthus`、`cmdb`、`rule`（本地规则判定）、`log`（外部日志分析器）。`domain.Step` 的注释只列了前四个，实现已扩展；前端证据链按 `source` 渲染分组，新增工具必须归入这 6 类之一。

#### 9.5 `promthus.query`（up 存活）

| 项 | 内容 |
|---|---|
| 调用点 | 排障 step④；巡检 T7 |
| 请求 | `{"query":"up{instance=~\"^10\\.1\\.2\\.3(:[0-9]+)?$|^10\\.1\\.2\\.4(:[0-9]+)?$\"}"}` |
| 查询构造 | `identity.UpQuery(hosts)`：每个 host 经 `NormalizeHost` → `regexp.QuoteMeta` → 包成 `^host(:[0-9]+)?$` → 去重后用 `|` 连接；全部为空则**不发起调用** |
| 返回形态 | **文本行**：`{instance="10.1.2.3:9100", job="node"} => 1 @[1756143048]`，时间戳为**秒** |
| 必读字段 | `metric.instance`（必须能 `NormalizeHost` 后命中主机别名表）、`value`（`1` 存活 / `0` 失联） |
| 平台结构 | `map[hostKey]float64`（当前实现为覆盖写：同一主机多序列时**最后一条生效**；建议改为"任一为 0 即判失联"） |
| 前置条件 | ① `node_exporter` 已纳管；② `instance` 标签是 `IP` 或 `IP:port`；③ 标签值能被 `NormalizeHost` 归一 |
| 缺失行为 | 无匹配序列 → `NO_DATA`（提示"可能未纳管或标签不一致"），**不判健康**；序列命中但 `instance` 归属校验失败 → 丢弃该序列 |
| 下游流转 | ① T7 Finding；② 作为 `collectCMDB` 的 `up` 入参，与 CMDB `state` 交叉验证 |

> **严格归属校验**：PromQL 用正则做"候选召回"，平台再用 `aliasToHost[NormalizeHost(instance)] == 当前主机 Key` 做"精确归属"，避免 `10.1.2.3` 误吃 `10.1.2.30` 的序列。

#### 9.10 排障链路新增工具（M2–M5）

> 调用点：`internal/diagnose/engine.go`。以下 8 个工具在 M2–M5 接入，排障链路工具调用点由 8 个扩为 12 个（另 4 个为原有 `list_alerts` / `query` / `cmdb_server_query` / `list_applications_tool`）；验真 4 个工具不建 `Step`，会话证据链为 10–11 条。

| 工具 | 调用点（`execute()` 顺序） | 请求要点 | 必读字段 | 缺失 / 失败行为 |
|---|---|---|---|---|
| `promthus.healthy` | 第 3 步 验真 | 无参 | 任意 2xx 且 envelope 无 `isError` | 调用失败 → `sourceHealth[promthus]=unavailable`；后续 Prometheus 结论封顶 0.5 |
| `promthus.targets_metadata` | 第 3 步 验真 | `{"match_target":"<host>"}` | `data.activeTargets[].labels.instance`、`health`、`lastError` | 无此 target → `degraded`，detail 记「未纳管」；target 存在但 `health!=up` → `unavailable` |
| `promthus.series` | 第 3 步 验真 | `{"match[]":"up{instance=~\"<host>.*\"}"}` | `data[]`（非空即证明序列存在） | 空数组 → 该主机 `NO_DATA`；本步只写 `checks`，不阻断 |
| `promthus.range_query` | 第 5 步 取证（基线） | `{"query":"node_load1{instance=~\"...\"}","start":RFC3339,"end":RFC3339,"step":"60s"}` | `data.result[].values[][]`（秒级时间戳 + 数值） | 采样点 <2 → 判无数据；前后 1/3 均值比 ≥1.3 → 记「持续劣化」 |
| `pinpoint.drag_heatmap_tool` | 第 5 步 取证（链路入口） | `{"application_name":..., "from":13位毫秒,"to":13位毫秒}` | `traceIds[]`（取首个非空） | 无 `traceIds` → 跳过 trace，不伪造证据 |
| `pinpoint.get_transaction_trace_tool` | 第 5 步 取证 + 第 6 步 定因 | `{"trace_id":"<id>"}` | 根 span `elapsed`；子 span `executionMilliseconds` + `parentId`（兼容嵌套 `callStack` 与扁平数组） | 无 span → 跳过；非根 span 占根 `elapsed` ≥50% → 判「调用链瓶颈」并定级 `critical` |
| `elasticsearch.get_shards` | 第 3 步 验真 | 无参 | 分片 `state`（`STARTED` 正常）、`unassigned` 计数 | 存在未分配分片 → `sourceHealth[es]=degraded`，日志空结果不当作「无日志」 |
| `elasticsearch.search` | 第 5 步 取证（日志） | `{"index":"logs-*","query_body":{size:0,track_total_hits:true,range + query_string(host)}}` | `hits.total.value`；`relation=gte` 记下限 | 无候选主机 → **直接跳过**（防默认命中）；查询失败 → 回退本地 `log-analyzer`；两者皆失败 → `logErrors=0` 且不进证据集 |

**与巡检 T10 的差异**：排障侧 `query_string` 的 host 子句按候选主机列表拼成 `host:"h1" OR host:"h2" ...`，且必须先有候选主机；巡检侧逐主机查询。两者共用 `esTotalHits` 解析。

**降级口径**：`degradedSources()` 同时统计 `degraded` 与 `unavailable`；命中时排序后**所有候选置信度一律封顶 0.5**，问题单 `confidence=degraded`，会话 `status` 最多为 `investigating`，不会进入 `root_caused`。

### 12. 失败与降级矩阵

| 失败类型 | 典型错误 | 平台判定 | 证据链 `Status` | 是否继续 |
|---|---|---|---|---|
| 服务未启动 | `connection refused` | 该步不可用 | `error` | 继续其余步 |
| 超时 | `context deadline exceeded` | 该步 `NO_DATA` | `error` | 继续 |
| 工具未注册 | `unknown server` | 该数据端整体不可用 | `skipped` | 继续 |
| 工具被禁 | `tool denied` | 与未注册同 | `skipped` | 继续 |
| 业务 `isError` | 服务端 `isError:true` | 该步失败 | `error` | 继续 |
| 返回解析失败 | JSON/文本都无法识别 | `NO_DATA`，保留 `preview` | `warn` | 继续 |
| 返回空集合 | `[]` / `records:[]` | 视工具语义：告警=无告警；资产=账实不符（`P1`） | 按语义 | 继续 |
| 字段缺失 | 无 `state` / 无 `instance` | `NO_DATA`，**不猜默认值** | `warn` | 继续 |
| 末尾截断 | `Preview.truncated=true` | 结论仍基于结构化字段；原文仅预览 | `ok` | 继续 |

> 统一原则：**上游数据是证据源，不是决策源**。任何数据缺失只降低结论置信度，平台用四态显式表达，不把"查不到"翻译成"没问题"。

### 13. 数据流转链路（四条主链）

#### 13.1 身份映射链（所有其它链路的地基）

```
拓扑快照（data/platform/topo/*.json）
   ↓ 抽出 connectAddr / apolloAppId / apolloAppName
[应用键] [主机键]（NormalizeHost 去端口/小写/去尾点）
   ↓
pinpoint list_applications_tool ──► 回填 PinpointAppID/PinpointAppName（别名双向登记）
   ↓
cmdb cmdb_server_query（全量分页 200×5）──► 回填 IP / hostName / CMDB ID / 机房
   ↓
（可选）DNS 正反解
   ↓
identity_app / identity_host 落盘 + 内存索引（appAlias / hostAlias）
```

产出物：`/api/identity/{stats,apps,hosts,resolve}`。后续排障、巡检、稽核的所有"主机反查"都依赖这张表，否则会出现"Prometheus 有、CMDB 查无"的假风险。

#### 13.2 排障证据链（13 个工具调用点 / 10–11 条步骤）

```
请求（中间件类型 + 地址 / 应用）
  → 拓扑影响面（本地快照，不调上游服务）
  → ① Prometheus 活跃告警 ── list_alerts
  → ② Prometheus 目标存活 ── query(up)
  → ③ 数据源验真（M2，不建 Step，写 sourceHealth）── healthy / targets_metadata / series / get_shards
  → ④ CMDB 资产归属       ── cmdb_server_query（×≤5 主机）
  → ⑤ Pinpoint 应用清单   ── list_applications_tool
  → ⑥ Pinpoint 服务地图   ── get_server_map_tool
  → ⑦ 指标基线            ── range_query（采样点 <2 即 NO_DATA）
  → ⑧ 热力图取 traceId    ── drag_heatmap_tool
  → ⑨ 单笔调用链          ── get_transaction_trace_tool（非根 span ≥50% 判瓶颈）
  → ⑩ 日志证据            ── es.search（失败回退本地 log_analyzer）
  → ⑪ 规则排序 / 证据定因（置信度 = (0.25 + 0.10×来源数 + 0.02×条数，封顶 0.9) × 规则强度系数）
  → 归档：会话 + 问题单（DiagnosisTicket）+ 自动建工单/知识库

证据互证逻辑：
  Prometheus up=0 且 CMDB state=0（在线）→ "资产显示在线但心跳丢失"，指向网络/宿主机
  Prometheus 查无序列 且 CMDB 有记录     → "未纳管监控"，判 NO_DATA 而非健康
  CMDB 查无记录 但拓扑有依赖             → P1 账实不符
  子 span 占根 elapsed ≥50%              → 调用链瓶颈，问题单 critical
  任一源 degraded/unavailable            → 所有候选置信度封顶 0.5，禁止 root_caused
```

> 本节只保留压缩流程；**逐步骤的工具名、关键入参、产出与前端步号对照**统一维护在《排障使用动线与实现逻辑说明》§4.2，避免两处重复。

#### 13.3 巡检链（四态：NOT_TRIGGERED / RISK / NO_DATA / NOT_APPLICABLE）

```
拓扑行 → collectScopeHosts（按被依赖应用数降序，≤20 台）
  → 批次缓存 hostMCPCache（同主机同批次只查一次）
     ├─ T7  up            → prometheus.query
     ├─ T9  CMDB 一致性   → cmdb.cmdb_server_query
     ├─ T10 日志错误      → es.list_indices + es.search
     └─ T11 指标阈值      → prometheus.host_metrics_realtime
  → Finding（含 Evidence / Impact）→ 巡检报告 → 工单
```

**四态原则**：查询失败、无序列、无索引一律 `NO_DATA`，绝不降级成"正常"。这是平台跨服务数据质量的核心约束。

#### 13.4 告警 → 自动排障 → 工单 → 知识库

```
prometheus.list_alerts ─┐
Alertmanager /api/v2/alerts ─┤→ mergeAlerts（同 fingerprint 合并，补抑制态）
prometheus.range_query（劣化扫描）─┘
        ↓
   fingerprint 幂等 upsert（ticket / alarm_event）
        ↓
   四规则准入（firing / 未抑制 / P1 / 无关联会话）
        ↓
   自动创建排障会话（复用 9.2 证据链）
        ↓
   root_caused → 自动建工单 + 归档知识库（相似案例检索）
```

### 14. 缺口与对齐建议

#### 14.1 数据口径缺口

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | `from_ts/to_ts` 平台传 **UnixMilli**，Prometheus 侧时间却是**秒**/RFC3339 | Pinpoint 与 Prometheus 时间窗对不上，证据时间轴错位 | 在网关适配层统一「内部毫秒、出口按工具转」；对 pinpoint 明确 ms 契约并加断言 |
| 2 | `list_alerts` 的 Alert 字段**首字母大写、无 json tag** | 平台若按小写解析会全空 | 当前依赖 Go `encoding/json` 的大小写不敏感匹配才通过（脆弱）；建议服务端补 json tag，平台侧保留 `PromAlert` 兼容层 |
| 3 | Prometheus `query` 返回 `result` 为**文本行** | 需要正则/手工解析，易漏 | 计划性切换到 `data.result` 结构；网关侧已有 `PrometheusQuery/Samples` 双解析，保留但收敛 |
| 4 | CMDB 返回 `content[0].text` 双重编码 | 直接 `json.Unmarshal` 失败 | 已用 `ResultOf` 处理；建议 CMDB 直接返回 `structuredContent` |
| 5 | 分页口径不统一（CMDB `currentPage/pageSize` vs Prometheus `limit` vs Pinpoint `limit`） | 批量任务难以统一预算控制 | 引入统一 `QueryBudget`（最大条数/最大页数/总超时） |
| 6 | ES 无 schema 约定：索引名与 `host`/`level` 字段名未落地为配置基线 | T10 依赖 4 个环境变量，换集群即失效；字段不符时巡检 T10 恒 `NO_DATA` 且不报错 | 启动时调 `get_mappings` 自检字段，缺失则在巡检报告里显式提示"字段未对齐"；把 `ES_LOG_*` 收敛为部署基线 |
| 7 | 主机标识四套并存（IP / IP:port / hostName / node） | `instance` 前缀匹配易误配 | 保持 `NormalizeHost` + 严格归属二次校验；新增主机必须先落 identity |
| 8 | 应用标识两套（Pinpoint applicationName / EasyViews projectName / 平台 appId） | 排障可能匹配错应用 | 用 `build_app_mapping_tool` 的思想做一张三方映射表，落 identity；模糊包含匹配降级为"候选"而非"命中" |
| 9 | ES 上游服务默认不注册（`ES_MCP_URL` 为空） | 日志巡检恒 `NO_DATA` | 部署清单里把 ES 作为"可选但建议"项显式标注，避免误读为"无日志异常" |
| 10 | `up` 聚合为覆盖写（`up[host] = value`） | 同一主机多个 exporter 序列时，最后一条掩盖前一条的 0 | 改为"任一序列为 0 即失联"，或在 `map` 中保留切片后聚合 |
| 11 | 拓扑双源未定权威：EasyViews 在 `pinpoint-mcp` 与 `promthus-mcp` 各封装一份，5 组工具互为镜像 | 同一拓扑可能两个服务口径不同，平台无法判定谁为准 | 为每组拓扑工具指定唯一权威源并写入网关路由，禁止双源混用 |

#### 14.2 能力编排缺口（工具已有、平台未用）

| 优先级 | 能力 | 用哪个工具 | 价值 |
|---|---|---|---|
| P0 | 单笔慢调用下钻 | pinpoint `get_transaction_trace_tool` | 从"服务级"下钻到"单次请求"，补齐排障最后一公里 |
| P0 | 指标 ↔ 链路打通（trace ↔ metric 未打通） | prometheus `exemplar_query` | 工具已具备返回 `traceId`/`spanId` 的能力，但平台排障链路未使用，调用链证据与指标证据仍是两条平行线；接入后与上一条形成闭环 |
| P1 | 变更关联 | cmdb `project_deployment_query` | 排障时自动比对"故障前是否有发布"，直接给出变更嫌疑 |
| P1 | 架构风险常态化 | pinpoint `analyze_link_topology_tool` + `analyze_host_concentration_tool` | 环依赖、长调用链、宿主机集中部署，从"事后排障"提前到"事前体检" |
| P2 | 外网暴露面 | cmdb `server_public_ip_query` | 与安全/合规打通 |
| P2 | ES 字段自发现 | es `get_mappings` | 消除硬编码字段配置 |
| P3 | 规则治理 | prometheus `list_rules` | 规则覆盖率 / 空规则 / 长期不触发规则盘点 |

#### 14.3 建议的平台侧目标数据模型

```
AppIdentity
  appId, apolloAppId, apolloAppName
  pinpointAppId, pinpointAppName
  easViewsProjectName, deployNode
  cmdbProjectId, cmdbProductId
  hosts[]

HostIdentity
  key（归一键）
  ips[], hostNames[], addrs[]
  cmdb: {id, node(机房), state, operA, operB, usingBy, environment, specification, productProjectList}
  prom: {instance[], up, cpuUsage, memUsage, diskUsage, load, ...}
  es:   {index, errorCount(lookback), lastLogAt}
  pinpoint: {middlewareType, instanceCount}

Evidence（统一证据条目）
  source, tool, args, latencyMs, status(ok/error/skipped)
  window {from, to, unit}
  payloadPreview（≤4KB）+ 关键指标摘要
```

这套模型能把四个服务的返回**收敛成两类实体（应用、主机）+ 一条证据**，而不是让每个业务模块各自解析各家的 JSON。
