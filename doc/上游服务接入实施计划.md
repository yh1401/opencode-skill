# 上游服务接入实施计划（对齐流转契约）

> **版本**：v3。契约基线：[上游服务数据契约与工具对照](./上游服务数据契约与工具对照.md)（下称"契约文档"：第一部分定义**平台该消费什么**，第二部分 §3.1/§4.1/§5.1/§6.1 给出**四个服务 71 个工具的完整介绍与请求/返回参数**；本文个别章节沿用 v3 写作时的 68 快照）。
> v2 按 **契约条款 → 任务 → 依赖 → DoD** 拆到可派工粒度；v3 在此基础上补齐三件事：**全量工具分级（§11，旧快照 68 / 现行 71）**、**各服务上下游依赖（§12）**、**接口调用顺序与编排队列（§13）**。
>
> 阅读路径：要**派工**看 §2 WBS；要**决定某个工具接不接**看 §11；要**确认上游前置条件与下游消费方**看 §12；要**排调用时序、查谁先谁后**看 §13；要**卡验收**看 §4 门禁与 §5 测试。
>
> **实施状态（2026-11-06）**：M1 网关与归一、M2 数据源验真、M3 问题单、M4 三路取证（range_query / 调用链下钻 / ES 日志）、M5 证据驱动定因已全部落地；平台已消费 **15 / 71** 个工具（Pinpoint 4 / Prometheus 7 / CMDB 1 / ES 3；旧快照按 68 计）。L2 的 `drag_heatmap_tool` → `get_transaction_trace_tool` 链路已完成，L3 的 `healthy` / `targets_metadata` / `series` 与 L6 的 `get_shards` 已接入。详见《契约文档》第二部分 §0.3 的实施后口径与 §9.10 契约（五步逐接口清单见《排障使用动线与实现逻辑说明》附录 A）。
>
> **工具数口径（2026-11-13 校对）**：最新契约口径为 **71**（Pinpoint 25 / Prometheus 36 / CMDB 5 / ES 5，见《上游服务数据契约与工具对照》v3.1）。本文 §11 分档表沿用旧快照 **68**（Pinpoint 22），少算的 3 个是 `analyze_nodes_runtime_tool`、`arch_task_open_tool`、`arch_task_status_tool`；本地 mock 为 **63**（Pinpoint 17 / 36 / 5 / 5），平台实际消费 15。三者差异来自快照时间与构建裁剪，不改变 §11 的"接不接"判断，故不改写分档计数，避免与契约文档错位。

## 0. 本计划的组织方式

| 要素 | 约定 |
|---|---|
| 任务编号 | `<域><序号>`，如 `C2` = Prometheus 域第 2 项 |
| 输入 | 契约文档第一部分的对应契约小节（§3–§6）与条件（§9） |
| 产出 | 代码落点（文件）+ 可观测结果 |
| DoD | 引用契约文档第一部分 §13 的具体断言，且必须可被自动化验证 |
| 依赖 | 只写**硬依赖**；软依赖在备注中说明 |
| 角色 | 后端 / SRE / CMDB / ES / 前端 |

**四个域可并行，但两条汇合线不能跳**：

```
线1（先行，可独立交付）：A → C → I        （存活 + 指标 + 告警）
线2（地基）：            A → D3 → F → G/H  （资产 + 身份）
线3（调用链）：          A → B1 → B2 → G   （应用 + 服务地图）
线4（可选）：            A → E             （日志，依赖字段对齐）
汇合：G（排障）、H（巡检）、I（告警）都依赖 F 完成
```

| 单服务灰度 | 服务首次接入 | 只填该服务 URL，其余留空/mock | 清空该 URL |
| 全局降级 | 接入后异常率升高 | `MCP_ENABLED=false` | 恢复开关 |
| 巡检暂停 | 巡检超预算或 `NO_DATA` 异常高 | `INSPECT_MCP_ENABLED=false` | 恢复开关 |
| ES 摘除 | 索引/字段问题 | `ES_MCP_URL` 置空 | 填回 |
| 工具熔断 | 单工具返回异常 | `MCP_ALLOW_TOOLS` 收紧 | 恢复白名单 |

**回滚判据（量化）**：`NO_DATA` 占比 > 50%，或单次巡检耗时超批次预算，或同一 fingerprint 事件数异常增长 → 先回滚对应服务，再定位契约。

## 12. 各服务上下游依赖

### 12.1 依赖总图

```
                ┌──────────── 上游（真实数据源，平台不直连） ────────────┐
                │ Pinpoint Web API + EasyViews      → pinpoint-mcp      │
                │ Prometheus API + Alertmanager + EasyViews → promthus-mcp │

                │ Elasticsearch REST                → elasticsearch-mcp  │

                                        ▼
        ┌───────────────┬───────────────┼───────────────┬───────────────┐
        ▼               ▼               ▼               ▼               ▼
   identity 地基    diagnose 排障    inspect 巡检    alarm 告警      topo / 知识库
```

**依赖方向铁律**：数据只能「服务 → 平台」，平台**不回写**任何上游服务；四个服务之间也**互不调用**，所有跨源关联都在平台的 `identity` 层完成。

| 关键缺口 | 返回是 `content[0].text` 里的**字符串化 JSON**（`{code,message,fail,data}`，`data={records,total,currentPage,pageSize,pages}`）；`state` 语义需映射 |

### 12.5 Elasticsearch 上游服务

| 维度 | 内容 |
|---|---|
| 上游系统 | Elasticsearch REST（`_cat/indices`、`_mapping`、`_search`、`_esql`、`_cat/shards`） |
| 上游前置条件 | ① `ES_MCP_URL` 非空，否则整个服务**不注册**；② `logs-*` 类索引已创建且有数据；③ 字段约定 `ES_LOG_INDEX` / `TIME_FIELD` / `LEVEL_FIELD` / `HOST_FIELD`（默认 `logs-*` / `@timestamp` / `level` / `host`）与真实 mapping 一致；④ 请求超时 `ES_REQUEST_TIMEOUT_SECS=30`；⑤ 全部工具 `read_only_hint=true` |
| 产出数据 | 索引清单与文档数；字段映射；日志命中数与样本；ES\|QL 结果；分片状态 |
| 下游消费 | `inspect` T10（H4）、`diagnose` step⑥、日志分析页、稽核 |
| 时序前置 | `list_indices` → `get_mappings` → `search`；`list_indices` 每批次只调一次，禁止逐主机调用 |
| 关键缺口 | 无固定 schema（靠 E3 自检）；返回是「固定文案 + JSON」混排，需 `ContentJSON`；`Total results` 与 `hits.total` 两种计数口径 |

### 12.6 跨服务依赖矩阵

| 供给方 → 消费方 | Pinpoint | Prometheus | CMDB | ES | 说明 |
|---|---|---|---|---|---|
| Pinpoint | — | 弱（`exemplar_query` 反向定位 traceId） | **强**（应用 → 部署项目 → 主机 IP） | 弱（应用名作为日志检索补充维度） | Pinpoint 提供"谁在调谁" |
| Prometheus | 弱（指标点 → traceId） | — | 中（`instance` 的 IP 去 CMDB 查归属） | 弱（时间窗对齐） | Prometheus 提供"是否活着/是否变慢" |
| CMDB | **强**（主机 IP → 应用名） | **强**（IP 归一后做 `instance` 匹配） | — | 中（`hostName` 字段过滤） | CMDB 是唯一的主机权威源 |
| ES | 弱 | 弱 | 中（用 CMDB 主机名补 `host` 字段） | — | ES 只提供"发生了什么" |

**三条硬依赖**（缺任一则结论不可信）：
1. `CMDB.ip` → `Prometheus.instance`：IP 归一（F1）不做，`up` 与资产永远对不上。
2. `Pinpoint.applicationName` → 平台应用实体：映射（L1/F2）不做，服务地图的边无处挂载。
3. `CMDB.hostname` → `ES.host`：字段不一致（E3）不校准，T10 会静默全 0。

## 13. 接口调用顺序

### 13.1 全局编排六原则

| # | 原则 | 具体约束 |
|---|---|---|
| 1 | 先自检后业务 | 每个采集周期第一次调用必须是健康自检；自检失败直接降级，不进入业务链 |
| 2 | 先地基后证据 | `identity` 未构建完成前，G/H/I 不允许开跑（沿用 v2 禁止顺序） |
| 3 | 由粗到细 | 应用 → 拓扑 → 告警 → 指标 → 资产 → 日志，先定位再取证 |
| 4 | 同类合批 | `list_indices` / `list_applications` / `list_nodes` / `get_mappings` 每批次只调一次并在批次内缓存 |
| 5 | 不断链 | 任一步 `NO_DATA` 不短路后续步骤，继续采集，最后按四态优先级汇总 |
| 6 | 写操作零编排 | P3 工具永不进入自动流程，也不进入人工触发的批量任务 |

### 13.2 S0 全局启动自检（每实例启动一次 / 每小时一次）

| 序 | 服务 | 工具 | 判据 |
|---|---|---|---|
| 1 | 网关 | `probe` × 4 | 四端点可达；`ES_MCP_URL` 为空视为「未接入」而非「故障」 |
| 2 | Prometheus | `build_info` → `healthy` → `ready` → `flags` → `config` → `runtime_info` → `wal_replay_status` | 全部返回即视为上游健康；任一失败标记该源 `degraded` |
| 3 | Prometheus | `alertmanagers` | 告警通道可达，否则 I 链改用 `list_alerts` 单通道 |
| 4 | Prometheus | `list_targets` → `targets_metadata` | 得到抓取面基数，作为后续"未纳管"判定的分母 |
| 5 | ES | `list_indices` → `get_mappings` | 索引存在 + 字段名与 `ES_LOG_*` 一致，否则 H4 标「字段未对齐」 |
| 6 | Pinpoint | `list_applications_tool` | 应用基数为 0 时，整个 Pinpoint 域标 `empty` |
| 7 | CMDB | `cmdb_server_query`（`pageSize=1`） | 验证双层解码与分页字段，失败则 D 域不可用 |

### 13.3 S1 身份地基序列（G/H/I 的强制前置）

| 序 | 工具 | 输入来源 | 产出 |
|---|---|---|---|
| 1 | `cmdb_server_query`（全量分页） | `IDENTITY_CMDB_PAGES × PAGE_SIZE` | 主机全集：`ip` / `hostname` / `state` / 机房 |
| 2 | `project_deployment_query`（L5） | 步骤 1 的工程名 | 部署记录：工程 ↔ 主机 |
| 3 | `list_applications_tool` | — | 应用名 + `service_type_code` |
| 4 | `list_nodes_tool` → `get_module_topology_tool`（L1） | 节点前缀 | 模块 ↔ 工程 |
| 5 | `build_app_mapping_tool`（L1） | 步骤 3 + 步骤 4 | 项目名 ↔ `applicationName`（含 `ambiguous` / `unmatched`） |
| 6 | `get_project_deploy_tool`（L1） | 节点名 | 项目 ↔ 云主机 IP |
| 7 | 平台合并写 `identity_app` / `identity_host` | 1–6 | 四元组：`ip + hostName + cmdb.id + pinpoint 应用名` |

> 顺序不可颠倒：**3 必须在 5 之前**（映射需要应用清单）；**4 必须在 5、6 之前**（模块与部署都以节点为入参）；**1 必须在 2 之前**（部署记录要按工程名去查）。

### 13.4 S2 排障序列（单次会话，已实施 12 步）

| 步 | 工具 | 失败/降级时 |
|---|---|---|
| ① 应用清单 | `list_applications_tool` | 无 `appId` → ① ② `skipped`，② 起按中间件/主机视角继续 |
| ② 服务地图 | `get_server_map_tool`（13 位毫秒） | 空窗 → 该步 `warn`，不判健康 |
| ③ 数据源验真 | `healthy` → `targets_metadata` → `series` → `get_shards` | 任一源异常 → `sourceHealth=degraded/unavailable`，结论置信度封顶 0.5 |
| ④ 告警 | `list_alerts` | 字段大写兼容失败 → 文本兜底并标 `degraded` |
| ⑤ 存活 | `query`（`up{instance=~"IP:.*"}`） | 无序列 → 结合 `targets_metadata` 分流「未纳管」与「采集故障」 |
| ⑥ 资产 | `cmdb_server_query` | 无记录 → 信号 `cmdb_unmatched`（账实不一致） |
| ⑦ 拓扑影响面 | 平台 `topo` 自有数据 | 断源 → 仅少一张图，不影响结论 |
| ⑧ 指标基线 | `range_query`（`node_load1` 近 60 分钟，`step=60s`） | 采样点 <2 → 该步 `warn`；前后 1/3 均值比 ≥1.3 判「资源使用劣化」 |
| ⑨ 调用链热力图 | `drag_heatmap_tool` | 无 `traceIds` → 跳过下钻，不影响主结论 |
| ⑩ 单笔调用链 | `get_transaction_trace_tool` | 单 span 占 `elapsed` ≥50% → 判「调用链瓶颈」，根 span 不参与 |
| ⑪ 日志取证 | ES `search`（按候选主机过滤）→ 失败回退本地 log-analyzer | 无候选主机或索引不存在 → 跳过 ES，不制造假证据 |
| ⑫ 汇总 | 问题单（实体/级别/信号/时间窗/影响面/可信度）+ 证据驱动排序 | 无证据 → 强制「疑似」且 `status=no_data` |

> 第 ③ 步是新增的「采集故障 vs 业务故障」分水岭：`healthy/targets_metadata/series/get_shards` 任一不可用，先降可信度，再谈根因。

### 13.5 S3 巡检序列（批次内）

```
批次开始
  ├─ 全局一次：list_indices（T10 前置）
  └─ 每主机（≤ INSPECT_MCP_MAX_HOSTS，默认 20）
       ├─ T7  query(up)                          ← 先判存活
       ├─ T11 host_metrics_realtime              ← 存活才查指标
       ├─ T9  cmdb_server_query                  ← 资产比对
       ├─ T8  get_server_map_tool（按应用聚合）    ← 每应用一次，不按主机
       └─ T10 search（host 字段过滤）              ← 复用批次索引结果
  → 四态汇总（NO_DATA > RISK > NOT_TRIGGERED > NOT_APPLICABLE）
```

顺序理由：**T7 先于 T11**（主机失联时指标为空属正常，不能重复记风险）；**T8 按应用聚合**（同一应用只查一次，避免 20 台主机打 20 次服务地图）；**T10 复用索引**（`list_indices` 不逐主机调用）。

### 13.6 S4 告警序列

`list_alerts` → 归一（大小写 + `severity` 缺省 `info`）→ `fingerprint = lower(alertname|instance|severity)`（`instance` 先归一）→ 四道准入（firing / 未抑制 / 级别 / 无进行中会话）→ 触发 S2 排障 → 结论回写。

> 只在准入通过后调用 S2，避免告警风暴放大为排障风暴。

### 13.7 各服务内部调用顺序

| 服务 | 顺序 | 说明 |
|---|---|---|
| **Pinpoint** | `list_applications_tool` → `list_nodes_tool` → `get_module_topology_tool` → `build_app_mapping_tool` → `get_server_map_tool` → `drag_heatmap_tool` → `get_transaction_trace_tool`；分析类放在最后：`list_arch_rules_tool` → `arch_label_probe_tool` → `arch_metric_query_tool` → `arch_rule_check_tool` | 应用清单提供 `service_type_code`，节点清单提供后续所有 EasyViews 入参 |
| **Prometheus** | 自检包 → `list_targets` / `targets_metadata` → `label_names` / `label_values` / `metric_metadata` → `series` → `query` / `range_query` / `exemplar_query` → `host_metrics_realtime` / `host_metrics_trend` → `list_alerts` / `list_rules` / `alertmanagers` | 先确认"有没有被采集"，再判"值是多少" |
| **CMDB** | `cmdb_server_query` → `project_deployment_query` → `server_public_ip_query` → `product_query` → `project_basis_query` | 资产是锚点；部署与公网 IP 依赖资产 IP |
| **ES** | `list_indices` → `get_mappings` → `search` → `get_shards` → `esql`（默认不用） | 索引存在性 → 字段正确性 → 查询；`get_shards` 用于判因 |

### 13.8 并发、缓存与预算

| 项 | 约定 |
|---|---|
| 并发度 | 单服务并发 ≤ 2；跨服务可并行（如 ④ `query` 与 ⑤ `cmdb_server_query` 并行） |
| 单会话调用上限 | 排障 ≤ 20 次；巡检 ≤ `MAX_HOSTS × 3 + 全局 2` |
| 批次缓存 | `list_indices` / `list_applications` / `list_nodes` / `get_mappings` / `list_targets` 批次内唯一 |
| 单次超时 | `MCP_TIMEOUT_MS=8000`；批量任务用独立超时，不继承默认值 |
| 熔断 | 同一工具连续 3 次失败 → 本批次跳过该工具并标 `degraded` |
| 截断 | 结果按 `Preview(4096)` 落证据链，原文超出标 `truncated` |

### 13.9 顺序相关的验收用例

| # | 用例 | 期望 |
|---|---|---|
| 1 | 跳过 `list_indices` 直接 `search` | 视为编排违规，测试应拦截 |
| 2 | `get_mappings` 未跑就开 T10 | 报告必须出现「字段未校验」提示 |
| 3 | 同一应用 20 台主机巡检 | `get_server_map_tool` 只被调用 1 次 |
| 4 | `up` 无序列但 `targets_metadata` 有该 target | 判「采集异常」，不判「主机失联」 |
| 5 | `ES_MCP_URL` 为空 | 跳过 S0 第 5 步，H4 全 `NO_DATA`，不报错 |
| 6 | CMDB 分页只拉了第 1 页 | 报告必须显式输出「未覆盖主机数」，不得静默 |
