# 架构巡检性能优化建议（pinpoint-mcp + arch-opt-query）

> 基于 2026-11-02 全节点巡检实测：30 个节点串行跑完，单节点 `arch_label_probe_tool` 耗时 **10~11s**，光前置探测就 ~5.5 分钟，全程 12 分钟以上。
> 目标：**12 分钟 → 2~3 分钟**，共 4 处改动，约 100 行。

---

## 一、问题定位

`arch_label_probe_tool` 一次调用内部完全是串行的：

```
7 个指标族 × 每个 4 次 HTTP（labels / cmdb_node / cluster / env）= 29 次请求，全 await 串行
+ 1 次 label_values("cluster")
≈ 30 次 HTTP × 250ms ≈ 7.5s，叠加 MCP 往返 ≈ 10~11s/节点
```

而 Agent 对 30 个节点是**逐个串行调用**，于是 `30 × 11s ≈ 330s`。

两个层面的浪费：

| 层面 | 现状 | 浪费 |
|---|---|---|
| MCP 内部 | `arch_label_probe` 串行发 30 次 HTTP | 单节点 11s → 可到 3s |
| HTTP 连接 | `httpx.AsyncClient` 未配连接池 | 每次请求多一次 TCP/TLS 握手 |
| 编排层 | Agent 30 节点串行发 30 次 tool call | 30 次 → 可压到 1 次 |

## 二、改动清单

### P0-1 探测内部改并发（arch_tools.py L3825-3828）

现状：

```python
matrix: list[dict] = []
for family, metrics in _PROBE_METRIC_FAMILIES.items():
    for metric in metrics:
        item = await _probe_metric(client, metric, family, node, env, deployment)
        matrix.append(item)
```

改为：

```python
async def _safe_probe(metric: str, family: str) -> dict:
    try:
        return await _probe_metric(client, metric, family, node, env, deployment)
    except Exception as e:
        # 保持矩阵完整，避免 _stats() 的分母随异常缩水
        return {"metric": metric, "family": family,
                "status": "FAIL", "error": str(e)[:200]}

tasks = [_safe_probe(m, f)
         for f, ms in _PROBE_METRIC_FAMILIES.items() for m in ms]
matrix = list(await asyncio.gather(*tasks))
```

同时把下面这句 `label_values("cluster")` 也并入同一批 gather（可选）：

```python
cluster_task = client.label_values("cluster")
...
matrix, cluster_values = await asyncio.gather(
    asyncio.gather(*tasks), cluster_task, return_exceptions=True
)
```

> 注意：单节点并发只有 7 路，对 Prometheus 压力可忽略，不需要再加 Semaphore。

**预期：11s → 3s**

### P0-2 加 HTTP 连接池（prometheus_client.py L32-36）

现状：

```python
self._client = httpx.AsyncClient(
    base_url=self.base_url,
    timeout=timeout,
    verify=ssl_verify,
)
```

改为：

```python
self._client = httpx.AsyncClient(
    base_url=self.base_url,
    timeout=timeout,
    verify=ssl_verify,
    limits=httpx.Limits(max_connections=32, max_keepalive_connections=16),
)
```

> 不要加 `http2=True`，会引入 `h2` 依赖，收益不确定。

**预期：每次请求 -150~250ms；配合 P0-1 的 7 路并发，收益叠加**

### P0-3 新增「全节点」批量工具（最关键）

Agent 串行调 30 次是**编排层**的问题，只能靠 MCP 侧提供一把梭的工具解决。新增 2 个工具，内部并发跑节点。

`arch_tools.py` 新增：

```python
async def arch_label_probe_all(node_prefix: str = "云公司",
                               env: Optional[str] = None) -> dict:
    """一次探测所有节点的标签口径，内部并发"""
    nodes_res = await list_nodes(node_prefix=node_prefix)
    nodes = [n.get("node") for n in nodes_res.get("nodes", []) if n.get("node")]
    sem = asyncio.Semaphore(config.ARCH_NODE_CONCURRENCY)

    async def _one(n: str) -> tuple[str, dict]:
        async with sem:
            try:
                return n, await arch_label_probe(n, env=env)
            except Exception as e:
                return n, {"status": "FAIL", "error": str(e)[:200]}

    pairs = await asyncio.gather(*[_one(n) for n in nodes])
    results = dict(pairs)
    return {
        "total": len(nodes),
        "results": results,
        # 汇总每个节点的建议取数口径，Agent 不用逐节点读原始结构
        "summary": [
            {"node": n, "mode": (r.get("verdict") or {}).get("suggestedMode"),
             "status": r.get("status")}
            for n, r in pairs
        ],
    }


async def analyze_all_nodes(node_prefix: str = "云公司",
                            rules: Optional[list[str]] = None,
                            env: Optional[str] = None) -> dict:
    """一次跑完所有节点的 8 条规则，内部按节点并发"""
    nodes_res = await list_nodes(node_prefix=node_prefix)
    nodes = [n.get("node") for n in nodes_res.get("nodes", []) if n.get("node")]
    sem = asyncio.Semaphore(config.ARCH_NODE_CONCURRENCY)

    async def _one(n: str) -> tuple[str, dict]:
        async with sem:
            try:
                return n, await analyze_node_runtime(node=n, rules=rules, env=env)
            except Exception as e:
                return n, {"status": "FAIL", "error": str(e)[:200]}

    pairs = await asyncio.gather(*[_one(n) for n in nodes])
    return {
        "total": len(nodes),
        "nodeResults": dict(pairs),
        # 跨节点风险汇总，避免 Agent 自己再遍历一遍
        "riskIndex": [
            {"node": n, "riskCount": sum(
                int(rr.get("riskCount") or 0)
                for rr in (r.get("ruleReports") or [])),
             "rules": [rr.get("rule") for rr in (r.get("ruleReports") or [])
                       if (rr.get("riskCount") or 0) > 0]}
            for n, r in pairs
        ],
    }
```

`config.py` 新增一个并发旋钮（默认 3，避免 30 节点 × 8 规则同时打穿 Prometheus）：

```python
# 节点级并发：一次巡检多个节点时，同时分析的节点数
ARCH_NODE_CONCURRENCY: int = int(os.environ.get("ARCH_NODE_CONCURRENCY", "3"))
```

`server.py` 参照 `arch_label_probe_tool` / `analyze_node_runtime_tool` 的注册方式，加两个 tool 即可。

**预期：Agent 侧 60 次 tool call → 2 次**

### P1-1 SKILL.md 增加编排约束（arch-opt-query）

在批量巡检场景明确写死：

```markdown
## 全节点巡检（多节点）

⚠️ 禁止对节点列表逐个串行调用工具。

1. 一次性调用 `arch_label_probe_all_tool`（内部并发）
2. 一次性调用 `analyze_all_nodes_tool`（内部并发）
3. 仅当某节点返回 FAIL / 口径异常时，才对该节点单独下钻
4. 不支持上述批量工具时，才退化为逐节点调用，并在报告中标注"N 次串行调用"
```

> 这条是**当前就能生效的兜底**：在 MCP 未上线批量工具前，Agent 至少可以在同一条消息里并行发多个 tool_use，而不是一次一发。

### P1-2 顺带修：cluster 映射缺第二个集群（config.py L92-94）

现状只配了一个 cluster，但广州4d 实际有两个：

```
广州4d生产（289 deployment） + 看家广州4d多az生产（131 deployment）
```

这意味着每次广州4d 巡检漏掉 ~30% 的应用。

改动需要动数据结构（node → 多个 cluster），共 3 处：

1. `config.py`：`ARCH_NODE_CLUSTER_MAP: dict[str, list[str]]`，解析时按 `,` 再拆一层
2. `arch_tools.py` `_node_label()`：返回 `("cluster", "a|b")`
3. `_label_selector()` 与 `_probe_metric()`：value 含 `|` 时用 `=~` 而非 `=`（2 处）

**预期：广州4d 覆盖 289 → 420 个 deployment**

## 三、预期收益

| 改动 | 改动量 | 预期收益 |
|---|---|---|
| P0-1 探测内并发 | ~10 行 | 单节点 11s → 3s |
| P0-2 连接池 | 1 行 | 每请求 -150~250ms |
| P0-3 全节点批量工具 | ~70 行 | 60 次调用 → 2 次 |
| P1-1 SKILL 约束 | 文档 | 防止 Agent 回退串行 |
| P1-2 多集群映射 | ~20 行 | 覆盖率 +30% |

**30 节点全量巡检：12 分钟 → 2~3 分钟。**

---

## 四、验收方式

1. **单节点**：`arch_label_probe_tool(node="云公司->广州4d")` 连续跑 3 次，耗时稳定 < 4s（现在 ~11s）
2. **全节点**：`arch_label_probe_all_tool()` 一次返回 30 个节点，总耗时 < 60s
3. **规则分析**：`analyze_all_nodes_tool()` 一次返回 30 个节点，`riskIndex` 与逐节点跑的结果一致
4. **覆盖率**：广州4d 的 `scope.totalDeployments` 从 289 变成 420
5. **回归**：单节点原有返回结构不变，`verdict.suggestedMode` 取值不受影响
